## 二、定位：后端交易为主线，AI 工程化为亮点

### 2.1 一句话定位

> 这不是一个"AI 客服 Demo"，而是一个**把高并发交易的一致性做深、把大模型当外部依赖治理好**的后端项目——交易链路（原子预扣 → 异步削峰 → 跨系统最终一致 → 可观测）是主线，AI 能力是工程化落地的亮点。

### 2.2 为什么这样定（关键决策）

| 决策 | 理由 |
|------|------|
| **交易为主线，AI 为亮点**（而非 AI 为主） | 纯 AI 项目（Agent/RAG 堆砌）在 Java 后端岗是"不对口"的；后端交易（一致性/消息/缓存）才是 Java 岗的硬通货 |
| **不写区块链存证** | 区块链在 2026 秋招后端岗认可度有限，写了反而分散主线、引发"这是不是 Web3"的误判 |
| **不写 Advanced RAG 作为独立条** | RAG 命中率是 AI 指标，后端面试官不 care；压缩进 AI 工程化一条即可 |
| **保留"毒消息修复"作为亮点** | 这是真实踩坑故事，最能证明"不是背教程" |

### 2.3 故事线（面试 1 分钟版）

"我这个项目最核心的是一条**高并发交易的完整链路**：限时抢购从 Redis 原子预扣开始，经过 MQ 异步削峰，最后消费者落库，中间用本地消息表 + 定时对账保证跨系统最终一致。

这条链路里我踩过一个真实的坑：消息重试计数失效导致毒消息无限重投，我定位到根因是重新入队不累计重试次数，改用 Redis 计数后解决了。

除了交易，我还把大模型当作不可靠外部依赖做了服务治理——多模型路由、故障降级、分级限流、语义缓存，用评测系统验证效果、用全链路追踪做成本归因。"

## 四、简历优化策略（对齐最新版）

### 4.1 项目标题与描述

- 标题：「本地生活商户服务平台（高并发交易 + AI 智能客服）」。
- 项目描述聚焦**交易一致性主线**，AI 作为工程化亮点收尾。

### 4.2 五条工作内容（最新定稿，逐条措辞已优化）

1. **跨系统数据一致性**：针对三阶段跨系统操作（Redis 预扣 → MQ 异步投递 → 消费者落库）导致的库存泄漏，引入本地消息表 + 定时对账 + 失败补偿，将跨系统操作收敛为最终一致；对账先反查订单是否落库再决定补偿，避免"消息已送达却误回滚"造成的库存透支，配合订单超时自动关单与库存回补，异常场景下库存与订单守恒。

2. **高并发交易的库存一致性**：针对高并发抢购下的库存透支与重复提交，采用 Redis Lua 脚本将库存校验、扣减与单人限购约束原子化，消除"读-判-写"竞态窗口；数据库层以乐观锁 CAS 兜底并发扣减正确性，唯一索引保证写入幂等，形成“Redis 原子操作 + DB 乐观锁”的双层保障。

3. **异步解耦与消息可靠消费**：针对流量洪峰下的消息丢失与消费积压，引入 RabbitMQ 将订单落库从同步链路解耦，核心接口响应时间由 350ms 降至 130ms；结合 Direct Exchange 精准路由、手动确认、死信队列与失败重试保障可靠投递，并修复消费端重试计数失效导致的消息循环重投（毒消息堆积）问题。

4. **全链路追踪与可观测性**：建设请求级全链路追踪，以 traceId 贯穿 Redis、MQ、数据库与模型调用，实现一次请求跨组件的日志串联与耗时定位；基于调用追踪做成本归因与容量评估，为限流阈值与降级策略提供量化依据；接入 Prometheus + Micrometer 输出核心指标，构建从采集到告警的监控链路。

5. **AI 能力工程化与治理**：针对客服多意图场景，构建"路由 + 专业子智能体"编排架构，工具调用准确率由 72% 提升至 89%，自建 LLM-as-Judge 评测闭环，实现准确率的自动化回归验证；将大模型作为不可靠外部依赖治理，通过多模型路由、故障降级、分级限流与语义缓存，整体调用成本降低 50%。

### 4.3 技能栏

- Java 主线：Java / Spring Boot / MySQL / Redis / RabbitMQ / MyBatis-Plus / Linux / Git。
- AI 工程：LangChain4j / LLM-as-Judge 评测 / Agent 可观测 / 语义缓存。
- 加分：全链路追踪 / 本地消息表 / 分布式 ID。
