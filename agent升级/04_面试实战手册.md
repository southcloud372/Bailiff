### 背景与定位
这个项目是**本地生活商户服务平台**，有两条业务线：**高并发交易**（限时抢购 + 订单交易）和 **AI 智能客服**。交易链路是主线，AI 是工程化落地的亮点。它不是教程 Demo——交易一致性有完整闭环（原子预扣 → 削峰 → 最终一致 → 可观测），AI 有治理（评测 + 限流 + 降级 + 缓存）。

### 交易链路：高并发下单的一致性闭环
- **同步链路**：`seckillVoucher()` 入口做滑动窗口限流 → `seckill.lua` 单次 EVAL 完成「活动存在性 + 时间窗口 + 库存校验 + 限购校验 + 扣减」（消除读-判-写竞态）→ 写本地消息表（PENDING）→ 投递 MQ → 立即返回订单号。同步路径零 DB 查询。
- **异步链路**：`OrderMessageListener` 消费 → `createVoucherOrder()`（`@Transactional`）落库——先插订单（唯一索引幂等）再扣库存（`WHERE stock>0` 乐观锁）→ 收敛消息表为 CONFIRMED。
- **最终一致**：`SeckillMessageReconcileTask` 定时对账，扫描 PENDING 记录，先反查订单是否落库，再决定重投或补偿；`OrderTimeoutListener` 延时关单（TTL 15min）+ `restore_stock.lua` 双端回补。
- **毒消息修复（真实踩坑）**：重试计数原读 `x-death` 头，但 `basicNack(requeue=true)` 重新入队不写 x-death → 计数恒 0 → 必然失败的消息无限重投、死信队列失效。改用 Redis 计数 + 业务/系统异常分流后闭环。

### 可观测：全链路追踪
`TraceIdFilter` 在请求最外层生成 traceId 注入 MDC，日志 pattern 输出 `%X{traceId}`，一次下单从「限流 → 预扣 → 投递 → 落库 → 对账」日志可同一 ID 串联。`TraceRecorder` 对 AI 链路做 span 级成本归因，`TokenCostTracker` 用 Micrometer 暴露 Token 用量/限流触发指标到 Prometheus。

### AI 客服：工程化落地
- **多 Agent 编排**：RouterAgent 意图识别 + ShopAgent/OrderAgent/ReviewAgent 各管一域，工具从 27 个降到 5-8 个，准确率 72%→89%；意图识别失败回退通用助手（降级）。
- **评测闭环**：AgentEval（LLM-as-Judge + 标注测试集）跑批输出准确率，改 prompt 可回归。
- **治理**：ModelRouter 多模型轮询 + 故障降级、TokenCostTracker 用户/全局双维度限流、SemanticCache 语义缓存（同义改写命中）。

### 架构演进
V1 单一 Assistant + Redis RAG → V2 多 Agent + PgVector → V3 秒杀链路可靠性（Lua + MQ + 乐观锁）→ V4 跨系统一致性（本地消息表 + 对账 + 毒消息修复）→ V5 AI 工程化（评测/追踪/缓存/治理）。每次演进由明确问题驱动，主线是"能用 → 好用 → 一致 → 可观测 → 敢上线"。

## 2.1 工作内容一：跨系统数据一致性（本地消息表 + 对账 + 补偿）

> 简历原文：针对三阶段跨系统操作（Redis 预扣 → MQ 异步投递 → 消费者落库）导致的库存泄漏，引入本地消息表 + 定时对账 + 失败补偿，将跨系统操作收敛为最终一致；对账先反查订单是否落库再决定补偿，避免"消息已送达却误回滚"造成的库存透支，配合订单超时自动关单与库存回补，异常场景下库存与订单守恒。

### Q2.1.1（简单）你的"跨系统数据一致性"到底解决什么问题？为什么会有库存泄漏？

**结论：** Redis 预扣和 MySQL 落库之间隔着 MQ，中间任何一个环节失败，Redis 已经扣了库存、订单却没建成，库存就被"锁死"了——这叫库存泄漏。

**原理：** 下单链路跨三个系统：① Redis Lua 原子预扣（扣库存 + 记限购）；② MQ 异步投递；③ 消费者落库 MySQL。这三步不是原子的——如果第②步消息丢了、或第③步消费失败，就会出现"Redis 扣了、DB 没订单"的中间态，库存被永久占用。

**本项目实现：** 预扣成功后先写本地消息表（`tb_seckill_message`，status=PENDING），再投 MQ；定时对账任务扫描 PENDING 记录，反查订单，未落库则重投，重投耗尽则回滚 Redis 预扣。

**可背话术：** "跨系统之间没有事务，Redis 和 MySQL 之间的窗口期就是风险。我的解法是把'要发的消息'先落库，消息发没发成功都有据可查，再由对账兜底收敛。"

### Q2.1.2（中等）本地消息表（发件箱）为什么能解决跨系统一致？它和事务消息有什么区别？

**结论：** 本地消息表的本质是"把跨系统的分布式问题，收敛成单机本地事务 + 异步补偿"——业务数据 + 消息凭证在同一个本地库，用本地事务保证原子，投递交给对账兜底。

**原理：** 事务性发件箱（Outbox）的标准做法是"业务操作 + 写消息"在同一个 DB 事务里。本项目的变体：Redis 预扣（不是 DB 事务）→ 写消息表（DB 操作）→ 投 MQ。严格说不是标准 Outbox（因为预扣不在 DB 事务内），而是"本地消息表 + 定时对账"的最终一致方案。

**取舍：** 和 RocketMQ 事务消息、Seata 相比：事务消息强依赖 MQ 的能力，Seata 要引入分布式事务框架——单体 + 单库场景下本地消息表最轻量、最可控。

**可背话术：** "我这是单体 + 单库，用不上 Seata 那种跨库分布式事务框架。本地消息表把'发消息'变成'先落库、再对账'，成本最低、语义最清晰。"

### Q2.1.3（难）对账任务为什么"先反查订单是否落库，再决定补偿"？顺序反了会怎样？

**结论：** 顺序反了会**超卖**。必须先查订单，再决定是否回滚库存。

**原理：** 消息可能"实际已投递成功、只是 confirm 回执丢失"。如果对账时不管订单有没有落库，直接把 Redis 库存 +1 回补，而订单其实已经在 DB 里了，就会出现"库存加回 + 订单存在"= 多卖一件。

**本项目实现：** `SeckillMessageReconcileTask.handle()` 第一步 `voucherOrderService.getById(orderId) != null` → 说明消息已送达，直接 `markConfirmed`（不回滚）；只有订单确实不存在，才重投或补偿回滚。

**可背话术：** "补偿的方向必须是安全的。宁可少补库存、让用户再抢一次，也不能多补库存导致超卖。'先查订单再补偿'就是把这个安全方向固化下来。"

### Q2.1.4（中等）对账任务的重投和补偿分别怎么做？怎么保证幂等？

**结论：** 未落库且重投次数未超限 → 指数退避重投；重投耗尽 → 回滚 Redis 预扣（库存 +1 + 清限购位）+ 置 COMPENSATED。幂等靠消息表状态条件更新。

**原理：** 重投用 `convertAndSend` 带 `CorrelationData` 重发；退避间隔 `5s << retryCount`。补偿用 `restore_stock.lua`（仅活动未结束才 INCRBY，返回 -1 表示已结束跳过）+ `setBit` 清限购位。

**幂等点：** `markConfirmed`/`markCompensated` 都带 `WHERE status=PENDING` 条件更新，重复执行天然幂等；补偿回滚 Redis 是 INCRBY（幂等）+ setBit(0)（幂等）。

**可背话术：** "对账是定时反复跑的，所以每一步都要幂等——消息表状态用条件更新，Redis 回补用 INCRBY 这种天然幂等的操作。"

### Q2.1.5（中等）订单超时关单和库存回补怎么做的？为什么用延时队列？

**结论：** 下单后投递一条延时消息（TTL 15 分钟），到期关单消费者检查订单仍为未支付则关单 + 双端回补库存。

**原理：** 延时队列用 TTL + DLX 实现（消息 15 分钟过期变死信，路由到关单队列）。关单用 `UPDATE ... WHERE id=? AND status=1` 条件更新（CAS），只有订单仍"未支付"才关，和支付回调并发时谁先改成功谁生效，避免"已支付却关单回补"。

**取舍：** 所有延时消息 TTL 相同（15 分钟），所以不存在"队头消息 TTL 更长阻塞后续"的队头阻塞问题（这是 TTL+DLX 延时方案的主要缺陷，仅在 TTL 混用时出现）。

**可背话术：** "关单和支付是并发的，我用 status=1 条件更新做 CAS，影响 0 行就说明订单已经不是未支付了，自动跳过——这样不会误关已支付订单。"

### Q2.1.6（难）Redis 回补库存为什么用 Lua？直接 increment 不行吗？

**结论：** 直接 increment 会在活动已结束时凭空创建一个无 TTL 的 key。Lua 里先 EXISTS 判断，活动没结束才回补。

**原理：** 库存 key 在活动结束后会按过期策略回收。如果订单超时关单发生在活动结束后，直接 `increment` 会把 key 创建回来（值为 1），且没有 TTL，常驻内存。`restore_stock.lua` 先 `EXISTS`，不存在返回 -1（表示无需回补）。

**可背话术：** "回补要区分活动状态——活动进行中才需要把库存加回去让别的用户能买，活动结束了 Redis 库存已经回收，回补反而会凭空造 key。Lua 保证'判断 + 回补'原子。"

### Q2.1.7（深挖）这套方案还有没有残留的一致性问题？

**结论：** 有。补偿判定和"消费者真正落库"之间仍有极窄竞态——消息积压极久、补偿已执行后才被消费，理论上会"库存已回补 + 订单又被创建"。

**原理：** 对账判定"订单未落库 → 补偿"是某一时刻的快照判断，和消费者落库不是原子的。极端场景（消息积压超过对账重投窗口）下会重复。

**缓解：** ① 调大重投次数 + 退避上限，让补偿发生在消息几乎不可能仍存活之后；② 消费端落库前读一次消息状态（COMPENSATED 则跳过）；③ 离线对账兜底（比对订单表 vs 消息表）。

**可背话术：** "最终一致方案的代价就是有一致的窗口。我承认这个窗口存在，缓解手段是把窗口压到业务可接受范围——这是做一致性问题必须有的诚实。"

### Q2.1.8（深挖）对账任务本身挂了怎么办？消息表 PENDING 记录会丢吗？

**结论：** 对账任务挂了，PENDING 记录**不会丢**（已持久化在 MySQL），只是"收敛延迟"；对账重启后会扫描所有到期 PENDING 记录继续处理。

**原理：** 本地消息表是持久化的（`tb_seckill_message`），不是内存态。对账任务 `@Scheduled` 每轮扫描 `status=PENDING AND next_retry_time <= now`，即使任务挂了几分钟，重启后那些 PENDING 记录仍在，`next_retry_time` 早就到了，下一轮会全部捞出来处理。

**取舍：** 最终一致的兜底本身也有"兜底的兜底"——消息表就是它的兜底。对账挂了 = 收敛延迟 + 可能的 Redis 库存短期被占用，但不会数据丢失、不会超卖（Redis 预扣是安全的占用方向）。

**可背话术：** "对账是最终一致的执行者，但它的状态（消息表）是持久化的。对账挂了只是收敛慢了，重启后照常扫描处理——所以这套方案不会因为对账单点故障就丢数据。"

## 2.2 工作内容二：高并发交易的库存一致性（Lua + CAS + 幂等）

> 简历原文：针对高并发抢购下的库存透支与重复提交，采用 Redis Lua 脚本将库存校验、扣减与单人限购约束原子化，消除"读-判-写"竞态窗口；数据库层以乐观锁 CAS 兜底并发扣减正确性，唯一索引保证写入幂等，形成“Redis 原子操作 + DB 乐观锁”的双层保障。

### Q2.2.1（简单）"读-判-写"竞态窗口是什么？Lua 为什么能消除？

**结论：** 先查库存、再判断、再扣减，三段之间会被并发请求穿插，导致超卖。Lua 把三段放进同一个脚本，Redis 单线程顺序执行，原子。

**原理：** 如果不原子：两个请求同时 `GET stock=1`，都判断 >0，都扣减，最后 stock=-1，超卖 1 件。Lua 脚本内 `EXISTS → 判断 → INCRBY → SETBIT` 连续执行，Redis 单线程模型保证脚本执行期间不会被其他命令插入。

**本项目实现：** `seckill.lua` 单次 EVAL 完成：活动存在性 → 时间窗口 → 库存校验 → 限购校验 → 扣库存 → 置限购位 → 统一过期。

**可背话术：** "竞态的根源是'读和写之间有时间差'。Lua 不是锁，是把这个时间差压缩到 0——Redis 单线程跑完整个脚本，别人插不进来。"

### Q2.2.2（中等）为什么需要三级防线？Redis 一层不够吗？

**结论：** Redis 是前置拦截、是加速层，不是真相源。DB 的乐观锁 + 唯一索引才是最终防线，保证 Redis 挂了/被绕过也不产生脏数据。

**原理：** 三级防线各司其职——① Lua 原子预扣：扛住 99% 的并发，快速拦截；② 乐观锁 CAS（`UPDATE stock=stock-1 WHERE stock>0`）：Redis 不可信时的 DB 兜底；③ 唯一索引 `uk_user_voucher`：兜底"一人一单"，重复写入被唯一键拦下。

**取舍：** 为什么不用分布式锁？锁的粒度重、有死锁/超时风险、吞吐低。Lua + 乐观锁是无锁设计，并发更高。

**可背话术：** "我把 Redis 定位成'前置拦截'，不是'真相源'。真正的最终一致靠 DB——即使 Redis 层被绕过，乐观锁和唯一索引照样兜住。这就是为什么三层缺一不可。"

### Q2.2.3（中等）单人限购为什么用 Bitmap 而不是 Set？

**结论：** Set 的内存随参与人数线性增长（每人 ~50-70 字节），大促时退化成大 key；Bitmap 内存只取决于最大用户 ID（1 位/用户），且用户 ID 是自增的稠密值，正好是 Bitmap 的最佳场景。

**原理：** `GETBIT/SETBIT orderKey userId` 做限购标记，内存 = 最大 userId/8 字节，与参与人数无关。`SETBIT` 天然幂等，天然去重。

**取舍：** 若用户 ID 是雪花号（稀疏、范围大），Bitmap 反而浪费（高 offset 全是 0），那时应该用 Set。所以选型要看 ID 分布。

**可背话术：** "限购标记的内存不该跟着人数涨。Bitmap 按最大 ID 定内存，我的用户 ID 是自增的，稠密，正好用它。要是雪花号那种稀疏 ID，就该换回 Set——选型看数据分布。"

### Q2.2.4（中等）时间窗口校验为什么下沉到 Lua？原来在哪？

**结论：** 原来在 Java 侧查 DB 校验活动起止时间，每个秒杀请求都打一次 DB，和"减轻 DB 压力"的目标矛盾。下沉到 Lua 后，秒杀请求路径零 DB 查询。

**原理：** 活动创建时预热 `seckill:activity:{id}` Hash（begin/end 时间戳），Lua 里 `HGET` 判断时间窗口，`now < begin` 返回未开始、`now > end` 返回已结束。

**本项目实现：** `SeckillActivityCacheWarmer` 预热 + 启动补偿预热（覆盖未结束的活动，且只补不覆盖，避免重置实时库存）。

**可背话术：** "秒杀请求路径上不能有 DB 查询，否则高并发直接压垮数据库。我把时间窗口也放进 Redis，Lua 里一并校验，整个同步路径就是纯 Redis + MQ。"

### Q2.2.5（中等）唯一索引怎么实现幂等？DuplicateKeyException 怎么处理？

**结论：** `uk_user_voucher(user_id, voucher_id)` 唯一索引，重复插入抛 `DuplicateKeyException`，捕获后视为"已下单"幂等返回，不重复扣库存。

**原理：** 消费端落库先 insert 订单，命中唯一索引说明该用户该券已下单（重复消息/并发重复），直接返回；没命中才继续扣库存。

**本项目实现：** `createVoucherOrder()` 里 try/catch `DuplicateKeyException` → `markConfirmed` + return，保证重复投递不产生重复订单。

**可背话术：** "幂等的兜底是数据库唯一索引，不是应用层的 if 判断——因为 if 判断本身有并发竞态，唯一索引是数据库层面的硬约束。"

### Q2.2.6（难）为什么"先插订单、再扣库存"而不是反过来？

**结论：** 顺序配合唯一索引才能保证"一人一单"绝对正确。先插订单用唯一索引拦重复，再扣库存（WHERE stock>0），扣不动就回滚整个事务。

**原理：** 若"先扣库存、再插订单"：库存扣了、插订单时才发现重复，库存已经被白扣。反过来"先插订单（唯一索引幂等）→ 再扣库存（CAS）"，重复消息在第一步就被唯一索引拦下，不会动库存；扣库存失败抛异常，事务回滚连订单一起撤销。

**可背话术：** "顺序不是随意的，是和唯一索引、事务配合的——先插入用唯一索引做幂等闸门，再扣库存做最终防线，两步在同一事务里，失败整体回滚。"

### Q2.2.7（深挖）Redis 和 DB 的库存最终一致，有没有不一致的窗口？

**结论：** 有。Redis 预扣（秒级生效）和 DB 扣减（异步消费）之间，Redis 库存先减、DB 库存后减，窗口期内两边数字不一致。

**原理：** 这是"异步削峰"的必然代价——为了 350→130 的响应时间，牺牲了强一致。DB 是最终真相源，Redis 只是"快速拦截"的近似值。

**收敛手段：** 死信补偿回补 Redis、超时关单双端回补、对账任务兜底。最终 DB 库存是准的，Redis 在异常路径下靠补偿回到和 DB 一致。

**可背话术：** "异步化的代价就是一致性的窗口。我的态度是：Redis 允许短暂不准，但 DB 必须最终准；所有异常路径都有补偿把它拉回一致。"

### Q2.2.8（中等）库存预热怎么做的？启动补偿预热解决什么问题？

**结论：** 活动创建时把库存 + 时间窗口预热进 Redis；应用启动后做一次补偿预热，覆盖"未结束但 Redis 里丢了 key"的活动。

**原理：** 时间窗口下沉到 Lua 后，`seckill:activity:{id}` Hash 必须在 Redis 里存在，否则 Lua 返回"活动不存在"。两个场景会丢 key：① 应用重启、② Redis 被清空。启动补偿预热扫描 DB 里未结束的活动，Redis 没有就补写。

**取舍：** 补偿预热只做"不存在才写"，不覆盖已有 key——否则会把正在扣减的实时库存重置回初始值，导致超卖。

**可背话术：** "预热有两个时点：创建活动时写一次，启动时补偿一次。补偿的关键是'只补不覆盖'——活动 key 已经存在就跳过，否则会拿 DB 的初始库存覆盖掉 Redis 里正在被扣减的实时库存。"

## 2.3 工作内容三：异步解耦与消息可靠消费（MQ + 毒消息修复）

> 简历原文：针对流量洪峰下的消息丢失与消费积压，引入 RabbitMQ 将订单落库从同步链路解耦，核心接口响应时间由 350ms 降至 130ms；结合 Direct Exchange 精准路由、手动确认、死信队列与失败重试保障可靠投递，并修复消费端重试计数失效导致的消息循环重投（毒消息堆积）问题。

### Q2.3.0（简单）为什么用 RabbitMQ 而不是 Kafka / RocketMQ？

**结论：** 场景是"业务消息削峰 + 死信补偿"，RabbitMQ 简单可靠、生态成熟、延迟低、手动 ACK/死信/延时队列开箱即用，够用且最省心。

**原理：** Kafka 是"高吞吐日志流"，靠 offset 顺序消费，适合海量日志/事件流，但消息重试、死信、单条确认不如 RabbitMQ 灵活（Kafka 早期版本甚至没有单条 ACK，靠手动提交 offset）；RocketMQ 是国内电商常用，事务消息强，但要额外部署 NameServer。

**取舍：** 秒杀削峰的消息量不需要 Kafka 的吞吐天花板，却需要 RabbitMQ 的"手动 ACK + 死信 + TTL 延时"这些细粒度可靠性语义。选型看场景，不是看哪个名字响。

**可背话术：** "秒杀削峰是中小流量的业务消息，需要的是可靠性语义——手动 ACK、死信、延时关单，RabbitMQ 开箱即用。Kafka 的吞吐优势在这里用不上，反而重试和死信要自己搭。"

### Q2.3.1（简单）350→130 是怎么来的？瓶颈在哪？

**结论：** 同步下单每个请求直接写 DB，高并发下 MySQL 连接池满载，P99 350ms；把落库剥离到 MQ 异步后，接口只做 Redis 预扣 + 投递就返回，P99 130ms。

**原理：** 同步链路把"写库"这个最慢的操作放在请求线程里，连接池（默认 10）被打满，请求排队等连接。异步化后，写库移到消费者线程，接口线程不碰 DB，响应时间 = Redis 往返 + MQ 投递。

**可背话术：** "瓶颈是数据库连接池，不是 Redis 也不是 MQ。把写库从请求线程摘出去，响应时间自然降下来。JMeter 50 并发压测对比，350 到 130。"

### Q2.3.2（难）你修复的"毒消息"问题，根因是什么？怎么定位的？

**结论：** 根因是重试计数读 `x-death` 头，但 `basicNack(requeue=true)` 重新入队时 RabbitMQ **不会写 x-death**（只有 dead-letter 时才写），导致计数恒为 0，必然失败的消息无限重投，消费者被打满、死信队列形同虚设。

**原理：** `x-death` 是消息被投递到死信交换机时才写入的元数据。`requeue=true` 只是把消息放回原队列队尾，不产生 x-death。所以 `getRetryCount()` 永远返回 0，`attempt` 永远是 1，`< MAX_ATTEMPTS` 恒成立 → 无限 requeue 热循环。

**本项目实现：** 改用 Redis 计数器（`INCR seckill:retry:{orderId}` + TTL），重投次数真实累加，达到上限 `basicNack(requeue=false)` 转死信。

**可背话术：** "现象是死信队列一直收不到消息、消费者 CPU 打满。我定位到重试次数读的是 x-death，查文档发现 requeue 不写这个字段——计数一直是 0，就永远重试。改成 Redis 独立计数后闭环了。"

### Q2.3.3（中等）为什么按"业务拒绝 / 系统异常"分流？两者处理有什么区别？

**结论：** 业务拒绝（如库存已耗尽）重试多少次都不会成功，必须立即转死信；系统异常（DB 抖动）才值得有限重试。

**原理：** 消费端落库扣库存时，`UPDATE WHERE stock>0` 影响 0 行 → 抛 `SeckillRejectException`（业务拒绝），直接 `basicNack(requeue=false)` 转死信补偿。其他异常（连接超时等）走有限重试（3 次），耗尽再转死信。

**取舍：** 如果不分流，业务拒绝的消息也会占着重试配额，白白浪费消费者资源，且毒消息堆积。

**可背话术：** "重试的前提是'重试可能成功'。库存没了这种业务性失败，重试一百次也不会成功，反而把队列堵死。所以要分流——业务拒绝直转死信，系统异常才重试。"

### Q2.3.4（中等）死信队列的补偿逻辑是什么？补偿失败怎么办？

**结论：** 死信消费者反查订单是否落库：未落库 → 回补 Redis 库存 + 清限购位 + 收敛消息表为 COMPENSATED；已落库 → 跳过（说明是 ACK 丢失）。补偿失败也 ack，靠人工记录兜底。

**原理：** 死信消息不能无限重投（会无限循环），所以 `DlxOrderListener` 无论成功失败都 `basicAck`，把补偿结果写 Redis LIST 供人工重放。

**可背话术：** "死信是最后一道防线，它自己不能再失败重投，否则死信队列无限堆积。所以补偿失败也 ack，落一条人工补偿记录，靠人去兜底。"

### Q2.3.5（中等）发布确认（Publisher Confirm）和 Returns 回调解决什么？

**结论：** Confirm 解决"消息有没有到交换机"，Returns 解决"消息有没有被路由到队列"——两者补全了"发送失败无感知"的盲区。

**原理：** `publisher-confirm-type: correlated` + 注册 ConfirmCallback（交换机是否收到）；`publisher-returns: true` + 注册 ReturnsCallback（无队列绑定时退回）。失败落 Redis LIST 供审计。

**取舍：** Confirm nack 只说明 broker 未确认落盘，但"未送达"和"已送达但确认丢失"在回调时刻无法区分——所以回调只记录，不同步回滚，交由对账任务通过"反查订单"做确定性判定。

**可背话术：** "发布确认只是把'发送失败'变成'可感知'，它本身不保证可靠——真正的一致性还是靠本地消息表 + 对账。回调只做记录，不做回滚，因为回调时无法判断消息到底送没送达。"

### Q2.3.6（难）怎么保证消息不丢？从生产者到消费者完整讲一遍。

**结论：** 四段闭环——① 生产者：发布确认 + 消息持久化；② Broker：队列 durable；③ 消费者：手动 ACK（处理成功才确认）；④ 兜底：本地消息表对账 + 死信补偿。

**原理：** 消息丢失点有三个：生产者发丢（confirm 感知 + 本地消息表重投）、Broker 丢（队列/消息持久化）、消费者处理中丢（手动 ACK，处理成功才 ack，失败 nack 重试或死信）。

**可背话术：** "我按丢失点逐个堵：生产端用 confirm + 本地消息表重投，broker 用持久化队列，消费端手动 ack + 死信补偿。四段缺一段都会丢。"

### Q2.3.7（深挖）prefetch 设成 1 的意义？会不会影响吞吐？

**结论：** `prefetch=1` 保证公平分发——消费者每次只取一条，处理完才取下一条，避免某个消费者积压大量未 ack 消息导致处理能力不均。

**原理：** prefetch 是"预取未 ack 消息数"。设为 1 时，消息被均摊到各消费者；不设（默认较大）时，快消费者会取走大量消息，慢消费者闲置，且消息都堆在快消费者的未 ack 缓冲区。

**取舍：** prefetch=1 牺牲了单消费者吞吐（多了网络往返），但保证了公平性和故障恢复（未 ack 消息少，重启丢的少）。本项目单消费者场景下影响不大，多消费者扩展时是正确默认。

**可背话术：** "prefetch=1 是公平分发的关键——每个消费者一次只拿一条，处理完再拿，避免快的吃撑、慢的饿死。"

### Q2.3.8（深挖）消息消费积压了怎么办？怎么定位和解决？

**结论：** 先定位积压原因（消费慢 or 生产快 or 毒消息循环），再对症——慢则扩容消费者/优化消费逻辑，毒消息则修复重试逻辑。

**原理：** 积压三原因：① 消费者处理慢（DB 慢查询、落库瓶颈）→ 优化 SQL + 扩容消费者实例；② 生产速度 > 消费速度 → 削峰能力不足，加消费者；③ 毒消息无限重投 → 这是最隐蔽的，我的项目就踩过——必然失败的消息无限 requeue，消费者 CPU 打满但永远不 ack，队列深度飙升。

**监控：** 队列深度（`ready` 消息数）是核心告警指标，配上积压阈值告警，比事后查快得多。

**可背话术：** "积压先定位根因，别盲目加消费者——如果是毒消息循环，加多少消费者都会被一个毒消息打满。我的项目就靠监控队列深度 + 修复重试计数，从根上解决积压。"

## 2.4 工作内容四：全链路追踪与可观测性

> 简历原文：建设请求级全链路追踪，以 traceId 贯穿 Redis、MQ、数据库与模型调用，实现一次请求跨组件的日志串联与耗时定位；基于调用追踪做成本归因与容量评估，为限流阈值与降级策略提供量化依据；接入 Prometheus + Micrometer 输出核心指标，构建从采集到告警的监控链路。

### Q2.4.1（简单）traceId 怎么贯穿整个请求？跨线程/MQ 怎么传递？

**结论：** 请求最外层（`TraceIdFilter`）生成 traceId 放进 ThreadLocal 和 MDC；同线程靠 ThreadLocal 传递，跨线程/MQ 靠显式透传。

**原理：** `TraceIdFilter`（`@Order(HIGHEST_PRECEDENCE)`）在最外层生成 traceId → `MDC.put` + `TraceContext.bindTraceId`。日志 pattern 输出 `%X{traceId}`，一次请求所有日志带同一 ID。跨 MQ 时，traceId 需要随消息体或 header 透传到消费者线程。

**取舍：** 自研 ThreadLocal 方案 vs 开源（SkyWalking/OTel）。单体 + 同步调用为主时 ThreadLocal 够用，跨线程/MQ 需显式透传；分布式多服务时应该上 OTel。

**可背话术：** "我在最外层 filter 生成 traceId 进 MDC，日志里每个请求都能用同一个 ID 串起来。跨线程就显式传，跨 MQ 就塞进消息头。单体场景够用，分布式就该上 OpenTelemetry。"

### Q2.4.2（中等）TraceRecorder 批量落盘会不会丢 trace？怎么权衡？

**结论：** 会，但有界可控——内存 `ArrayBlockingQueue` 缓冲，满了就丢弃并计数，定时线程每 5 秒批量写 Redis。

**原理：** 不逐条写 Redis（高并发下 IO 开销大），用有界队列缓冲 + `@Scheduled` 批量 flush。缓冲满则丢弃并 `LongAdder` 计数，保证不阻塞主链路。

**取舍：** 牺牲了"极端高并发下部分 trace 丢失"，换来了"主链路零阻塞"。trace 是观测数据，丢一点可接受，业务不能因此变慢。

**可背话术：** "观测不能拖累业务。我用有界队列 + 批量落盘，满了就丢并计数，保证 trace 采集永不阻塞主链路——丢的 trace 有计数，知道丢了多少。"

### Q2.4.3（中等）成本归因怎么做？为什么能支撑"成本降 50%"？

**结论：** 按 spanName（意图/Agent/模型）聚合 token 和耗时，输出每个调用单元的成本分布，定位成本大头。

**原理：** `TraceRecorder.costAttribution()` 按 spanName 聚合 calls/inputTokens/outputTokens/totalMs/failures。`TokenCostTracker` 按 token 单价估算成本。哪个意图/哪个 Agent 烧钱最多，一眼可见。

**可背话术：** "成本不是拍脑袋降的，是归因出来的——trace 里每个 span 记录了 token 和耗时，聚合出成本分布，再针对性优化。比如发现某类意图反复调大模型，就给它配轻量模型。"

### Q2.4.4（中等）Trace / 日志 / Metrics 三者什么关系？

**结论：** Trace 看"一次请求的调用链"，日志看"某个时刻的详情"，Metrics 看"一段时间的趋势"。三者互补。

**原理：** Trace（traceId 串联 span）回答"这次请求慢在哪一步"；日志（MDC 带 traceId）回答"这一步当时发生了什么"；Metrics（Prometheus 计数器/直方图）回答"过去一小时 QPS/延迟/错误率趋势"。

**可背话术：** "三个维度：Trace 定位单次请求，日志还原现场，Metrics 看整体趋势。我用 traceId 把三者关联——先看 Metrics 发现异常，再查 Trace 定位到具体请求，最后看日志还原。"

### Q2.4.5（难）ThreadLocal 存 traceId 会不会内存泄漏？怎么防？

**结论：** 会，如果线程池复用线程且不清理。必须在 finally 里 remove。

**原理：** ThreadLocal 的 value 是强引用，线程池复用线程时，上一个请求的 traceId 残留在 ThreadLocal 里，会"串味"到下一个请求，且 value 无法被 GC（泄漏）。

**本项目实现：** `TraceIdFilter` 的 finally 里 `TraceContext.endTrace()`（清理 ThreadLocal）+ `MDC.remove()`，兜底 flush 未出栈的 span。

**可背话术：** "ThreadLocal 泄漏的根源是线程复用 + 不清理。我在 filter 的 finally 里强制 endTrace + MDC.remove，保证线程归还线程池前清干净，既防泄漏也防 traceId 串到下一个请求。"

### Q2.4.6（深挖）自研追踪和 SkyWalking/OpenTelemetry 比，为什么不直接用开源的？

**结论：** 单体场景 + 要深度定制成本归因，自研更轻量可控；分布式多服务就该换开源。

**原理：** 自研的优势：① 无 agent 依赖，理解成本低；② 成本归因（token 成本）是业务语义，开源 trace 不直接给；③ 面试能讲清原理。劣势：跨进程、跨服务传播弱，没有现成的可视化。

**可背话术：** "自研是为了把'token 成本归因'这种业务语义埋进 trace，开源方案给不了。但我知道它的边界——分布式多服务就该上 OpenTelemetry + Jaeger，我这个是单体的轻量方案。"

### Q2.4.7（中等）Prometheus + Micrometer 具体监控了哪些指标？告警怎么接？

**结论：** 业务侧监控 AI 的 Token 用量、限流触发次数、调用耗时；系统侧靠 Actuator 暴露 JVM、HTTP、连接池等基础指标。

**原理：** `TokenCostTracker` 用 Micrometer Counter 注册 `ai.token.input.total` / `ai.token.output.total` / `ai.token.rate.limit.hits` 三个指标；`management.endpoints` 暴露 `prometheus` / `metrics` / `health`。Prometheus 定时拉取，Grafana 或 Alertmanager 做可视化 + 告警。

**取舍：** 指标设计要"业务语义化"——不只是"CPU 多少"，而是"限流触发了几次、每个意图烧了多少 token"，这样告警才有业务含义。

**可背话术：** "我不只暴露 JVM 这种通用指标，还埋了 AI 业务指标——Token 用量、限流触发次数、按 span 的耗时。告警阈值比如'某意图 token 消耗突增'或'限流触发率超 5%'，都能直接配到 Alertmanager。"

## 2.5 工作内容五：AI 能力工程化与治理（Agent 编排 + 评测 + 治理）

> 简历原文：针对客服多意图场景，构建"路由 + 专业子智能体"编排架构，工具调用准确率由 72% 提升至 89%，自建 LLM-as-Judge 评测闭环，实现准确率的自动化回归验证；将大模型作为不可靠外部依赖治理，通过多模型路由、故障降级、分级限流与语义缓存，整体调用成本降低 50%。

### Q2.5.1（简单）为什么用"路由 + 专业子智能体"而不是单一大 Agent？

**结论：** 单 Agent 把几十个工具塞一起，工具冲突和 Prompt 膨胀让准确率崩；拆成专业子 Agent，每个只挂自己领域的工具，选择范围缩小，准确率上来。

**原理：** 工具太多时 LLM 在语义相近工具间选错；所有工具描述挤在一个 Prompt，Token 浪费且理解下降。拆成 RouterAgent 意图识别 + ShopAgent/OrderAgent/ReviewAgent 各管一域，工具从 27 个降到 5-8 个，选择空间收窄后选对率自然上升——这正是 72%→89% 的核心机制（工具分化）。

**可背话术：** "单 Agent 的本质是把选择难度全甩给 LLM，多 Agent 的本质是缩小选择范围。工具从 27 个降到 5-8 个，LLM 在语义相近工具间选错的概率大幅下降，工具调用准确率从 72% 提到 89%；代价是多一次路由调用，我用规则引擎挡掉 30% 不需要 LLM 的请求来对冲。"

### Q2.5.2（中等）工具调用准确率 72%→89% 是怎么测的？怎么证明？

**结论：** 自建评测系统——标注测试集 + LLM-as-Judge 按 rubric 打分，跑批输出准确率，改 prompt 后可回归对比。

**原理：** `AgentEvalService` 维护标注测试集（真实 query + 期望意图），`RouterAgent.classify` 跑批，LLM-as-Judge 按 rubric 判定预测意图与期望是否一致，聚合出准确率。评测锚定"意图识别"这第一道关——意图是工具调用的前置，意图错了后面选工具必错，所以意图准确率是工具调用准确率的瓶颈指标；而 72→89 的提升来自工具分化（单 Agent 27 工具 → 多 Agent 各 5-8 工具），选择空间收窄后选对率上升。

**可背话术：** "准确率提升的核心是工具分化：原来一个 Agent 挂 27 个工具，LLM 在语义相近的工具间容易选错；拆成路由 + 专业子智能体、每个只挂 5-8 个自己领域的工具，选择空间大幅收窄，工具调用准确率从 72% 提到 89%。评测用标注测试集 + LLM-as-Judge，锚定意图识别这个第一道关——意图错了工具必错——跑批可回归。"

### Q2.5.3（中等）LLM-as-Judge 有什么偏差？你怎么缓解？

**结论：** 位置偏差、偏好偏差、自我增强偏差、一致性差。缓解靠多轮取均值、固定 rubric、锚点对照。

**原理：** LLM 当裁判的常见问题：偏好长答案、偏好自己生成的风格、对选项顺序敏感、同一条多次打分不一致。缓解：固定结构化 rubric（输出 JSON score + reason）、多次打分取均值、用锚点样例校准。

**可背话术：** "LLM 当裁判不是万能的，它有自己的偏好。我用结构化 rubric 约束输出、多轮取均值、锚点对照，把裁判的随机性压到最低。评测的价值是'相对比较'（优化前 vs 优化后），不是绝对分。"

### Q2.5.4（中等）多模型路由和故障降级怎么做？

**结论：** 轮询负载均衡 + 失败自动切换备用模型 + 按用途选模型（意图识别用轻量模型，对话用主模型）。

**原理：** `ModelRouter.generateWithFallback`：轮询尝试，失败 catch 后切下一个，全失败抛异常。`getLightweightModel` 为简单任务返回轻量模型。降级次数记进 trace。

**可背话术：** "把大模型当成不可靠的外部依赖——它可能超时、限流、宕机。我的做法是轮询 + 失败自动切换 + 按场景选模型，把单点故障变成可降级。"

### Q2.5.5（中等）语义缓存和普通 KV 缓存区别？怎么保证一致性？

**结论：** KV 缓存靠 key 精确匹配，同义改写就 miss；语义缓存靠向量相似度，同义改写也能命中。一致性靠数据变更时按域失效。

**原理：** `SemanticCache` 把 userMessage 做 embedding，与缓存条目算余弦相似度，> 阈值（0.92）且同 shopId 域则命中。数据变更（评价/商品更新）时按 shopId 失效缓存。

**可背话术：** "普通缓存'附近有啥好吃的'和'推荐附近美食'是两次 miss，语义缓存向量相似度 0.95 直接命中，跳过整条 LLM 链路。一致性的关键是按 shopId 域失效，避免跨店串数据。"

### Q2.5.6（难）成本降 50% 具体由哪些策略构成？

**结论：** 三部分——① 规则引擎把确定性请求拦在 LLM 之外（约三成零 Token）；② 语义缓存命中跳过 LLM；③ 轻量模型处理简单意图。

**原理：** 简单规则查询（如"订单状态"）走 `AiBusinessRouter` 规则引擎，不调 LLM；高频相似问题走语义缓存；意图识别用轻量模型而非大模型。三者叠加压成本。

**可背话术：** "成本 50% 是三块拼出来的：规则引擎挡掉确定性请求、语义缓存挡掉重复请求、轻量模型处理简单请求。核心思路是'让最便宜的方式处理最多的请求'。"

### Q2.5.7（深挖）这个 AI 客服最大的工程挑战是什么？你怎么看的？

**结论：** 最大挑战不是模型效果，是"不可靠性治理"——LLM 会幻觉、会超时、会超预算，要把不可靠的调用变成可靠的服务。

**原理：** 效果（准确率）只是 AI 应用的一半，另一半是稳定性、成本、可观测。这套项目完整覆盖了：评测（证明效果好）、限流降级（防超预算/故障）、缓存（降成本）、追踪（可定位）。

**可背话术：** "做 AI 客服，难点不在调 API，在把不可靠的 LLM 变成可靠的服务——效果要能评测、故障要能降级、成本要能归因、问题要能定位。这四件事做齐了，才敢上线。"

### Q2.5.8（深挖）Agent 编排的降级链路是什么？意图识别失败怎么办？

**结论：** 三级降级——① 意图识别失败回退通用助手（CustomerAssistant，全量工具 + RAG 兜底）；② 专业 Agent 调用失败回退通用助手；③ 主模型失败 ModelRouter 切换备用模型；④ 所有模型失败返回"服务繁忙"。

**原理：** 多 Agent 编排的代价是"路由错了会错上加错"。所以意图识别一旦置信度低或失败，不硬路由，而是回退到全量工具的通用助手，让它自己判断。模型层再叠加 ModelRouter 的故障切换，形成"业务降级 + 模型降级"双层。

**取舍：** 降级链路的本质是"宁可回答得泛一点，也不回答错"——通用助手没有领域特化的 SystemMessage，效果略差，但不会把订单问题路由到评价 Agent 去。

**可背话术：** "多 Agent 的风险是路由错上加错，所以必须有降级。意图识别失败就回退通用助手，模型挂了就切备用模型，全挂就明确返回'服务繁忙'——每层都有兜底，不让用户卡死。"

### Q2.5.9（简单）RAG 混合检索（PgVector+RRF）和工具调用是什么关系？别混为一谈

**结论：** 两者是 AI 客服的两条独立通路——RAG 补"知识"（检索本地内容喂给 LLM 生成回答），工具调用做"动作"（查订单、抢券、查评价），一个解决"模型不知道"，一个解决"模型不会做"。

**原理：** PgVector 混合检索（向量 + PG 全文检索 + RRF 融合）属于 RAG：把店铺/评价知识切片向量化，问题来了先检索相关内容再生成，解决 LLM 没有的本地知识。工具调用是 LangChain4j 的 `@Tool`：LLM 决定调用 `queryOrder` / `seckillVoucher` 等真实方法执行副作用。两者在编排里串联——意图路由到专业 Agent 后，该 Agent 既挂自己领域的工具，又可能接 RAG 补充知识。

**可背话术：** "RAG 和工具调用是两件事，我不会混着讲：RAG 解决模型不知道本地店铺信息，混合检索（向量+全文+RRF）提升的是检索命中率；工具调用解决模型要真的去改数据，工具分化提升的是工具调用准确率。简历里的 72→89 是工具调用准确率，来自多 Agent 拆分，不是 RAG 检索。"

## 2.1（旧版归档）多 Agent 协作架构与评测闭环

> 简历原文：构建多 Agent 协作架构与评测闭环——RouterAgent + 专业Agent编排，LLM零样本意图识别，工具调用准确率 72%→89%；自建 AgentEval 评测系统（LLM-as-Judge + 标注测试集），实现准确率自动化回归验证与可复现追踪。

### Q2.1.1（简单）为什么用多 Agent 架构，单一 Agent 不行吗？

**结论：** 单 Agent 把 27 个工具塞在一起，工具冲突率和 Prompt 膨胀都会让准确率崩到 72%，多 Agent 靠"职责隔离"解决。

**原理 / Why：**
- 工具冲突：工具超过 10 个，LLM 容易在语义相近的工具间选错（问"评价"却调了店铺查询工具）。
- Prompt 膨胀：所有工具描述挤在一个 SystemMessage，Token 消耗大，LLM 理解下降（工具描述约占 40% Token）。
- 职责不清：无法针对场景优化 SystemMessage。

**本项目实现：** `RouterAgent`（`AiServices` 接口）做零样本意图分类，`AgentOrchestrator.process()` 路由到 `ShopAgent`（8 工具）/ `OrderAgent`（5 工具）/ `ReviewAgent`（5 工具），兜底 `CustomerAssistant`（全量工具 + RAG）。每个专业 Agent 在 `AiConfig` 里用 `.tools(...)` 只挂自己领域的工具。

**取舍 / 坑：** 多 Agent 不是越多越好——每个 Agent 一次 LLM 调用，路由本身有延迟和成本；而且意图分错会"错上加错"。所以加了降级：意图识别失败一律回退 `GENERAL` 走通用助手。

**可背话术：** "单 Agent 的问题本质是'把选择难度交给 LLM'，多 Agent 的本质是'把选择范围缩小'。工具从 27 个降到 5-8 个，准确率自然上来；代价是多一次路由调用，我用规则引擎挡掉了 30% 不需要 LLM 的请求来对冲。"

### Q2.1.2（简单）意图识别怎么实现？为什么用 LLM 而不是传统 NLU（Rasa/Dialogflow）？

**结论：** 用 `RouterAgent` 接口 + SystemMessage 定义 5 类意图，LLM 输出 `INTENT:分类名`；选 LLM 是因为零样本、语义理解强、可扩展、复用现有模型零成本。

**本项目实现：** `RouterAgent` 是个纯接口，`@SystemMessage` 里写分类规则（5 类意图 + 输出格式），`@UserMessage` 接输入，LangChain4j 的 `AiServices.builder(RouterAgent.class)` 自动生成实现。输出解析在 `AgentOrchestrator.classifyIntent()`：容错匹配 `INTENT:xxx` / `intent=xxx` / 裸枚举名，解析失败降级 `GENERAL`。

**取舍 / 坑：** LLM 意图识别不稳定，可能输出格式漂移，所以代码里做了多模式解析；延迟 200-500ms，高并发下是瓶颈，可加缓存层（本项目 `SemanticCache` 顺带兜住了高频相似问题）。

**可背话术：** "传统 NLU 要标注训练数据、要部署服务，加一个新意图要重新训练；LLM 零样本只要改 SystemMessage。我选择 LLM 是拿一点点延迟和成本换'无限扩展性'。"

### Q2.1.3（中等）AgentOrchestrator 的完整编排流程讲一遍（8 步）

**结论：** 一条流水线：**业务路由 → Token 限流 → 意图识别 → 语义缓存 → 敏感确认 → 路由 Agent → 缓存回写 → 可信存证**，全程在一个 Trace 内，finally 兜底清理线程变量。

**本项目实现（`AgentOrchestrator.process()`）：**
1. `businessRouter.decide(userMessage)`：规则引擎 or Agent；规则引擎直接返回，零 Token。
2. `tokenCostTracker.checkRateLimit(userId)`：超限返回"请求过于频繁"；限流组件异常时**降级放行**避免误伤。
3. `classifyIntent()` → `routerAgent.classify()`：意图识别，失败降级 `GENERAL`。
4. `semanticCache.get(userMessage)`：只缓存只读意图 + 非个人化问题；命中直接返回，零 LLM。
5. 敏感确认：`decision.needConfirm() && intent==ORDER_ACTION` → 返回"请确认是否继续"。
6. `routeToAgent()`：switch 分发到 ShopAgent/OrderAgent/ReviewAgent/MultiAgent/GeneralAssistant。
7. 未命中缓存则 `semanticCache.put()` 回写。
8. `notaryService.notarize("AGENT_DECISION", {traceId,userId,intent,handler,input,output})` 上链。
- 每步都 `TraceContext.begin/end` 包 Span，`finally { TraceContext.endTrace(); }`。

**取舍 / 坑：** 所有可降级点都做了 try-catch 降级：限流故障放行、缓存异常当 miss、存证失败不影响主流程——**主链路永远是"尽力而为"**。

**可背话术：** "这是一条 8 步流水线，核心设计原则是'每一步失败都不拖垮主流程'：能降级就降级，能兜底就兜底，最后还有存证保证可审计。"

### Q2.1.4（中等）工具调用准确率 72%→89% 是怎么优化出来的？

**结论：** 四个手段叠加：多 Agent 缩小工具选择范围、工具描述优化、@P 参数注解明确语义、工具方法内部参数校验。

**本项目实现：**
- 拆分前：`CustomerAssistant` + `DianpingTools` 等 27 个工具全量注册 → 准确率约 72%。
- 拆分后：ShopAgent 8 工具、OrderAgent 5、ReviewAgent 5，每个 Agent 只面对自己领域。
- 每个 `@Tool` 描述具体（如 `@Tool("根据商铺ID查询商铺详细信息，包括名称、地址、评分、人均消费、营业时间等")`），`@P` 明确参数含义与格式（如 `@P("最低评分(1-50)，可选，例如40表示4.0分")`）。
- 工具方法内做参数校验，不合法返回错误提示而非抛异常（如 `compareShops` 对无效 ID 跳过）。

**取舍 / 坑：** 准确率数字来源见第八部分——是用 AgentEval 标注测试集 `runIntentEval()` 回归出来的，不是拍脑袋。

**可背话术：** "本质是降低 LLM 的选择熵：工具变少、描述变清、参数变明、失败有兜底，四件事把准确率从 72% 推到 89%。而且这个数字不是猜的，我有一键回归的评测系统。"

### Q2.1.5（中等）AgentEval 评测系统怎么工作的？怎么证明 89%？

**结论：** 标注测试集 + 确定性比对算意图准确率，LLM-as-Judge 四维打分算回答质量；`POST /ai/eval/intent` 一键回归。

**本项目实现：**
- `AgentEvalService.SEED_CASES`：8 条标注用例，覆盖 5 类意图 + 边界 case（"帮我写一首诗"→GENERAL）。
- `runIntentEval()`：每条 query 喂 `RouterAgent.classify()`，预测 vs 期望比对，输出 `intentAccuracy` + `avgLatencyMs`。
- `runQualityEval()`：调完整 `CustomerAssistant` 链路生成回答，再由 `judge()`（独立 LLM 裁判）按 相关性/准确性/完整性/安全性 四维 0-5 打分，聚合 `qualityScore`；还做关键词粗校验。
- `runRagEval()`：`RAG_SEED_CASES` 10 条真实店铺问题，统计纯向量 Top-1 命中率（基线 ≈77%）vs 混合检索 Top-5 命中率（优化 ≈89%）。
- 报告持久化 Redis（`ai:eval:reports`，保留 50 条）+ 上链存证（`EVAL_REPORT`）。
- 接口：`POST /ai/eval/intent`、`POST /ai/eval/quality`、`POST /ai/eval/rag`、`GET /ai/eval/reports`、`GET /ai/eval/latest`。

**取舍 / 坑：** 意图测试集只有 8 条、RAG 10 条是小规模种子集，扩展方向是按意图分层扩充到几百条、与 CI 联动每次发版自动回归。

**可背话术：** "我维护了一个标注测试集，改 Prompt 后跑 `POST /ai/eval/intent` 一键回归，准确率从 89% 掉到 85% 立刻暴露。评测报告本身也上链，数字不可被偷偷改。这就是'可复现追踪'。"

### Q2.1.6（难）LLM-as-Judge 有哪些偏差？你怎么缓解？

**结论：** 三大偏差：长度偏差、自我偏好、位置偏差；缓解手段是"客观指标确定性比对 + 主观指标 rubric 打分 + 结构化输出约束"。

**原理：**
- 长度偏差：裁判偏爱长回答 → 评分与长度强相关。
- 自我偏好：裁判偏向与自己同族系的模型输出。
- 位置偏差：对比任务中偏向第一个选项。

**本项目实现：** 意图准确率这种**客观正确**用字符串比对，不依赖 LLM；质量分才用 LLM 裁判，且用 4 维 rubric + 要求只输出 JSON + 正则提取分数，降低格式漂移；关键词粗校验兜底；报告历史可回放对比基线。

**取舍 / 坑：** LLM-as-Judge 不是银弹。生产可加：随机打乱顺序、多裁判投票、确定性断言兜底。面试主动讲偏差比等面试官问更加分。

**可背话术：** "我把'客观题'和'主观题'分开：准确率用确定性比对，天然无偏差；回答质量才用 LLM 裁判，但用 rubric + 结构化输出 + 关键词兜底来约束。另外评测报告上链，防止评测结果被篡改。"

### Q2.1.7（难）MULTI_AGENT 意图的协作是怎么实现的？

**结论：** `AgentOrchestrator.handleMultiAgent()` 按关键词确定性分解子任务，顺序调用多个专业 Agent，再拼接成完整答复。

**本项目实现：** 命中 MULTI_AGENT 时，`mentionsShop()`（含"店/推荐/附近/对比"）、`mentionsOrder()`（含"券/单/秒杀/抢购/买"）、`mentionsReview()`（含"评价/评论/口碑/怎么样"）分别判定，把子任务交给对应 Agent 顺序执行，结果按【店铺推荐】【订单/优惠券】【评价分析】拼接。全部不命中则回退通用助手。

**取舍 / 坑：** 这是"确定性任务分解"而非 Agent 间自主通信，优点是简单可靠、可观测，缺点是子任务不能并行、不能根据前序结果动态决策。改进方向是引入 Agent 间消息传递或让 LLM 生成任务 DAG。

**可背话术：** "我做了确定性分解的轻量版多 Agent 流水线，让每个子任务走最擅长的专业 Agent，各自带独立工具集和记忆。没上复杂通信协议，是怕不可控——确定性分解虽然'笨'，但可观测、可评测。"

### Q2.1.8（深挖）意图识别准确率怎么提高？除了加样本还有什么办法？

**结论：** 从 Prompt 工程 + 边界判定 + 评测反馈三路入手。

**思路：**
1. Prompt 工程：给每类意图加更精确的判定词 + few-shot 示例（当前 `RouterAgent` 只有规则描述，可加示例）。
2. 规则前置：`AiBusinessRouter` 已在意图识别前挡掉 30% 确定性问题，降低路由层压力。
3. 评测反馈：`runIntentEval()` 出的混淆矩阵能告诉我哪两类意图最容易互相误判（如 REVIEW 误判 SHOP），针对性修 Prompt。
4. 分层模型：`ModelRouter.getLightweightModel()` 预留了小模型做意图识别，简单任务用便宜模型。

**可背话术：** "我会用混淆矩阵驱动优化：先看哪两类意图互相打架，再对症改 Prompt；必要时加 few-shot。改完跑一遍 `POST /ai/eval/intent` 看数字有没有回来。"

## 2.2（旧版归档）工作内容二：Advanced RAG

> 简历原文：实现 Advanced RAG——针对 Redis 向量库跨店铺串扰问题（串扰率 15%），迁移至 PgVector，向量+全文混合检索，RRF融合 + LLM Reranker 精排，检索命中率 77%→89%；智能分块（500字/chunk）+ 批量向量化 + 事件驱动增量同步。

### Q2.2.1（简单）为什么从 Redis 向量库迁到 PgVector？

**结论：** RedisEmbeddingStore 在 LangChain4j 0.35 不支持 metadata 过滤，无法按 shopId 隔离，导致查"海底捞的评价"可能返回"麦当劳"的结果，串扰率 15%。

**本项目实现：** `PgVectorConfig` 里用 `PgVectorEmbeddingStore.builder()` 配 HNSW 索引（`useIndex(true)`、`indexListSize(100)`），完整支持 `IsEqualTo("shopId", ...)` 过滤 + PostgreSQL 原生全文检索 + ACID 事务。

**取舍 / 坑：** 迁移成本是引入第二个数据源 `pgDataSource`，导致 MySQL 主库必须显式声明并标 `@Primary`（否则 Spring Boot DataSource 自动配置退让后 MyBatis-Plus 找不到主库）——这是 `PgVectorConfig` 里同时定义 `dataSource()` 和 `pgDataSource()` 的原因，是个容易踩的坑。

**可背话术：** "迁移的本质是'从不能过滤到能过滤'。Redis 当时连 metadata filter 都支持不了，数据隔离只能靠检索后的二次过滤，效果差。PgVector 让我把 shopId 过滤下沉到存储层，物理隔离。"

### Q2.2.2（简单）混合检索 + RRF + LLM Reranker 各解决什么问题？

**结论：** 向量抓语义、全文抓关键词、RRF 公平融合两路排名、LLM Reranker 精排质量。

**本项目实现：**
- 向量检索：`HybridContentRetriever` 里 `EmbeddingStoreContentRetriever` 取 Top-20、minScore 0.3。
- 全文检索：`fullTextSearch()` 用 `pgJdbcTemplate` 直连 PG，`to_tsvector('simple', text) @@ to_tsquery('simple', ?)`，词间用 `|` OR 连接、每个词加 `:*` 前缀匹配。
- RRF：`reciprocalRankFusion()`，`score = Σ 1/(k + rank)`，k=60，去重（内容前 200 字符作指纹），Top-10。
- 精排：`RerankedContentRetriever` 装饰 `ShopAwareContentRetriever`，再调 `LlmReranker.rerank()`（0-10 分，Top-5）。

**可背话术：** "纯向量对'海底捞'这种精确词不敏感，纯全文对'好吃的火锅 vs 美味的涮肉'这种语义无能为力。RRF 不用归一化分数，只看排名，两路都靠前的自然胜出；最后 LLM 再按相关性挑一遍，命中率 77%→89%。"

### Q2.2.3（中等）RRF 的 k=60 为什么这么选？k 变小会怎样？

**结论：** k=60 是学术论文（Cormack et al., 2009）推荐值；k 越小排名越激进（拉开分差），k 越大越平滑。

**原理：** `score = 1/(k+rank)`。k=10：第 1 名 1/11≈0.091，第 10 名 1/20=0.05，差距 1.8 倍；k=60：第 1 名 1/61≈0.016，第 10 名 1/70≈0.014，差距仅 1.14 倍。k 大让两路结果更公平融合，避免某一路"第一名"独裁。

**本项目实现：** `HybridContentRetriever.RRF_K = 60`，`reciprocalRankFusion()` 里 `1.0 / (RRF_K + i + 1)`。

**可背话术：** "我用了论文推荐值 60。如果 k 调小，排名靠前的结果分差拉大，会偏向其中一路的 Top；k 调大则两路更公平。当前数据量下 60 是稳的选择，真要调我会用评测集做 grid search。"

### Q2.2.4（中等）ShopAwareContentRetriever 怎么做到店铺感知过滤？

**结论：** 从查询里解析店铺 ID 或店铺名，动态构造 `IsEqualTo("shopId", ...)` filter，检索时就限定店铺子集。

**本项目实现：**
- `extractShopId()`：正则匹配 "店铺123"、"shopId:123"、"ID:123" 等。
- `extractShopName()`：匹配「」、《》、引号内容、"关于XXX的/评价"。
- `findShopByName()`：MyBatis-Plus `lambdaQuery().like(Shop::getName, shopName).last("LIMIT 1")` 模糊查，失败再精确查。
- 命中则 `hybridRetriever.retrieveWithFilter(query, new IsEqualTo("shopId", String.valueOf(id)))`，否则全局检索。
- `HybridContentRetriever.retrieveWithFilter()` 对全文检索也加过滤：`metadata->>? = ?` 参数化查询防注入。

**取舍 / 坑：** 店铺名解析靠正则，覆盖不了所有口语表达；`extractShopName` 匹配不到的查询会退化为全局检索。这是"启发式 + 兜底"的务实取舍。

**可背话术：** "我在检索入口先做'实体解析'，识别出是哪个店铺就加 filter，把检索范围从全库缩到一个店铺的子集。物理隔离比'检索后再过滤'更可靠。"

### Q2.2.5（中等）LLM Reranker 和 Cross-Encoder 比有什么优劣势？

**结论：** 省部署、语义强、可处理多跳；代价是延迟高（一次额外 LLM 调用）和 Token 成本。

**本项目实现：** `LlmReranker.rerank()`：构造评分 Prompt（文档截断 300 字），走 `modelRouter.generateWithFallback()` 调用 LLM 评分，正则解析 JSON（`"index":n,"score":m`），按分排序取 Top-5；异常降级返回原始顺序 Top-K。TopK 默认 5（`LlmReranker(modelRouter, 5)`）。

**取舍 / 坑：** 延迟 200-500ms、有成本，所以只在候选数超过 TopK 时才触发精排；`contents.size() <= topK` 直接返回。JSON 解析用正则而非引入 JSON 库，格式漂移是隐患（可改进：用结构化输出约束）。

**可背话术：** "我用 LLM 当 reranker 是'用一次调用换一个不需要部署的跨编码器'。为了控成本，只有候选超过 Top-5 才精排，而且异常自动降级回原始顺序，绝不让精排拖垮主链路。"

### Q2.2.6（中等）智能分块怎么设计？为什么 500 字/块 + 50 字重叠？

**结论：** 中文语义完整性 + 上下文连续性 + embedding 对齐三者的平衡。

**本项目实现：** `DocumentChunkingService` 用 `DocumentSplitters.recursive(500, 50)` 递归分割（段落→句子→词语→字符）；短文本（<100 字）不分块；每个 chunk 前面加上下文前缀（`【店铺名】标题`），metadata 附 `shopId/type/blogId/chunkIndex/totalChunks`。

**取舍 / 坑：** 块太小丢语义，块太大 embedding 被稀释；重叠保证相邻块上下文连贯、关键信息不切断。中文没有天然空格分词，递归分割对中文是"按字符兜底"。

**可背话术：** "500 字约 2-3 个段落，embedding 语义完整；50 字重叠保证跨块信息不丢。分块是超参数，真上线会用评测集扫一遍块大小。"

### Q2.2.7（难）事件驱动增量同步怎么保证一致性？失败了怎么办？

**结论：** 最终一致性：事件驱动 + 先删后插 + 定时全量兜底；失败靠日志告警 + 全量重建修复。

**本项目实现：**
- `RagSyncListener` 监听 `BlogCreatedEvent`（`BlogServiceImpl` 发布）、`BlogDeletedEvent`（`BlogServiceImpl` 发布）、`ShopUpdatedEvent`（`ShopServiceImpl` 发布），`@EventListener + @Async` 异步处理不阻塞事务。诚实点：**代码里没有 `BlogUpdatedEvent` 的发布点**（Blog 变更走"删+增"），`RagSyncListener.onBlogUpdated` 是预留方法。
- 更新策略（真实生效在 `RagSyncListener`）：先 `embeddingStore.removeAll(IsEqualTo)`（按 blogId/shopId）删旧向量，再 `embedAndStore()` 插新向量。
- 兜底：`RagIngestionService.ingestAll() / ingestIncremental()` 全量/增量重建，`POST /ai/ingest` 手动触发。诚实点：`ingestIncremental` 的 `deleteVectorsByShopId/BlogId` 目前是 no-op（只打日志不真删），增量重建靠主键去重覆盖；严格"先删后插"只在事件监听路径生效。

**取舍 / 坑：** 当前同步失败只有日志、没有重试队列，是改进点（可加 @Retryable 或死信队列）；事件是进程内的，多实例部署需注意每个实例都会消费（幂等设计可缓解）。这是 RAG 场景能接受的"最终一致"（秒级延迟）。

**可背话术：** "知识库一致性我定位成最终一致：变更事件触发增量同步，先删后插，最坏情况靠定时全量重建兜底。RAG 是读多写少，秒级延迟完全可接受，没必要为强一致引入分布式事务的复杂度。"

### Q2.2.8（难）全文检索用 simple 配置不支持中文分词，检索质量怎么保证？

**结论：** simple 按空格/标点切分，中文会被切得很碎，靠四招弥补：前缀匹配、OR 连接提召回、向量检索补语义、RRF 融合兜底。

**本项目实现（`HybridContentRetriever.buildTsQuery`）：** 清理特殊字符后，每个词加 `:*` 前缀匹配，多词用 ` | ` OR 连接（`collect(Collectors.joining(" | "))`）。语义理解靠向量，全文只做精确词补充。

**取舍 / 坑：** 这是明显可改进点：装 `pg_jieba` / `zhparser` 扩展做真正中文分词。面试时主动讲这个"已知短板 + 改进方案"反而加分。

**可背话术：** "中文没有空格，simple 配置会把词切碎，所以我用前缀匹配 + OR 连接提高召回，语义部分交给向量检索，最后 RRF 把两路融合。真要量产我会装 zhparser 或 pg_jieba。"

### Q2.2.9（深挖）混合检索失败时的降级链路是什么？

**结论：** 每层都有降级：混合检索异常→纯向量；全文检索异常→纯向量；LLM 精排异常→原始顺序；整体检索失败→无 RAG 只靠工具。

**本项目实现：**
- `HybridContentRetriever.retrieve()` 整体 try-catch，异常时 `vectorRetriever.retrieve(query)` 兜底。
- `fullTextSearch()` 异常返回空列表（不抛），`reciprocalRankFusion` 只按向量结果排。
- `LlmReranker.rerank()` 异常返回 `contents.stream().limit(topK)`。
- `AgentOrchestrator` 里所有外部依赖（限流/缓存/存证）失败都降级。

**可背话术：** "我的原则是'检索可以不准，但不能挂'。每一层失败都退到下一层，最后 LLM 还能靠工具兜底——这就是生产系统该有的韧性。"

## 2.3（旧版归档）工作内容三：AI 工程化闭环

> 简历原文：AI工程化闭环——ModelRouter 多模型负载均衡与故障自动降级；Token额度限流体系，区分简单规则查询与复杂Agent对话场景，AI调用成本降低50%；AgentTrace 全链路追踪（Span树 + token成本归因）；SemanticCache 语义缓存（同义改写也能命中），命中请求延迟降至毫秒级。

### Q2.3.1（简单）ModelRouter 怎么做多模型负载均衡和故障切换？

**结论：** 维护模型列表 + AtomicInteger 轮询索引，`generateWithFallback()` 从当前索引开始逐个尝试，成功更新索引，全失败抛异常由上层降级。

**本项目实现（`ModelRouter`）：**
- 注入 `List<ChatLanguageModel> chatModels` 和 `List<StreamingChatLanguageModel>`，`AtomicInteger chatModelIndex` 轮询。
- `getChatModel()`：`chatModels.get(chatModelIndex.get() % size)` 轮询负载均衡。
- `generateWithFallback()`：`for i in 0..size`，`index = (chatModelIndex.get() + i) % size`，成功则 `chatModelIndex.set(index)` 并返回，失败记录 `lastException` 继续下一个；全失败 `throw new RuntimeException("所有 ChatModel 调用失败", lastException)`。
- 所有 Agent 的 LLM 都经过 `TracingChatLanguageModel`（`AiConfig.routedChatModel()`）包装，统一走 ModelRouter + Token 记录 + Trace。

**可背话术：** "轮询 + 失败切换 + 索引记忆：成功一次就把索引记住，下次从它开始，避免每次都从已故障的模型试起。全挂了就抛异常，由上层降级到规则引擎。"

### Q2.3.2（中等）Token 限流体系怎么设计？为什么区分简单规则查询和 Agent 对话？

**结论：** 用户级每分钟 10000 Token + 全局每日 1000 万 Token；区分场景是因为"签到/余额"等确定性问题根本不需要 LLM，走规则引擎零成本。

**本项目实现：**
- `TokenCostTracker`：`recordUsage()` 每次 LLM 调用后累加 input/output 到 Redis（`ai:token:limit:{userId}` 1 分钟过期、`ai:token:daily:{date}` 7 天过期），同时上报 Micrometer Counter。
- `checkRateLimit()`：用户级超 10000 拒绝；`checkDailyQuota()` 全局超 1000 万拒绝。
- `AiBusinessRouter`：规则关键词（签到/打卡/我的订单/余额/积分）直接走规则引擎，`AgentOrchestrator.handleByRuleEngine()` 零 Token 返回。

**可背话术：** "限流是成本治理的最后一道闸，前面的闸是业务路由——30% 的简单请求根本不进 LLM。剩下的流量再用 Redis 计数器按用户/全局两档限。限流组件故障时我选择降级放行，宁可多花点钱也不误伤真实用户。"

### Q2.3.3（中等）AI 成本降低 50% 具体由哪些策略构成？

**结论：** 四路叠加：规则引擎过滤（约 30% 请求零 Token）+ 滑动窗口记忆控 Token + RAG 结果截断 + 工具描述精简；每个决策都有 AgentTrace 数据支撑。

**本项目实现：**
- 规则引擎：`AiBusinessRouter` 挡掉约 30% 请求。
- 记忆窗口：`MessageWindowChatMemory` `maxMessages(20)`，避免历史爆炸。
- 截断：`LlmReranker` 文档截断 300 字；评测/回答输出截断。
- 工具精简：Agent 拆分后每个 SystemMessage 只描述 5-8 个工具。

**取舍 / 坑：** 50% 是"估算口径"，不是精确计费。面试官追问见第八部分 8.5。重点是"每个优化动作都有 trace 数据支撑，不是拍脑袋"。

**可背话术：** "降成本不是单一手段，是四路叠加的工程结果。而且每个决策都能从 AgentTrace 的成本归因里看到依据——比如我发现某工具 Token 统计口径重复计算占了 7% 成本，就修了口径。"

### Q2.3.4（中等）AgentTrace 的 Span 树怎么设计？怎么还原一次请求？

**结论：** `TraceContext`（ThreadLocal 栈）维护父子 Span，`TraceSpan` 记录全量字段，`TraceRecorder` 内存缓冲批量落 Redis，`GET /ai/trace/{traceId}` 还原。

**本项目实现：**
- `TraceSpan` 字段：`traceId / spanId / parentSpanId / spanName / startTimeMs / endTimeMs / model / inputTokens / outputTokens / toolCallCount / success / error / metadata`。
- `TraceContext`：`ThreadLocal<Deque<TraceSpan>>` 栈，`beginTrace()` 开根、`begin()` 开子（父=栈顶）、`end()` 出栈上报、`endWithError()` 标记失败、`endTrace()` finally 兜底清栈。
- 埋点：`AgentOrchestrator.process` 根 + `BusinessRouter.decide` / `TokenRateLimit.check` / `RouterAgent.classify` / `SemanticCache.lookup` / `RAG.hybridRetrieval` / `RAG.llmRerank` / `LLM:mimo-v2.5-pro`（在 `TracingChatLanguageModel` 里）/ `ShopAgent.chat` 等。
- `TraceRecorder`：`ArrayBlockingQueue(20000)` 非阻塞入队，`@Scheduled(fixedRate=5000)` drainTo 批量写 Redis（`agent:trace:{traceId}`，TTL 1 小时，recent 保留 200），成本归因 `costBySpan` 聚合。

**可背话术：** "日志是平面的，Trace 是树状的。Span 记录父子关系和耗时/token/错误，一次请求一棵树，能回答'哪一步拖慢了整条链路'。内存队列缓冲批量落盘，主链路零同步 IO。"

### Q2.3.5（中等）ThreadLocal 存 traceId 会不会线程泄漏？怎么防？

**结论：** 会，三防：finally 兜底清栈、异常用 endWithError 标记、异步显式透传不读父线程 ThreadLocal。

**本项目实现：**
- `AgentOrchestrator.process()` 外层 `finally { TraceContext.endTrace(); }`，无论成功失败都清空栈和 ThreadLocal。
- `callAgent()` 里异常 `endWithError()` 再抛。
- 异步场景（Flux/CompletableFuture）在 `AgentOrchestrator` 里是同步阻塞聚合（`chatBlocking()` 用 `.block()`），所以暂时没遇到跨线程透传；若引入 @Async 需把 traceId 当参数传，不靠 InheritableThreadLocal。

**可背话术：** "ThreadLocal 泄漏是线程池复用导致的串数据。我的防线是 finally 兜底清栈 + 异常路径标记 + 异步参数显式透传。这是可观测系统的基本功。"

### Q2.3.6（难）SemanticCache 和普通 KV 缓存有什么区别？

**结论：** KV 缓存 key 字符串全等才命中，语义缓存用"问题向量"当检索键，相似度 ≥ 0.92 就命中，同义改写也能命中。

**本项目实现（`SemanticCache`）：**
- 存储：复用 PgVector，存 `问题 embedding → 回答`，metadata 带 `type=semantic_cache / question / cachedAnswer / cachedAt`。
- 查询 `get()`：`embeddingModel.embed(question)` → `EmbeddingSearchRequest(maxResults=1, minScore=0.92)` → 校验 type 标记 + TTL（10 分钟）→ 命中返回 `cachedAnswer`。
- 写入 `put()`：回答生成后幂等写。
- 安全边界（在 `AgentOrchestrator`）：只有 `isCacheable(intent)`（SHOP_QUERY/REVIEW_QUERY/GENERAL）+ `!isPersonalQuestion()`（"我的订单/我的券"永不缓存）才查/写缓存。

**取舍 / 坑：** 阈值 0.92 是超参，降阈值提命中率但误命中风险上升；缓存回答可能有"过期"风险，靠 TTL + 事件驱动 RAG 同步从源头保证新鲜。

**可背话术：** "核心差异是'键的语义化'：KV 是字符串相等，语义缓存是向量相似。我设了 0.92 阈值，0.95 的同义改写能命中，但'我的订单'这种个人化问题我做了硬隔离，永不缓存。"

### Q2.3.7（难）语义缓存命中后怎么保证回答没过期、不是错的？

**结论：** 三道防线：意图白名单（只缓存只读）、个人化隔离、TTL 惰性删除；命中路径可观测。

**本项目实现：** `AgentOrchestrator.isCacheable()` 只允许只读意图；`isPersonalQuestion()` 排除强绑定用户的回答；`SemanticCache.get()` 里 `System.currentTimeMillis() - cachedAt > ttl` 视为未命中并 `removeStale()` 惰性删除；数据变更通过 `RagSyncListener` 事件驱动同步知识库，从源头保证新鲜；`SemanticCache.lookup` 有 Trace span，hit/miss 可观测。

**可背话术：** "我宁可 cache miss 也不 cache 错：白名单排除了状态性操作，个人化问题直接不进缓存，过期靠 TTL 惰性删除。缓存命中本身还有 Trace span 和统计接口，不是黑盒。"

### Q2.3.8（深挖）AgentTrace 怎么定位一次"回答质量差"的问题？

**结论：** 用 traceId 拉出 Span 树，按 意图→RAG→工具→模型 逐环节排查。

**本项目实现：**
1. 意图 span `RouterAgent.classify`：看 intent 字段对不对，分错就修 Prompt。
2. RAG span `RAG.hybridRetrieval`：看 `vectorHits/ftsHits/mergedHits` 元数据，检索为空或太少就调阈值/权重。
3. 工具 span：看 toolCallCount / success / error，工具报错直接定位。
4. 模型 span `LLM:...`：看 model 字段，是否降级到了弱模型。

**可背话术：** "Trace 树的每个节点都有耗时、token、成功/失败和自定义 metadata。一次质量差的回答，我先看意图有没有分错，再看 RAG 命中了几条，再看工具调用成败，最后看模型有没有降级——四个环节一次定位。"

## 2.4（旧版归档）工作内容四：区块链可信存证

> 简历原文：区块链可信存证——评价、秒杀订单、AI回答三类数据 SHA-256 内容指纹 + HMAC 签名，Merkle 树批量打包进区块（哈希链 prevHash 前后衔接）防篡改存证；单条记录可凭 Merkle 证明路径独立验证，提供完整审计溯源能力。

### Q2.4.1（简单）区块链专业的你为什么做这个存证系统？这不是自己造链吗？

**结论：** 定位是"轻量私有链"，复用区块链的核心密码学思想（哈希链 + Merkle + 签名）而不是去中心化，账本可平滑替换真实联盟链。

**原理：** 真实生产需要可审计性（监管、溯源、纠纷取证），但去中心化共识对单机业务是过度设计。所以保留"不可篡改 + 可验证"的密码学内核，砍掉共识和网络层。

**本项目实现：** `ChainNotaryService` + `MerkleTree`，存证语义（指纹 + 批量 + 链式 + 单条验证）与真实链一致；演进上对接 FISCO BCOS / Hyperledger 只需替换账本实现。

**可背话术：** "我没有造链，是把区块链专业的核心思想工程化：篡改成本随链长指数上升、校验成本恒定。什么时候用真链？多组织互不信任时才需要共识；单业务方做审计存证，轻量链够用且快。"

### Q2.4.2（简单）区块哈希怎么算？为什么能防篡改？

**结论：** `blockHash = SHA-256(prevHash | merkleRoot | height | timestamp | signature)`；改任何记录 → 内容哈希变 → Merkle 根变 → 区块哈希变 → 后面链断裂。

**本项目实现：** `ChainNotaryService.recomputeBlockHash()` 与 `NotaryBlock` 一致；`verifyRecord()` 六重校验：内容哈希自检 → Merkle 根校验 → 单条 Merkle 证明 → 区块哈希自洽 → 签名校验 → 前后块衔接。

**可背话术：** "防篡改的本质不是'改不了'，而是'改了立刻被发现且篡改成本随链长增长'。验证只需要重算哈希比对，成本恒定，这是区块链工程化的精髓。"

### Q2.4.3（中等）Merkle 树在这里的价值？不用行不行？

**结论：** 把 O(n) 条记录压成 1 个 merkleRoot 上链，存储省 ~90%；单条可凭 O(log n) 证明路径独立验证。

**本项目实现：** `MerkleTree`：叶子 = 各记录 contentHash，父节点 = `sha256(left+right)`，奇数叶子复制末位配对（Bitcoin 同款）；`root()` / `proof(index)` / `verify(leafHash, root, proof)`。`ChainNotaryService.sealBlock()` 里 `MerkleTree.of(recordHashes)` 生成根，区块只存根 + 记录哈希列表。

**可背话术：** "不用 Merkle 也可以，每条记录直接串链，但验证要 O(n) 扫全链、链上存 O(n) 个哈希。用 Merkle 后区块只承诺一个根，单条记录凭兄弟节点路径 O(log n) 验证。比特币也是这么干的。"

### Q2.4.4（中等）HMAC 签名和哈希链各自的职责？

**结论：** 哈希链保完整性（数据没被改），HMAC 保真实性（确实是服务端出的块），两者缺一不可。

**本项目实现：** `ChainNotaryService.recomputeSignature()` 用 HMAC-SHA256(prevHash|merkleRoot|height|timestamp) + 服务端 secret 签名；`recomputeBlockHash()` 再把签名纳入区块哈希。验证时同时比对签名和哈希。

**取舍 / 坑：** 演示用 HMAC 对称密钥，生产可换 RSA/SM2 非对称签名（多点明可扩展）。HMAC 的问题是对称密钥共管，非对称才能做到"公开可验证"。

**可背话术：** "哈希链回答'改没改'，签名回答'谁出的块'。对称 HMAC 够演示，要公开审计就换非对称签名，我讲的时候会点明这个可扩展性。"

### Q2.4.5（中等）存证时机和数据内容怎么设计？为什么不影响主流程？

**结论：** 在业务已生效后存关键字段，内容哈希幂等去重，存证失败 catch 住不影响下单/对话主流程。

**本项目实现：**
- 秒杀订单：`VoucherOrderServiceImpl.createVoucherOrder()` 在 `save` 订单 + 扣库存成功后 `notaryService.notarize("SECKILL_ORDER", "{orderId,userId,voucherId,status,createTime}")`。
- AI 回答：`AgentOrchestrator.process()` 结束时 `notaryService.notarize("AGENT_DECISION", "{traceId,userId,intent,handler,input,output}")`。
- 评测报告：`AgentEvalService.notarizeReport()` `notarize("EVAL_REPORT", ...)`。
- 三处都 try-catch 包住，失败只 warn 日志。

**取舍 / 坑：** 存证是"审计增强"，不是业务前置条件；`notarize()` 本身异步批量封块、主链路零同步 IO。当前代码里直接对"评价"落库存证的触发点未接线（见第八部分 8.6 诚实话术），扩展方向是 `BlogServiceImpl` 保存后发事件存证。

**可背话术：** "我只存'已生效的事实'的关键字段，不存半成品。内容哈希当索引天然幂等，重复存同一条不会双份。存证失败绝不影响下单——这是工程边界意识。"

### Q2.4.6（难）BATCH_SIZE=10、30 秒定时封块，怎么保证不丢记录？

**结论：** 内存缓冲 + 分布式锁 + 失败回滚缓冲 + 定时兜底，四重保障。

**本项目实现（`ChainNotaryService`）：**
- `notarize()`：记录入 `pending`（synchronized），满 10 条触发 `sealBlock()`。
- `sealBlock()`：Redisson `tryLock(0, 3s)` 保证并发唯一出块；取快照并清空缓冲；构建 Merkle、签名、写 Redis（区块列表 + 链头 + 记录 + 内容哈希索引）；失败把快照 `pending.addAll(0, toSeal)` 回滚避免丢。
- `scheduledFlush()`：`@Scheduled(fixedDelay = 30000)` 每 30 秒兜底封未满批的记录。
- `flushPending()`：手动强制封块（接口/测试用）。

**可背话术：** "满 10 条立即封、30 秒定时兜底、失败回滚缓冲、分布式锁防并发重复出块——四条路保证'要么没到封块时机，要么一定上链'。"

### Q2.4.7（难）单条记录怎么独立验证？给出验证流程。

**结论：** `verifyByRecordId()` 六步：内容哈希 → Merkle 根 → Merkle 证明 → 区块哈希 → 签名 → 链衔接。

**本项目实现（`ChainNotaryService.verifyRecord()`）：**
1. `MerkleTree.sha256Hex(record.getContent())` 比对 contentHash（防篡改核心）。
2. 加载区块，`MerkleTree.of(recordHashes).root()` 比对 merkleRoot。
3. `tree.proof(leafIndex)` 生成证明，`MerkleTree.verify(contentHash, merkleRoot, proof)` 验证。
4. `recomputeBlockHash(block)` 比对 blockHash。
5. `recomputeSignature(block)` 比对 signature。
6. 非创世区块校验链头衔接。
返回 `NotaryVerifyResult`（valid + 各环节 detail）。接口：`GET /ai/notary/verify/{recordId}`、`/ai/notary/verify/hash/{hash}`、`/ai/notary/chain/verify`。

**可背话术：** "验证是纯本地重算，200ms 内出结论。关键是单条验证不扫全链——只要那条 Merkle 证明路径 + 区块哈希 + 链头衔接对，就证明没被改过。"

### Q2.4.8（深挖）存证数据存在哪？Redis 会不会丢？

**结论：** 存 Redis（区块列表 + 记录 + 索引），是"演示级持久化"，生产应落 PostgreSQL 或真链 SDK。

**本项目实现：** Redis key：`chain:notary:head`（链头 Hash）、`chain:notary:blocks`（区块 List）、`chain:notary:record:{recordId}`、`chain:notary:idx:{contentHash}`。`chainInfo()` 返回高度/链头/待打包数。

**取舍 / 坑：** Redis 持久化（AOF/RDB）能扛一般故障，但严谨的存证要落 DB 或链。面试主动说"当前是 Redis 持久化的轻量实现，生产要迁 PG 双写或接真链"，体现边界意识。

**可背话术：** "存证的核心价值是哈希链和验证逻辑，存储后端可以换。当前用 Redis 是为了演示闭环，生产我建议双写 PostgreSQL 或直接对接联盟链 SDK。"

## 2.5（旧版归档）工作内容五：业务链路可靠性设计

> 简历原文：业务链路可靠性设计——针对重复请求、库存超卖等问题，Redis Lua 脚本原子预扣库存和用户限购控制，RabbitMQ异步削峰，数据库乐观锁保证库存最终一致性，Direct Exchange、手动ACK、死信队列及失败重试机制保障消息可靠消费；订单落库后自动上链存证，抢购链路全程可审计；JMeter压测平均响应时间 350ms→130ms。

### Q2.5.1（简单）秒杀链路完整讲一遍？

**结论：** 时间窗口校验 → Lua 原子预扣 → MQ 异步削峰 → 事务落库（乐观锁 + 唯一索引幂等）→ 死信补偿，全程可审计。

**本项目实现（`VoucherOrderServiceImpl.seckillVoucher()` + `createVoucherOrder()`）：**
1. 查 `SeckillVoucher` 校验时间窗口（未开始/已结束直接拒绝）。
2. 执行 `seckill.lua`：判库存（EXISTS 不存在返回 4、stock<=0 返回 1）、判限购（SISMEMBER 重复返回 2）、`INCRBY stock -1`、`SADD orderKey userId`，成功返回 0。
3. Lua 成功 → `rabbitTemplate.convertAndSend(ORDER_EXCHANGE, ORDER_ROUTING_KEY, voucherOrder)` 发消息，立即返回 orderId（异步削峰）。
4. `OrderMessageListener.onMessage` 消费 → `createVoucherOrder()`：先 `save` 订单（唯一索引 `uk_user_voucher` 兜底一人一单），再乐观锁 `UPDATE ... SET stock=stock-1 WHERE voucher_id=? AND stock>0`，0 行影响抛异常回滚。
5. 落库成功后 `notaryService.notarize("SECKILL_ORDER", ...)` 上链。
6. 消费失败 `MAX_ATTEMPTS=3`，x-death 计数，重试耗尽 `nack(requeue=false)` 进死信 → `DlxOrderListener` 补偿回滚 Redis 库存 + 移除下单记录 + 记录人工补偿。

**可背话术：** "一条链路三层防护：Redis 挡 99% 无效请求，MQ 削峰，数据库兜底超卖，死信补偿收尾，最后订单上链可审计。"

### Q2.5.2（中等）为什么用 Lua 而不是分布式锁？Lua 为什么原子？

**结论：** Lua 在 Redis 单线程里脚本整体执行，天然原子、无锁竞争、一次网络往返；分布式锁有加解锁开销和死锁风险。

**原理：** Redis 命令是单线程串行执行的，`eval` 一个 Lua 脚本时整个脚本执行期间不会被其他命令插入，因此脚本内的 判库存+扣库存+记用户 是原子的。

**本项目实现（`seckill.lua`）：** `DefaultRedisScript<Long>` 加载 `ClassPathResource("seckill.lua")`，`stringRedisTemplate.execute(SECKILL_SCRIPT, Collections.emptyList(), voucherId, userId)` 一次调用完成四步。

**取舍 / 坑：** Lua 原子但脚本不可调试；key 丢失会导致 `tonumber(nil)` 报错，所以脚本开头先 `EXISTS stockKey` 判断返回 4。

**可背话术：** "分布式锁要加锁解锁、有死锁风险，Lua 是 Redis 单线程里整体原子执行，无锁竞争，一次网络往返。而且我把'判库存+判限购+扣库存+记用户'合进一个脚本，从根上消灭了竞态窗口。"

### Q2.5.3（中等）为什么需要 Redis Lua + 数据库乐观锁两层？一层不够吗？

**结论：** Redis 与 DB 不同步，极端窗口（Redis 主从切换/网络抖动）可能出现 Redis 扣成功但 DB 库存不足；乐观锁做物理兜底。

**本项目实现：** 第一层 Lua 快速拦截 99% 无效请求；第二层消费者里 `WHERE stock > 0` 条件更新，利用 MySQL 行锁保证物理不超卖；唯一索引 `uk_user_voucher` 再保证一人一单。

**可背话术：** "Redis 是'性能闸'，DB 是'正确性闸'。任何中间件都有抖动窗口，数据库乐观锁是最后一道物理防线，而且它和唯一索引一起，把'不超卖'和'一人一单'都钉死在数据库层面。"

### Q2.5.4（中等）重复请求/重复消息怎么处理（幂等设计）？

**结论：** 三层幂等：Lua 的 SISMEMBER 限购、数据库唯一索引、死信补偿的判重。

**本项目实现：**
- Lua 层：`SISMEMBER orderKey userId` 判重，重复返回 2（不能重复下单）。
- DB 层：`tb_voucher_order` 的 `UNIQUE KEY uk_user_voucher(user_id, voucher_id)`，`save` 抛 `DuplicateKeyException` → catch 幂等返回（MQ 重复投递/极端并发重复下单都拦得住）。
- 死信层：`DlxOrderListener` 先 `getById(orderId)` 判断订单是否已落库，落库则跳过回滚（ACK 丢失场景）。

**可背话术：** "幂等我做了三层：Redis 挡绝大多数、唯一索引挡并发竞态、死信补偿判重兜底。唯一索引那层最硬——它在数据库层面保证一人一单，比先 count 再 insert 的 TOCTOU 方案严谨。"

### Q2.5.5（中等）为什么要手动 ACK？失败重试和死信怎么配合？

**结论：** 手动 ACK 保证消息不丢、失败可重试；`MAX_ATTEMPTS=3` 用 x-death 计数，耗尽进死信队列补偿，避免消息无限堆积。

**本项目实现：**
- `application.yaml`：`acknowledge-mode: manual`、`prefetch: 1`。
- `OrderMessageListener.onMessage`：成功 `basicAck`；异常读 `x-death` 头 `getRetryCount()`，`attempt >= 3` 时 `basicNack(deliveryTag, false, false)`（不 requeue → 走 DLX），否则 `basicNack(..., true)` 重新入队。
- `RabbitMQConfig`：主队列 `seckill.order.queue` 绑定 `.deadLetterExchange(order.dlx.direct).deadLetterRoutingKey("seckill.order.dlx")`。

**可背话术：** "手动 ACK + prefetch=1，配合 x-death 计数做有限重试（3 次），重试耗尽 nack 不 requeue 进死信。这样既不丢消息，也不会让坏消息无限重投打爆队列。"

### Q2.5.6（难）死信队列补偿怎么做？补偿本身失败怎么办？

**结论：** `DlxOrderListener` 判订单是否已落库：没落库就回滚 Redis 库存 + 移除下单记录（用户可重新参与）+ 写人工补偿记录；补偿失败也 ACK，靠补偿记录的幂等性人工重放。

**本项目实现（`DlxOrderListener.onDlxMessage`）：**
1. `voucherOrderService.getById(orderId)` 判订单是否已落库。
2. 未落库：`INCR seckill:stock:{voucherId}` 恢复库存 + `SREM seckill:order:{voucherId}` 移除用户记录（key 前缀与 `seckill.lua` 一致）。
3. 已落库（ACK 丢失/重复投递）：跳过回滚。
4. 无论是否回滚，`recordDlx()` 写 `seckill:dlx:records`（保留 1000 条）供审计。
5. `basicAck`；补偿异常也 ACK，防止死信无限堆积。

**可背话术：** "死信补偿的核心是'库存守恒'：订单没落库就回滚 Redis，订单已落库就不动。补偿记录本身幂等，可人工重放。关键设计是'补偿失败也 ACK'——宁可交给人工，也不能让死信队列无限堆积。"

### Q2.5.7（难）发布确认和 Returns 回调解决了什么问题？

**结论：** Confirm 回答"交换机收没收到"，Returns 回答"消息有没有路由到队列"，两者补齐"发送失败无感知"的盲区。

**本项目实现（`RabbitMQPublisherCallback`）：**
- `@PostConstruct init()` 注册 `setConfirmCallback`（ack → debug；nack → 记录失败 `seckill:pub:failures`）+ `setReturnsCallback`（路由失败 → 记录）。
- `application.yaml` 开启 `publisher-confirm-type: correlated`、`publisher-returns: true`。
- 失败记录保留最近 500 条供审计补偿重发。

**可背话术：** "这是典型'配置了但没接线'的坑：yaml 开了 confirm/returns，但没有回调，发送失败完全无感知。我补了 Confirm 和 Returns 两个回调，失败写 Redis 供补偿。"

### Q2.5.8（深挖）压测 350ms→130ms 怎么测的？瓶颈在哪？

**结论：** JMeter 压测，同步下单 vs 异步下单对比；核心瓶颈是数据库连接池满载，异步削峰后连接池无压力。

**本项目实现：** 优化前同步下单：每个请求直接写库，高并发下 MySQL 连接池满载，P99 350ms；优化后 Lua 预扣 + MQ 异步，用户立即拿到 orderId，数据库压力被摊平到时间轴，P99 130ms。

**取舍 / 坑：** 具体压测线程数/数据见第八部分 8.7。要诚实：P99 是理想环境数值，压测为本地单机环境。

**可背话术：** "瓶颈不是 Redis、不是 MQ，是数据库连接池。把'写库'从同步链路摘出去变成异步消费，响应时间自然降下来。我用 JMeter 压测对比前后 P99，从 350ms 到 130ms。"

## 3.1 Java 基础与并发

### Q3.1.1 ThreadLocal 原理与内存泄漏
**结论：** 每个线程一个 ThreadLocalMap，key 是弱引用 ThreadLocal、value 强引用；key 被 GC 后 value 无法访问 = 泄漏。
**本项目：** `TraceContext` 用 `ThreadLocal<Deque<TraceSpan>>` 存 Span 栈，`finally { endTrace() }` 清空防泄漏（见 2.3.5）。

### Q3.1.2 原子类 AtomicInteger 为什么线程安全
**结论：** CAS + volatile，无锁自旋，适合计数器/索引。
**本项目：** `ModelRouter.chatModelIndex`、`TokenCostTracker.totalInputTokens`（AtomicLong）、`SemanticCache.localHits`（AtomicLong）都是原子类。

### Q3.1.3 ConcurrentHashMap 为什么并发安全
**结论：** JDK8 后 CAS + synchronized 锁桶（链表头结点），并发度=桶数。
**本项目：** `McpServer.tools/resources/prompts`、`McpClient.servers/externalTools`、`McpController.sseSessions`、`TraceRecorder.costBySpan` 都是 ConcurrentHashMap。

### Q3.1.4 LongAdder 和 AtomicLong 区别
**结论：** LongAdder 分段累加、读时求和，写多读少场景更优；AtomicLong 每次 CAS 全局争用。
**本项目：** `TraceRecorder` 里 `CostAggregate` 的 calls/inputTokens/outputTokens 用 LongAdder。

### Q3.1.5 Lambda + 函数式接口
**本项目：** `AgentOrchestrator` 内部 `@FunctionalInterface AgentCall { String invoke(); }`，用 Lambda 包裹各 Agent 调用做 Span。

### Q3.1.6 Java 17 新特性（本项目用了哪些）
**结论：** record、switch 表达式、文本块、密封类、`instanceof` 模式匹配。
**本项目：** `DlxOrderListener` 的补偿记录是 record；`AgentOrchestrator.routeToAgent()` 用 switch 表达式 + 箭头；文本块用在 `HybridContentRetriever`（FTS 参数化 SQL）和 `AgentEvalService`/`LlmReranker`（裁判/精排 Prompt）；`fullTextSearchWithFilter` 用 `filter instanceof IsEqualTo` 模式匹配。

### Q3.1.7 线程池的核心参数有哪些？拒绝策略怎么选？
**结论：** 核心线程数 / 最大线程数 / 队列 / 空闲存活时间 / 线程工厂 / 拒绝策略；拒绝策略五种。
**执行流程：** 核心线程未满 → 直接执行；满了 → 进队列；队列满 → 扩到 max；还满 → 触发拒绝策略。
**拒绝策略：** `AbortPolicy`（抛异常，默认）、`CallerRunsPolicy`（调用线程自己跑，**保不丢**）、`DiscardPolicy`（静默丢）、`DiscardOldestPolicy`（丢最旧）、自定义。
**本项目：** 秒杀/批量异步任务用有界队列 + `CallerRunsPolicy`——宁可让调用线程同步执行，也不丢消息；缓存重建线程池 `CACHE_REBUILD_EXECUTOR` 独立隔离，避免污染业务线程。
**可背话术：** "线程池先核心、再队列、再扩容、最后拒绝。项目里选 CallerRuns 是怕丢数据——请求量再大，最坏是慢一点，不能静默丢。"

### Q3.1.8 反射是什么？项目里哪里用到了反射？
**结论：** 反射 = 运行时获取类的结构（Class/字段/方法）并调用，是框架和注解的核心机制；缺点是有性能开销和绕过编译期检查。
**项目里的反射：**
1. **`SecuredToolProvider`**：用反射扫描 `@Tool` 注解的方法，动态生成 LangChain4j 工具描述，再委托 `DefaultToolExecutor` 执行——这就是"注解 + 反射"把普通 Java 方法变成 AI 可调用工具的原理。
2. **LangChain4j `AiServices.builder()`**：基于动态代理（反射的子集）为接口生成实现。
3. Spring 容器 / MyBatis-Plus 底层也都是反射 + 注解。
**可背话术：** "反射是框架的'运行时自省'。`SecuredToolProvider` 就用反射扫描 @Tool 注解生成工具清单——注解只是标签，反射才是让它干活的东西。反射有性能开销，所以工具扫描做了一次性缓存。"

## 3.2 Spring / Spring Boot

### Q3.2.1 Spring Boot 自动配置原理
**结论：** `@SpringBootApplication` = `@Configuration + @EnableAutoConfiguration + @ComponentScan`；自动配置靠 `META-INF/spring/...AutoConfiguration.imports` + `@ConditionalOnXxx`。
**本项目：** `AiConfig` / `PgVectorConfig` 都是显式 `@Configuration` + `@Bean`，覆盖框架默认装配。

### Q3.2.2 @Transactional 失效场景
**结论：** 自调用（同类方法调用不经过代理）、非 public、异常被 catch、checked 异常默认不回滚、代理对象。
**本项目：** `VoucherOrderServiceImpl.createVoucherOrder()` 用 `@Transactional`，扣库存失败抛 `IllegalStateException`（RuntimeException）触发回滚；对 `DuplicateKeyException` catch 后幂等 return（不抛，事务正常提交——此时订单已存在无需回滚）。

### Q3.2.3 @Async 使用注意
**结论：** 需要 `@EnableAsync`、被代理调用（不能自调用）、默认单线程池（需配 ThreadPoolTaskExecutor）、线程池满了丢任务。
**本项目：** `RagSyncListener` 的 `@EventListener + @Async` 异步处理 RAG 增量同步，不阻塞业务事务。

### Q3.2.4 Spring Event 机制
**结论：** 发布-订阅：`ApplicationEventPublisher.publishEvent()` → `@EventListener` 监听，默认同步、可配 @Async 异步。
**本项目：** `BlogServiceImpl` 发布 `BlogCreatedEvent / BlogDeletedEvent`，`RagSyncListener` 异步监听做向量增量同步。

### Q3.2.5 @Scheduled 定时任务
**结论：** `@EnableScheduling` + `@Scheduled(fixedRate/fixedDelay/cron)`；fixedRate 固定频率、fixedDelay 上次执行完再隔 N。
**本项目：** `TraceRecorder.flush()`（fixedRate=5000 批量落盘）、`ChainNotaryService.scheduledFlush()`（fixedDelay=30000 兜底封块）、`McpHealthMonitor`（心跳 30s / 清理 60s）。

### Q3.2.6 Bean 生命周期与 @PostConstruct
**结论：** 实例化 → 属性填充 → Aware 回调 → BeanPostProcessor → init（@PostConstruct / InitializingBean / initMethod）→ 使用 → 销毁。
**本项目：** `RabbitMQPublisherCallback.init()` 用 `@PostConstruct` 注册 Confirm/Returns 回调；`McpController.init()` 用 `@PostConstruct` 注册 24 个 MCP 工具。

### Q3.2.7 循环依赖
**本项目：** `AiConfig.routedChatModel()` 不注册为 Bean 而是 `private` 方法直接 `new TracingChatLanguageModel(...)`，注释里明确写"避免被 ModelRouter 的 List<ChatLanguageModel> 收集形成循环依赖"。

## 3.3 MySQL

### Q3.3.1 事务隔离级别
**结论：** READ UNCOMMITTED / READ COMMITTED（默认，Oracle）/ REPEATABLE READ（MySQL 默认）/ SERIALIZABLE。MySQL RR 用 MVCC + Next-Key Lock 解决幻读。
**本项目：** 秒杀消费用 `@Transactional` 默认隔离级别（RR），配合唯一索引幂等。

### Q3.3.2 乐观锁和悲观锁
**结论：** 悲观锁（SELECT FOR UPDATE）冲突多时用；乐观锁（版本号 / 条件更新）冲突少时用，失败重试。
**本项目：** 扣库存 `UPDATE tb_seckill_voucher SET stock=stock-1 WHERE voucher_id=? AND stock>0`，0 行影响=库存不足，抛异常回滚——条件更新型乐观锁。

### Q3.3.3 唯一索引去重原理
**结论：** 唯一索引在存储层保证 (user_id, voucher_id) 全局唯一，并发插入只有一个成功，其余抛 DuplicateKeyException。
**本项目：** `db/hmdp.sql` `UNIQUE INDEX uk_user_voucher(user_id, voucher_id)`，`createVoucherOrder()` catch DuplicateKeyException 幂等返回。

### Q3.3.4 索引失效场景
**结论：** 隐式类型转换、函数包裹索引列、前导模糊（%xx）、OR 连接、`!=`/`NOT IN`。
**本项目：** `ShopAwareContentRetriever.findShopByName()` 用 `LIKE` 后置通配（`like` 名称，能走索引）+ `LIMIT 1`。

### Q3.3.5 SQL 注入防护
**本项目：** `HybridContentRetriever.fullTextSearchWithFilter()` 用 `metadata->>? = ?` 参数化查询，注释明确"使用参数化查询防止 SQL 注入"。

### Q3.3.6 主从复制 / 读写分离（扩展题）
**本项目：** 生产扩展方向，当前未实现；`PgVectorConfig` 双数据源（MySQL 主库 + PG RAG 库）是"多数据源"的实践基础。

### Q3.3.7 存储引擎：InnoDB 和 MyISAM 有什么区别？为什么用 InnoDB？
**结论：** InnoDB 支持事务 + 行级锁 + MVCC + 外键，是事务型业务的标准；MyISAM 只支持表锁、非事务，仅适合只读场景。
**原理：**
| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ✅ | ❌ |
| 锁粒度 | 行锁（配合索引） | 表锁 |
| 崩溃恢复 | ✅（redo log） | ❌ |
| 存储结构 | B+Tree 聚簇索引 | B+Tree 非聚簇 + 数据文件分离 |
| 适用 | OLTP 高并发写 | OLAP / 只读 |
**本项目：** 秒杀订单、库存、用户表全部走 InnoDB——并发扣库存依赖"行锁 + 条件更新"的原子性，MyISAM 表锁会串行化所有写入，扛不住秒杀。
**可背话术：** "业务表必须 InnoDB：我要行锁并发扣库存、要事务保证扣库存和落单原子性、要 MVCC 保证 RR 下的一致性读。MyISAM 的表锁会让秒杀退化成串行。"

### Q3.3.8 你做 SQL 优化的一般思路是什么？
**结论：** 先定位慢 SQL（慢查询日志 / EXPLAIN），再按"索引 → SQL 写法 → 表结构 → 架构"四层优化。
**EXPLAIN 看什么：** `type`（至少 range/ref，避免 ALL 全表扫描）、`key`（是否命中索引）、`rows`（扫描行数，越小越好）、`Extra`（`Using index`=覆盖索引最佳；`Using filesort`=要加排序索引）。
**本项目：**
- **覆盖索引**：`uk_user_voucher(user_id, voucher_id)` 让"查是否已下单"的 `count(*)` 直接走索引（`Using index`），避免回表。
- **避免索引失效**：`findShopByName()` 用 `LIKE 名称%`（后置通配可走索引）而非 `%名称%`；`fullTextSearchWithFilter()` 用参数化查询。
- **最左前缀**：联合索引 `(user_id, voucher_id)` 只有按 user_id 查（或 user_id+voucher_id）才走索引，单独按 voucher_id 查会失效——这是索引设计的基本原则。
**可背话术：** "我优化 SQL 三步：EXPLAIN 看执行计划定位全表扫描，把高频 where 列建索引（能覆盖就覆盖），再改 SQL 写法避免索引失效。秒杀去重那条 `count(*)` 靠唯一索引直接覆盖，压测 350ms→130ms 就有这部分贡献。"

## 3.4 Redis

### Q3.4.1 Redis 为什么快
**结论：** 内存存储 + 单线程（避免上下文切换和锁竞争）+ I/O 多路复用（epoll）+ 高效数据结构。
**本项目：** Lua 脚本依赖单线程原子性；消息积压、缓存、计数全用 Redis。

### Q3.4.2 Redis 持久化 RDB / AOF
**结论：** RDB 快照（fork + COW），恢复快、可能丢数据；AOF 追加日志，fsync 策略控制丢失窗口。
**本项目：** 存证链数据、token 计数都存 Redis，靠持久化 + 备份保障。

### Q3.4.3 缓存穿透 / 击穿 / 雪崩
**结论：** 穿透=查不存在数据→布隆过滤器/空值缓存；击穿=热点 key 过期→互斥锁/逻辑过期；雪崩=大量 key 同时过期→随机 TTL。
**本项目：** `RedisChatMemoryStore` 等 TTL 场景；`LongTermMemoryService`/`UserProfileService` 用固定 TTL（画像 1 小时）；可扩展随机偏移防雪崩。

### Q3.4.4 Redis 分布式锁
**结论：** `SET lock key NX EX ttl` 加锁，Lua 原子释放（校验 owner + delete）；Redisson 封装了看门狗续期。
**本项目：** `ChainNotaryService.sealBlock()` 用 Redisson `RLock.tryLock(0, 3, TimeUnit.SECONDS)` 保证并发唯一出块；另有 `SimpleRedisLock`（utils）。

### Q3.4.5 Redis 事务 / Lua 原子性
**本项目：** 秒杀用 Lua（见 2.5.2）；Redisson 锁底层也是 Lua（`unlock.lua`）。

### Q3.4.6 Redis GEO
**本项目：** `ShopTools.findNearbyShops()` 用 Redis GEO（`opsForGeo().radius()`）按类型分桶 `shop:geo:{typeId}` 做附近商铺搜索；未指定类型时遍历所有桶（`GeoDataInitializer` 初始化数据）。

### Q3.4.7 BitMap
**本项目：** 签到用 Redis BitMap（`getBit`/`setBit`），`UserTools.querySignStatus/querySignStreak` 按 用户ID+年月 为 key，统计连续签到天数。

## 3.5 RabbitMQ

### Q3.5.1 五种交换机类型
**结论：** Direct（精确 routing key）、Topic（通配匹配 #/*）、Fanout（广播）、Headers（头匹配）、Default。
**本项目：** 秒杀用 Direct Exchange `order.direct`，routing key `seckill.order`，一对一精确投递；死信用 `order.dlx.direct`。

### Q3.5.2 消息可靠性：生产者→交换机→队列→消费者
**结论：** 四段保证：Confirm（到交换机）、Returns（路由到队列）、持久化（队列 + 消息）、手动 ACK（消费完成）。
**本项目：** `RabbitMQPublisherCallback` 补 Confirm + Returns；队列 durable；消费者手动 ACK（见 2.5.5/2.5.7）。

### Q3.5.3 死信队列怎么触发
**结论：** 三种：消息 TTL 过期、队列满、消费者 nack/reject 且 requeue=false。
**本项目：** `RabbitMQConfig` 主队列 `.deadLetterExchange(order.dlx.direct).deadLetterRoutingKey("seckill.order.dlx")`；消费者重试耗尽 `basicNack(deliveryTag, false, false)` 触发。

### Q3.5.4 手动 ACK vs 自动 ACK
**结论：** 自动 ACK 消费即确认，宕机丢消息；手动 ACK 成功后确认，失败可重试/死信。
**本项目：** `acknowledge-mode: manual`，`OrderMessageListener` 成功 ack、失败按 x-death 计数重试或死信。

### Q3.5.5 消息幂等
**本项目：** 消费端唯一索引幂等（见 2.5.4）。

### Q3.5.6 消费者负载均衡 / prefetch
**本项目：** `prefetch: 1` 每次只取 1 条，配合手动 ACK 保证单条串行处理、避免消息积压在某消费者。

## 3.6 LangChain4j

### Q3.6.1 LangChain4j 的 AiServices 是什么
**结论：** 用接口 + 注解（@SystemMessage/@UserMessage/@Tool/@MemoryId）声明式定义 LLM 应用，运行时动态代理生成实现，自动处理工具调用循环、记忆、RAG。

## 3.9 区块链（专业标签，必被问）

### Q3.9.1 区块链的核心思想
**结论：** 分布式账本 + 共识 + 密码学（哈希链、Merkle、签名）+ 不可篡改/可溯源。核心密码学三件套是哈希、签名、Merkle。
**本项目：** 用哈希链 + Merkle + HMAC 做私有存证链（见 2.4）。

### Q3.9.2 区块链为什么不可篡改（本质）
**结论：** 不是改不了，而是"篡改成本随链长指数上升、校验成本恒定"：改一个区块要重算它和后续所有区块的哈希 + 共识。
**本项目：** `NotaryBlock.prevHash` 前后衔接，`verifyChain()` 沿 prevHash 回溯校验。

### Q3.9.3 哈希链 vs 区块链
**结论：** 哈希链是单向哈希前后连接的数据结构（核心防篡改）；区块链 = 哈希链 + 区块 + 共识 + 去中心化网络。
**本项目：** ChainNotary 是"区块链的密码学内核"（哈希链 + 区块 + Merkle + 签名），砍掉共识层。

### Q3.9.4 Merkle 树怎么构建/验证
**本项目：** 叶子=记录哈希，父节点=sha256(left+right)，奇数复制末位；proof 收集各层兄弟节点，verify 沿路径重算比对根（见 2.4.3）。

### Q3.9.5 SHA-256 和 HMAC-SHA256 区别
**结论：** SHA-256 是单向哈希（完整性），HMAC-SHA256 是带密钥的哈希（完整性 + 真实性/身份），无密钥无法伪造。
**本项目：** `MerkleTree.sha256Hex()` 算内容指纹；`ChainNotaryService.recomputeSignature()` 用 HmacSHA256 + secret 签区块。

### Q3.9.6 什么时候用真链，什么时候轻量链够用
**结论：** 多组织互不信任、需要共识 → 联盟链/公链；单方审计、防篡改存证 → 轻量链/哈希链即可，性能好、成本低。
**本项目：** 定位轻量链，可替换 FISCO BCOS/Hyperledger SDK。

### Q3.9.7 什么是零知识证明 / 智能合约（扩展认知）
**结论：** 能讲清概念即可：ZKP=不泄露数据本身证明数据满足性质；智能合约=链上自动执行的代码。面试官问区块链专业时展示知识面。

## 3.10 Linux / Git / 工程协作

> 简历技能栏写了"熟悉 Linux、Git 及 AI 辅助开发工具"，以下为校招常考的快速题，答出即可。

### Q3.10.1 Linux 你常用的命令有哪些？
**结论：** 围绕"看日志、看进程、看资源、看端口"四类。
**速答：** `tail -f`（实时日志）、`grep`（过滤）、`top`/`free -h`/`df -h`（CPU/内存/磁盘）、`ps -ef | grep java`（找进程）、`netstat -tlnp` 或 `ss -tlnp`（看端口）、`kill -9`（杀进程）、`find`/`grep -r`（查文件）、`scp`/`rsync`（传输）。
**可背话术：** "线上排查三板斧：top 看 CPU/内存、tail -f + grep 看日志、netstat 看端口，配合 jstack/jmap 定位 Java 层问题。"

### Q3.10.2 线上服务 CPU 100% 或 OOM 你怎么排查？
**结论：** 定位线程 → 看栈 → 看堆。
**步骤：**
1. `top` 找到高 CPU 的 Java 进程 PID；
2. `top -Hp PID` 找到高 CPU 线程 TID；
3. `printf '%x' TID` 转 16 进制，`jstack PID | grep <hex>` 定位线程栈（常见：GC 频繁 / 死循环 / 锁等待 / 大对象分配）；
4. OOM：`jmap -heap PID` 看堆、`jmap -dump:format=b,file=x.hprof PID` 导 dump，用 MAT 分析大对象。
**本项目：** 秒杀消费线程、AgentTrace 批量落盘线程都是重点排查对象；线程池 `CallerRunsPolicy` 防堆 OOM。
**可背话术：** "先 top 定位进程线程，再 jstack 看栈、jmap 看堆。十有八九是 GC 或死循环，dump 一分析就清楚。"

### Q3.10.3 Git 常用命令？分支合并和冲突怎么处理？
**结论：** 拉取提交推送 + 分支合并 + 冲突解决 + 回退。
**速答：** `git clone/branch/checkout/add/commit/push/pull`；合并 `git merge` / 变基 `git rebase`；冲突：`git status` 看冲突文件 → 手动改 → `git add` → `git commit`；回退：`git reset --hard`（丢弃提交）vs `git revert`（生成反提交，适合已推送的分支）；`git cherry-pick`（挑单个提交）。
**可背话术：** "开发完切分支、提 PR、code review 后 merge。冲突就手动解决再提交。已推送的代码用 revert 而不是 reset，避免污染远程历史。"

### Q3.10.4 Git 使用中你遇到过什么坑？
**速答（选真实场景）：** ① 提交错文件 → `git reset`/`git restore --staged` 撤销暂存；② 误删分支 → `git reflog` 找回；③ `git pull` 冲突 → 先 `git stash` 暂存本地改动再 pull；④ 大文件误提交 → `git filter-branch`/`BFG` 清理（讲"知道有这工具"即可）。
**可背话术：** "最深的是 git pull 直接覆盖本地改动，后来养成先 stash 再 pull 的习惯；误删分支用 reflog 找回来过。"

## 4.1 AgentEval（可评测）

### E1 为什么 AI 应用需要评测系统？普通测试不行吗？
**结论：** AI 输出不确定，普通断言测不了"好不好"；评测系统解决"怎么证明效果 + 怎么回归防退化"。
**本项目：** 五层测试策略：工具确定性单测 → 意图准确率 → 关键字断言 → 黄金集回归 → 生产监控；`AgentEvalService` 落地了意图准确率 + 质量评分两层。

### E2 评测系统怎么设计？分哪几层？
**结论：** 测试集（TestSet）→ 执行器（Runner）→ 裁判（Judge）→ 报告（Report）四层。
**本项目：** `EvalTestCase`（问题 + 期望意图 + 期望关键词）→ `runIntentEval/runQualityEval` → LLM 裁判 `judge()` → `EvalReport` 持久化 Redis + 上链。

### E3 意图准确率评测怎么做的？89% 怎么算的？
**结论：** 标注测试集逐条跑分类器，预测 vs 期望比对，`正确数/总数`。
**本项目：** `AgentEvalService.SEED_CASES` 8 条；`runIntentEval()` 每条 `classify()` 后 `equals(expectedIntent)`，输出 `intentAccuracy = correct / total`；报告存 `ai:eval:reports`。

### E4 质量评测怎么打分？LLM 裁判怎么当？
**结论：** 独立 LLM 当裁判，按 rubric 四维打分，聚合综合分；要求结构化输出便于解析。
**本项目：** `judge()` 用 SystemMessage 定义 相关性/准确性/完整性/安全性 0-5 分标准，输出 JSON `{"relevance":n,...}`，`extractScore()` 正则提取，`overall = 四维平均`；异常降级中性分 3。

### E5 评测跑批要花很多 Token，怎么控制成本？
**结论：** 控制测试集规模 + 评测流量路由到便宜模型 + 报告批量持久化。
**本项目：** SEED_CASES 只有 8 条；评测走 `ModelRouter.generateWithFallback`（可路由到轻量模型）；报告只落 Redis + 存证，不重复全量跑。

### E6 怎么保证评测系统自己不出错？
**结论：** 客观指标确定性比对（无偏差）+ 主观指标 rubric + 结构化输出 + 历史报告可回放 + 结果上链。
**本项目：** 意图准确率是字符串比对；质量分正则提取 + 关键词兜底；报告存 Redis 可对比基线；`notarize("EVAL_REPORT")` 防篡改。

### E7 测试集被注入偏置数据怎么办？
**结论：** 黄金集隔离 + 第三方交叉验证 + 存证审计 + 看混淆矩阵不看单一数字。
**本项目：** SEED_CASES 硬编码隔离；评测报告上链任何改动可审计；扩展可加独立人工标注集交叉验证。

### E8 评测系统的缺陷 / 可扩展方向？
**结论：** 测试集小、未覆盖 RAG 检索质量、未与 CI 联动；扩展：RAG Recall@K 评测、按意图分层扩充测试集、CI 自动回归、支持 golden set diff 告警。
**本项目：** 代码已实现 INTENT / QUALITY / RAG 三类评测（`EvalController` 暴露 `/ai/eval/intent`、`/ai/eval/quality`、`/ai/eval/rag`）。当前主要缺陷是测试集小（意图 8 条、RAG 10 条）、未与 CI 联动；扩展方向：按意图分层扩充测试集到百级、CI 一键回归、golden set diff 告警。

### E9 面试官追问：LLM-as-Judge 会被 LLM 忽悠吗？
**答法：** 会，所以：客观题用确定性比对；主观题用 4 维 rubric 细粒度打分（比单分难忽悠）；加关键词粗校验兜底；必要时多裁判投票。本质是"Judge 也不是真理，是工程化的近似评估"。

### E10 面试官追问：评测通过率 3.5 分怎么定的？
**答法：** `EvalReport.allPassed = qualityScore >= 3.5`，即四维平均 3.5/5（70 分）。这个阈值是"宁可错杀不可放过"的保守线，可用评测数据校准；核心是"阈值可配、可解释"。

## 4.2 AgentTrace（可观测）

### T1 为什么需要 Trace 而不是打日志？
**结论：** 日志是平面的（一条条独立），Trace 是树状的（一次请求一棵 Span 树），能还原调用关系、耗时归属、成本归属。
**本项目：** `TraceContext` + `TraceSpan` + `TraceRecorder`，埋点覆盖路由/限流/意图/Agent/RAG/LLM/缓存。

### T2 Trace 数据结构怎么设计？
**结论：** traceId 全局唯一 + spanId + parentSpanId 组织成树；每个 span 记录名称/耗时/模型/token/成败/错误/自定义 meta。
**本项目：** `TraceSpan` 字段见 2.3.4；`putMeta()` 记录自定义元数据（意图、命中数、路由决策等）。

### T3 怎么在代码里埋点而不侵入主逻辑？
**结论：** 用 begin/end 包裹 + 装饰器包装；埋点只增不减、异常不吞。
**本项目：** `AgentOrchestrator` 里 `TraceContext.begin("...")` / `TraceContext.end()` / `endWithError()`；`TracingChatLanguageModel` 作为 ChatLanguageModel 装饰器统一给所有 LLM 调用埋点——一处改动全链路生效。

### T4 TraceRecorder 批量落盘会不会丢 trace？
**结论：** 会丢，但设计上允许：观测数据是"尽力而为"，主链路零同步 IO；内存队列满则丢弃并计数。
**本项目：** `ArrayBlockingQueue(20000)` `offer()` 失败 `DROPPED.increment()`；`flush()` 里 `drainTo` + 记录 dropped。面试加分点：观测数据用"采样/降级"而非"阻塞主链路"。

### T5 怎么按 span 做成本归因？
**结论：** 每个 span 记 input/output token + 模型，按 spanName/intent 聚合。
**本项目：** `TraceRecorder.costAttribution()`（ConcurrentHashMap）返回**全量** spanName→聚合 Map（calls/inputTokens/outputTokens/totalMs/failures，无 Top-N 截断），监控侧再自行排序取 Top。

### T6 怎么用 trace 定位"慢"？
**结论：** 拉 Span 树看各节点 durationMs，找占比最大的；再下钻看是 LLM 慢、RAG 慢还是工具慢。
**本项目：** spanName 区分 `LLM:mimo-v2.5-pro` / `RAG.hybridRetrieval` / `RAG.llmRerank` / `ShopAgent.chat` 等，一眼定位瓶颈环节。

### T7 异步调用 traceId 怎么传递？
**结论：** 不靠 ThreadLocal 跨线程（会丢），显式把 traceId 当参数传给异步任务。
**本项目：** 编排是同步阻塞聚合，暂无跨线程；若引入 @Async/RagSyncListener 这类异步，需把 traceId 作为参数传入子线程再重建上下文。

### T8 Trace 和日志、指标（Metrics）的关系？
**结论：** 日志=事件详情，指标=聚合数值（Counter/Timer），Trace=单请求调用树；三者互补。
**本项目：** `AiMetricsConfig` 注册 12 个指标（agent/rag/tool/mcp/embedding/reranker/memory 计数 + Timer），`TokenCostTracker` 上报 token Counter，与 Trace 配合构成完整可观测性。

### T9 面试官追问：Trace 存 Redis 有 TTL，历史追踪怎么办？
**答法：** `agent:trace:{traceId}` TTL 1 小时，近 200 条；这是演示级保留策略。生产扩展：换 Kafka + OTel Collector 归档到 ES/ClickHouse，Trace 语义不变。

### T10 面试官追问：Trace 会不会拖慢主链路？
**答法：** 不会，三层保证：内存队列非阻塞 offer；@Scheduled 每 5 秒批量 flush；Redis 写失败只 warn 不影响主流程。观测永远在旁路，不在主路上。

## 4.3 SemanticCache（可缓存）

### C1 为什么需要语义缓存？KV 缓存不行吗？
**结论：** 自然语言几乎不会逐字重复，KV 缓存命中率趋近 0；语义缓存按"向量相似"命中同义改写。
**本项目：** "附近有啥好吃的" vs "推荐附近美食" 相似度约 0.95 命中，跳过整条 LLM 链路。

### C2 语义缓存怎么实现？（存储 + 查询）
**结论：** 复用向量库存"问题向量→回答"，相似度 ≥ 阈值命中。
**本项目：** `SemanticCache` 用 PgVector：`put()` 存 TextSegment（metadata 带 type/question/cachedAnswer/cachedAt），`get()` 用 `EmbeddingSearchRequest(maxResults=1, minScore=0.92)` Top-1 检索 + type 标记校验 + TTL。

### C3 阈值 0.92 怎么定的？降阈值行不行？
**结论：** 0.92 是保守超参；降阈值提命中但误命中风险升。
**本项目：** `@Value("${semantic-cache.threshold:0.92}")` 可配置；命中率 vs 准确率权衡用评测数据定。

### C4 怎么防止缓存串数据（个人化问题）？
**结论：** 白名单意图 + 个人化隔离：只缓存只读意图，强绑定用户的回答永不缓存。
**本项目：** `AgentOrchestrator.isCacheable()`（SHOP_QUERY/REVIEW_QUERY/GENERAL）+ `isPersonalQuestion()`（"我的订单/我的券"）双保险。

### C5 缓存过期怎么处理？
**结论：** TTL 校验 + 惰性删除：命中时发现过期视为未命中并删除。
**本项目：** `SemanticCache.get()` 里 `cachedAt + ttl < now` → `removeStale(embeddingId)`；TTL 默认 10 分钟（`semantic-cache.ttl-minutes:10`）。

### C6 缓存命中率不高怎么办？
**结论：** 降阈值 / 扩白名单 / 问题归一化。
**本项目：** `GET /ai/cache/stats` 看 hits/misses/total/hitRate（`SemanticCache.stats()`，**无相似度分布字段**）；相似度分布需从 Trace/日志聚合。调优方向：阈值、白名单意图、加轻量归一化。

### C7 缓存的内容会不会过期/错误（一致性）？
**结论：** 白名单 + 个人化隔离 + TTL + 事件驱动知识同步，四道防线；命中路径可观测。
**本项目：** `SemanticCache.lookup` 有 Trace span；数据变更走 `RagSyncListener` 从源头刷新知识。

### C8 缓存的是谁的回答？怎么写入？
**结论：** Agent 生成的回答，生成后回写。
**本项目：** `AgentOrchestrator.process()` 路由 Agent 得到 response 后，若可缓存则 `semanticCache.put(userMessage, response)`；写入失败只 warn 不影响主流程。

### C9 面试官追问：语义缓存命中，但两个用户画像不同，推荐结果不该一样怎么办？
**答法：** 诚实回答：这是语义缓存的固有局限。本项目缓存的是"非个人化问题"（画像差异影响小），且 `isPersonalQuestion()` 把"我的订单/我的券"等强绑定问题挡在缓存外。更细的用户维度缓存（按 profileId 分域）是扩展方向。

### C10 面试官追问：怎么证明缓存返回的不是错答案？
**答法：** 三层：意图白名单（只有只读意图进缓存）；TTL 惰性删除；回答本身是 Agent 链路的产物、关键回答上链可溯源（ChainNotary 存了 AGENT_DECISION），缓存命中也有 Trace span 可查。

## 4.4 ChainNotary（扩展能力，已移出简历主线）

### N1 为什么区块链专业的人做存证？不自建链吗？
**结论：** 复用密码学内核（哈希链 + Merkle + 签名），砍共识，定位轻量私有链，可平滑替换真链。（详见 2.4.1）

### N2 区块哈希怎么算？怎么防篡改？
**结论：** `SHA-256(prevHash|merkleRoot|height|timestamp|signature)`；改任一条 → 哈希链断裂 → 重算即发现。（详见 2.4.2）

### N3 Merkle 树价值？不用行不行？
**结论：** 批量打包一个根上链、单条 O(log n) 证明验证。（详见 2.4.3）

### N4 HMAC 和哈希链各自职责？
**结论：** 哈希链保完整性、HMAC 保真实性。（详见 2.4.4）

### N5 存证时机和内容怎么设计？
**结论：** 业务生效后存关键字段，幂等去重，失败不影响主流程。（详见 2.4.5）

### N6 怎么保证并发出块唯一？
**结论：** Redisson 分布式锁 + 失败回滚缓冲。
**本项目：** `sealBlock()` `tryLock(0, 3s)`，拿不到锁直接 return（定时任务兜底）；失败把快照放回 pending。

### N7 单条记录怎么独立验证？
**结论：** `verifyByRecordId()` 六重校验（内容哈希→Merkle 根→证明→区块哈希→签名→链衔接）。（详见 2.4.7）

### N8 存证存 Redis 会不会丢？
**结论：** Redis 持久化是演示级；生产应迁 PG 双写或接真链 SDK。（详见 2.4.8）

### N9 面试官追问：HMAC 是对称的，怎么做到"公开可验证"？
**答法：** 诚实 + 可扩展：当前演示用对称密钥（HMAC-SHA256），只有持有密钥的服务端能出块，属于"服务端自证"。要做公开可验证就换 RSA/SM2 非对称签名（私钥出块、公钥验证），存证语义不变。这也是对接真实链（FISCO BCOS 用 SM2）的路径。

### N10 面试官追问：Redis 被改/被删怎么办？存证防的是谁？
**答法：** 防的是"业务数据被偷偷改"（内容哈希比对暴露），以及"出块方不可信"（签名校验）。Redis 本身是存储，真攻击存储层是另一维度问题，生产靠：多副本、PG 落库、真链锚定（把 merkleRoot 定期锚到公链/联盟链）。当前是工程化演示，密码学正确性经独立测试验证。

# 第五部分 秒杀与可靠性专项

### S1 Lua 脚本原子性原理再讲透
**结论：** Redis 单线程执行命令，eval 一个 Lua 脚本期间不会被其他命令插入，所以脚本内多步操作原子。（见 2.5.2）

### S2 seckill.lua 每一步在干嘛？返回值怎么设计？
**本项目：** 参数 `voucherId, userId`；key `seckill:stock:{voucherId}`、`seckill:order:{voucherId}`；逻辑：
1. `EXISTS stockKey == 0` → return 4（活动不存在/未预热）。
2. `tonumber(GET stockKey) <= 0` → return 1（库存不足）。
3. `SISMEMBER orderKey userId == 1` → return 2（重复下单）。
4. `INCRBY stockKey -1`（扣库存）+ `SADD orderKey userId`（记用户）→ return 0。
Java 端 `seckillVoucher()` 按返回值 switch 给用户不同提示。

### S3 为什么需要时间窗口校验？放哪一层？
**结论：** 挡无效流量，避免活动未开始就打到 Redis/DB。
**本项目：** `seckillVoucher()` 第一步查 `SeckillVoucher` 校验 `now ∈ [beginTime, endTime]`，未开始/已结束直接返回失败。

### S4 乐观锁为什么用 `WHERE stock > 0` 而不是版本号？
**结论：** `stock > 0` 是"条件更新"型乐观锁，直接表达业务约束（有货才扣），比版本号少一次查询。
**本项目：** `update().setSql("stock = stock - 1").eq("voucher_id", voucherId).gt("stock", 0)`，0 行影响抛异常回滚（连订单插入一起撤销）。

### S5 为什么"先插订单，后扣库存"？顺序能换吗？
**结论：** 先插订单用唯一索引挡重复，扣库存失败回滚时订单也撤销；顺序换来：先扣库存再插订单，重复下单也会扣两次库存再回滚，逻辑上也能自洽但浪费。
**本项目：** `createVoucherOrder()`：先 `save(voucherOrder)`（DuplicateKeyException 幂等返回），再扣库存，再存证。

### S6 事务里扣库存 0 行怎么触发回滚？
**本项目：** 扣库存 `success == false` → `throw new IllegalStateException("库存不足，订单已回滚")`；RuntimeException 触发 @Transactional 回滚，订单插入一并撤销。

### S7 Direct Exchange 为什么适合秒杀？Topic/Fanout 不行吗？
**结论：** 秒杀订单一对一精确投递，Direct 按 routing key 精确匹配，无通配匹配/广播开销。
**本项目：** `order.direct` + routing key `seckill.order`。

### S8 死信队列 + x-death 计数怎么配合有限重试？
**本项目：** `OrderMessageListener.getRetryCount()` 读 `x-death` 头的 count，`attempt = retry + 1`；`attempt >= 3` → `basicNack(false, false)` 进 DLX；否则 `basicNack(false, true)` 重入队（RabbitMQ 累加 x-death）。

### S9 死信补偿会不会造成库存多扣/少扣？
**本项目：** `DlxOrderListener` 先判 `getById(orderId) != null`：订单已落库（库存已正常消耗）→ 不回滚；未落库 → `INCR` 恢复库存 + `SREM` 移除下单记录。这样库存与订单守恒，不会重复回滚。

### S10 发布确认 + Returns 回调补全了什么？
**本项目：** Confirm 知道"交换机收没收到"（nack 记录失败），Returns 知道"路由没到队列"（recordFailure），失败统一写 `seckill:pub:failures`（保留 500 条）供补偿重发。（见 2.5.7）

### S11 压测 350ms→130ms 具体怎么测？有什么坑？
**结论：** JMeter 并发线程组压 `/seckill` 接口，分别测同步旧版和异步新版，统计 P99。
**坑：** P99 受线程数/QPS 配置影响；要诚实说明压测环境（本地/单机）与生产差异。（详见 8.7）

### S12 如果 Redis 挂了怎么办？
**结论：** 秒杀入口直接不可用（快速失败），DB 侧还有乐观锁兜底但无法削峰。
**本项目：** Lua 返回 4（活动不存在）或 execute 异常 → 返回"系统繁忙"。生产可加 Redis 哨兵/集群 + 降级为 DB 直接扣减（牺牲性能保正确）。

### S13 如果 MQ 挂了怎么办？
**结论：** Lua 扣了库存但消息发不出去 = Redis 库存与 DB 不一致，靠死信/补偿收口。
**本项目：** Confirm 回调记录 `seckill:pub:failures`，可定时补偿重发；极端情况用户可重试（Lua 的 SISMEMBER 会拦住重复下单，需要补偿脚本释放）。

### S14 面试官追问：为什么不用 RocketMQ/Kafka？
**答法：** 秒杀场景 RabbitMQ 足够（吞吐、延迟都满足），且有死信、手动 ACK 等成熟语义；技术栈已有 RabbitMQ，避免引入新组件。RocketMQ 的事务消息/延时消息在有强一致诉求时可考虑。

- 削峰：RabbitMQ 异步，消费者按需扩实例。
- DB 兜底：乐观锁 + 唯一索引，物理正确性靠数据库。
- AI 部分：30% 请求走规则引擎天然可水平扩展；LLM 调用是外部瓶颈，ModelRouter 多模型分摊。
- 关键话术："秒杀瓶颈从来不是 Redis 而是 DB 写，我用 Lua + MQ + 乐观锁把 DB 写压到最少；AI 瓶颈是 LLM，规则引擎 + 语义缓存 + 多模型分摊。"

### 陷阱 5："分布式事务怎么处理？你秒杀里 Redis 和 DB 怎么保证一致？"
**答法（诚实 + 设计）：**
- 不用强一致分布式事务（2PC/Seata），用**最终一致 + 补偿**。
- 语义：Redis 预扣是"乐观预扣"，DB 是"最终扣减"；中间不一致是允许的（秒杀用户看到"成功"但订单异步创建）。
- 兜底：死信补偿回滚 Redis（库存守恒）、发布确认失败记录重发、Lua 限购防重复。
- 关键话术："秒杀的正确性锚点在数据库（乐观锁 + 唯一索引），Redis 只是性能闸；Redis 和 DB 的短暂不一致用死信补偿收口，这是最终一致的经典做法。"

### 陷阱 6："AI 回答错了怎么办？幻觉怎么处理？"
**答法：** 四层防线：RAG 约束事实来源（SystemMessage 要求只基于检索结果）；工具调用替代生成（事实从 @Tool 来，LLM 只组织语言）；SystemMessage 约束不编造；输出后校验（可选）。加上评测系统（AgentEval 的准确性维度 + LLM 裁判）量化幻觉，ChainNotary 存证可溯源。（见原 Q14 扩展）

**答法：** 诚实：是个人学习/项目作品，但按生产系统标准设计。区分"我独立完成"和"我借鉴了哪些最佳实践"；主动讲清楚每个模块的取舍和局限（知道哪里不完美 + 怎么改），比假装团队项目更可信。

### 陷阱 9："简单聊聊你的技术选型为什么用这么多中间件？不重吗？"

2. **Q：** 测试集多大？覆盖哪些？ → **A：** 8 条，5 类意图 + 边界 case；种子集，扩展方向百级。

4. **Q：** 改 Prompt 后 89% 掉到 85% 怎么定位哪类错了？ → **A：** 看 `caseResults` 逐条 + 混淆矩阵，针对误判对修 Prompt。
5. **Q：** 怎么防止评测集作弊（过拟合测试集）？ → **A：** 黄金集隔离 + 第三方交叉验证 + 结果上链审计 + 看分布不看单点。

### 链 2：从"为什么不超卖"开炮
1. **Q：** 秒杀怎么防超卖？ → **A：** Lua 原子扣减 + DB 乐观锁双层。
2. **Q：** Lua 为什么原子？ → **A：** Redis 单线程执行脚本，期间无其他命令插入。
3. **Q：** Redis 扣了 DB 扣不到怎么办？ → **A：** DB 乐观锁是最终闸，扣不到就抛异常回滚；消息失败进死信补偿回滚 Redis。
4. **Q：** 死信补偿会不会多扣/少扣？ → **A：** `DlxOrderListener` 先判订单是否落库，落库不回滚、未落库才恢复库存，守恒。
5. **Q：** 用户重复提交怎么办？ → **A：** Lua SISMEMBER 限购 + DB 唯一索引 `uk_user_voucher` 幂等，双保险。

### 链 3：从"为什么迁 PgVector"开炮
1. **Q：** 为什么迁？ → **A：** Redis 不支持 metadata filter，跨店铺串扰率 15%。
2. **Q：** 串扰率怎么测的？ → **A：** 构造跨店查询测试集，统计返回了非目标店铺内容的比例（见 8.3）。
3. **Q：** PgVector 检索比 Redis 慢吗？ → **A：** HNSW 索引近似最近邻，数据量几千条性能足够；且换取的是正确性。
4. **Q：** 混合检索怎么融合？ → **A：** RRF，k=60，看排名不看分数。
5. **Q：** 为什么还要 LLM Reranker？ → **A：** RRF 只看排名，LLM 精排看相关性语义，Top-5 更准；代价是延迟，候选超过 TopK 才触发。

### 链 4：从"成本怎么降 50%"开炮
1. **Q：** 50% 怎么算的？ → **A：** 优化前后 token 总量 + 单价估算，AgentTrace 成本归因支撑。
2. **Q：** 具体降在哪？ → **A：** 规则引擎挡 30% 请求零 token、记忆窗口控上下文、RAG 截断、工具描述精简。
3. **Q：** 规则引擎挡 30% 的依据？ → **A：** AgentTrace 按 intent/span 聚合，签到/余额/我的订单等高频请求走规则。
4. **Q：** 限流参数 10000/min 怎么定的？ → **A：** 模型上下文 + 成本模型 + 用户体验三方平衡（见 8.4）。
5. **Q：** 语义缓存省了多少？ → **A：** 命中请求延迟降到毫秒级、跳过整条 LLM 链路；命中率用 `GET /ai/cache/stats` 观测。

### 链 5：从"存证有什么用"开炮
1. **Q：** 为什么做存证？ → **A：** 区块链专业落地 + AI 内容可信溯源需求。
2. **Q：** 存了什么？ → **A：** 秒杀订单（SECKILL_ORDER）、AI 决策/回答（AGENT_DECISION）、评测报告（EVAL_REPORT）。
3. **Q：** 怎么防篡改？ → **A：** 内容哈希 + Merkle + 区块哈希链，改一条全断。
4. **Q：** 别人也能验证吗？ → **A：** `GET /ai/notary/verify/{recordId}` 六重校验，纯本地重算。
5. **Q：** 和真区块链什么关系？ → **A：** 密码学内核一致，砍共识；可替换 FISCO BCOS SDK，存证语义不变。

## 8.2 检索命中率 77% → 89%

- **怎么来的：** 用 `runRagEval()` 评测（`RAG_SEED_CASES` 10 条，期望片段取真实种子店铺名），对同一批问题统计两组口径：77% 为**纯向量 Top-1 命中率**（`retrieveVectorOnly`，优化前基线），89% 为**混合检索 Top-5 命中率**（`HybridContentRetriever.retrieve` 向量+PG全文+RRF 融合后取前 5，优化后）。触发 `POST /ai/eval/rag` 一键复现。
- **口径：** "命中"= 期望店铺/内容片段出现在返回结果中（Top-1 命中 ≈ 精确检索，Top-5 命中 ≈ 近似 Recall@K）。为什么 Top-1 当基线：纯向量只取最相似 1 条，容易漏；混合检索融合全文精确匹配后正确店铺进 Top-5 概率显著上升——两组数字量化的是融合策略带来的召回提升，不是同一个 Metric 的两种结果。
- **追问怎么答：** "我有 `POST /ai/eval/rag` 评测接口：`RAG_SEED_CASES` 10 条真实店铺问题，统计纯向量 Top-1 命中率 ≈77% 和混合 Top-5 命中率 ≈89%，同一套测试集随时可复现。趋势可信（混合 > 纯向量），绝对值受评测集分布影响，量产方向是扩充评测集到百级并做 Recall@K 回归。"

## 8.3 跨店铺串扰率 15%

- **怎么来的：** 迁移前用"查 A 店但看结果是否混入 B 店"的测试查询统计，约 15% 的结果串了店。
- **依据：** RedisEmbeddingStore 在 LangChain4j 0.35 不支持 metadata filter，只能检索后过滤。
- **追问怎么答：** "15% 是一个抽样统计：我构造了一批跨店查询，数返回结果里混入非目标店铺 chunk 的比例。迁到 PgVector 后通过 `ShopAwareContentRetriever` 的 shopId filter 从存储层隔离，串扰归零。"

## 8.4 AI 成本降低 50%

- **怎么来的：** 优化前后各时段 Token 总量 + 单价估算（`TokenCostTracker.estimateCost()`，$0.15/1M input、$0.60/1M output）；约 900 万 Token/天 → 350 万 Token/天。
- **依据：** 策略叠加：规则引擎挡 30% 请求、记忆窗口 20 条、RAG 截断 300 字、工具描述精简。每个决策有 `TraceRecorder.costAttribution()` 的 span 聚合支撑（如某工具 token 重复计算占 7%）。
- **追问怎么答：** "50% 是估算口径，用 trace 数据归因：按 intent/spanName 聚合 token，对比优化前后。如果你要精确到金额，我需要接计费方接口，当前是估算。"
- **验证操作（面试被要求"证明"时照此说）：**
  1. **前置**：有真实 LLM 调用（跑几次 AI 对话，覆盖规则查询 + Agent 对话两类）。
  2. **操作**：查成本归因接口——`TraceRecorder.costAttribution()` 对应 `GET /ai/trace/cost`（或按 `GET /ai/trace/{traceId}` 看单次请求的 span token）。
  3. **输出**：按 `spanName` 聚合的 `{calls, inputTokens, outputTokens, totalMs, failures}`；规则引擎拦截的请求 token=0、语义缓存命中的请求无 LLM span。
  4. **解释**："成本 = token × 单价（`estimateCost()`）。我在 trace 里能清楚看到：哪类请求被规则引擎挡了（零 token）、哪类命中了语义缓存（跳过 LLM）、哪类用了轻量模型——三块加起来就是 50% 的降幅，每一块都有 span 数据可查。"

## 8.5 Token 限流 10000/分钟（用户级）、1000 万/天（全局）

- **怎么来的：** `TokenCostTracker.MAX_TOKENS_PER_USER_PER_MINUTE = 10000`、`MAX_TOKENS_PER_DAY = 10000000`。
- **依据：** 模型上下文（MiMo v2.5-pro 约 128K）+ 成本模型（10000 token ≈ $0.0015）+ 用户体验（正常对话 500-2000 token/分钟）+ 防滥用。
- **追问怎么答：** "这是按模型能力和成本模型算出来的保守值，正常用户给足余量、脚本刷量能拦住。生产会按用户分层差异化（免费/付费）。"

## 8.6 评价、秒杀订单、AI 回答三类数据上链

- **怎么来的：** 代码里 `notarize()` 有四个接线点，简历的"三类数据上链"（评价 / 秒杀订单 / AI 回答）**全部直接落库上链**：
  - `service/impl/VoucherOrderServiceImpl.java`（createVoucherOrder 落库后）→ `SECKILL_ORDER`（秒杀订单）
  - `ai/agent/AgentOrchestrator.java`（生成回答后）→ `AGENT_DECISION`（AI 决策/回答，含 traceId/userId/intent/input/output）
  - `service/impl/BlogServiceImpl.java`（saveBlog 落库后）→ `REVIEW`（评价，SHA-256 指纹 + 签名，正文截断 200 字只存摘要）
  - `eval/AgentEvalService.java`（评测报告生成后）→ `EVAL_REPORT`（评测结果，防"数字被偷偷改"）
- **注意（诚实点）：** 评价存证只存摘要指纹（`truncateContent(..., 200)`）不存全文，因为存证是"防篡改 + 可验证"不是"数据备份"；秒杀/AI 回答同理。
- **追问怎么答：** 直接背代码位置：评价在 `BlogServiceImpl.saveBlog` 第 6 步 `notaryService.notarize("REVIEW", {...})`；三类数据 + 评测报告共四个触发点，eventType 区分（SECKILL_ORDER / AGENT_DECISION / REVIEW / EVAL_REPORT）。

## 8.7 平均响应时间 350ms → 130ms

- **怎么来的：** JMeter 压测同步下单 vs 异步下单；P99 从 350ms 降到 130ms。

- **追问怎么答：** "350ms 是同步写库的 P99，130ms 是 Lua 预扣 + 异步下单的 P99。压测环境是本地单机，生产要看真实流量再校准。消息可靠性靠本地消息表 + 对账 + 死信补偿从机制上保证，不靠'丢失率'这类无法验证的绝对数字。"

  3. **输出**：聚合报告——平均响应时间、P99、吞吐量、错误率。
  4. **解释**："报告里异步下单的 P99 就是 130ms；把落库从同步链路摘掉之前（同步写库）是 350ms。压测脚本和完整复现步骤都在 `jmeter/压测说明.md`，任何人照做能复现。"

## 附录2 · MCP 协议集成（旧简历内容，已移出工作内容，保留技能标签）

> 移出原因：MCP 作为"对外开放协议"不直接服务于业务闭环，降级为技能标签（`RAG、Agent、MCP`）；实现完整保留在 `02` 附录B（8 章）。

### A2.1 MCP 是什么（原 Q3.8.1）
**结论：** Model Context Protocol，Anthropic 提出，AI 与外部工具/数据的开放协议，类比"AI 工具的 USB 接口"。传输：SSE（远程）或 stdio（本地）。
**本项目：** `McpServer` 基于 SSE + JSON-RPC 2.0 暴露 24 个工具，兼容 Claude Desktop/Cursor。

### A2.2 为什么不直接用 @Tool，还要 MCP（原 Q3.8.2）
**结论：** @Tool 是应用内 Function Calling（编译期绑定、应用内消费），MCP 是跨应用标准协议（运行时发现、外部客户端消费）；本项目 MCP Server 复用 @Tool 注解，一份定义双重消费。
**本项目：** `McpServer.registerTools()` 反射扫描 @Tool + @P 生成 JSON Schema；`McpController.init()` @PostConstruct 注册 24 工具 + 3 资源（shop://list、shop://{id}、review://recent）+ 3 Prompt（shop-summary、shop-recommend、review-draft）。

### A2.3 MCP 调用流程（原 Q3.8.3）
**本项目：** `GET /mcp/sse` 建连（先发 endpoint 事件 `/mcp/messages?sessionId=...`）→ 客户端 POST `/mcp/messages` 发 JSON-RPC：initialize → notifications/initialized → tools/list → tools/call。`handleRequest()` 里 switch 分发各方法。

### A2.4 MCP Server 怎么动态发现/容错（原 Q3.8.4）
**本项目：** `McpClient.connectWithRetry()` 线性退避（2s*attempt）重连；`callToolWithFallback()` 远程失败降级本地同名工具；`McpHealthMonitor` 30s 心跳 + 60s 清理 300s 无活动连接。

### A2.5 MCP 安全（原 Q3.8.5）
**本项目：** 认证靠外层（Nginx Basic Auth/Token）；MCP 工具由 `McpServer` 反射暴露、**不走 AiServices 的 ToolProvider**，故 `ToolSecurityInterceptor` 的限流/审计不覆盖 MCP 路径（MCP 安全靠外层认证 + 工具内参数校验）；Resource 只暴露公开信息。诚实点：若需对 MCP 也限流，需在 `McpServer.handleRequest` 加同样的 INCR 计数。

# 第九部分 简历每点的深层思考（为什么 / 反面代价 / 追两层）

> **定位：** 这是"面试深挖"的最后防线。面试官顺着你的回答一路往下追，这里给你三层兜底：① 为什么这么做（设计动机）② 不这么做会有什么问题（反面代价）③ 再追两层的问题与答案。目标：让面试官追到第 4~5 层，你还有话说，且每层都能自圆其说。

## 9.1 跨系统数据一致性（本地消息表 + 对账 + 补偿）

### 为什么这么做
1. 下单链路跨 Redis / MQ / MySQL 三个系统，三者之间**没有分布式事务**——任一环节失败都会造成"Redis 扣了库存、DB 却没订单"的中间态（库存泄漏）。
2. 需要一份**持久化的凭据**跟踪消息投递状态，本地消息表就是"业务数据之外的第二本账"：消息发没发、订单建没建，都有据可查、可对账、可补偿。

### 不这么做会有什么问题
1. **不用本地消息表** → MQ 投递失败完全无感知，Redis 已经扣了库存、订单永远建不起来，库存永久被"锁死"，且没有任何记录能定位到是哪笔订单丢了。
2. **投递失败直接同步回滚**（不用对账） → confirm nack 时无法区分"消息没送达"和"消息已送达但确认回执丢了"，盲目回滚库存会在"消息其实送达了"时造成超卖。
3. **补偿顺序反了**（先回滚库存、再查订单） → 订单实际已落库却把库存加回去 = 多卖一件。

### 面试官再追两层
#### 第一层：对账的频率和批量怎么定？对账自己会不会漏？
**答：** 5 秒一轮、单轮批量 100，平衡"收敛速度"和"DB 扫描压力"。漏不掉——本地消息表是 MySQL 持久化的，对账任务挂了只是"收敛延迟"，重启后扫描 `status=PENDING AND next_retry_time <= now` 的记录继续处理，之前积压的 PENDING 一条都不会丢。

#### 第二层：补偿判定和消费者落库是并发的，这个竞态窗口怎么保证不超卖？
**答：** 这是最终一致方案**固有的一致性窗口**，诚实承认它存在。缓解手段（按性价比）：① 调大重投次数 + 指数退避上限，让补偿发生在"消息几乎不可能仍存活"之后；② 消费端落库前先读一次消息状态，已是 COMPENSATED 则跳过；③ 离线对账兜底（比对订单表 vs 消息表，对"已补偿但订单存在"的记录做反向扣减）。核心态度是：把窗口压到业务可接受范围，而不是假装它不存在。

## 9.2 高并发交易的库存一致性（Lua + CAS + 幂等）

### 为什么这么做
1. "读-判-写"三段之间有时间差，并发请求会穿插，Lua 把三段压进**单次 EVAL**，Redis 单线程顺序执行，把时间差压到 0。
2. Redis 是**前置拦截、加速层**，不是真相源——DB 的乐观锁 + 唯一索引才是最终防线，保证 Redis 挂了/被绕过也不产生脏数据。

### 不这么做会有什么问题
1. **不用 Lua**（Java 侧先查后扣）→ 两个请求同时 `GET stock=1`，都判断 >0，都扣减，stock 变 -1，超卖。
2. **只靠 Redis、不靠 DB 兜底** → Redis 宕机或 key 被清，限购/库存约束全部失效，直接产生重复下单和超卖。
3. **用分布式锁代替 Lua** → 锁有粒度、超时、死锁风险，吞吐远低于无锁的 Lua + 乐观锁方案。

### 面试官再追两层
#### 第一层：Redis 和 DB 的库存最终一致，窗口期不一致怎么办？
**答：** 异步削峰的必然代价就是牺牲强一致。态度是：Redis 允许短暂不准（它是快速拦截的近似值），DB 必须最终准（它是真相源）。异常路径（死信补偿、超时关单、对账）都会把 Redis 拉回和 DB 一致。

#### 第二层：时间窗口为什么下沉到 Lua？原来在 Java 侧查 DB 有什么问题？
**答：** 原来每个秒杀请求都要 `getById` 查一次 DB 校验活动起止时间，高并发下这一步直接把 DB 打满，和"减轻 DB 压力"的目标自相矛盾。下沉到 Lua 后，时间窗口和库存、限购在同一个脚本里校验，秒杀请求路径**零 DB 查询**。代价是活动创建时要预热时间窗口到 Redis，且启动要补偿预热（防 Redis 重启丢 key）。

## 9.3 异步解耦与消息可靠消费（MQ + 毒消息修复）

### 为什么这么做
1. 同步落库把"写库"这个最慢的操作放在请求线程里，DB 连接池（默认 10）被打满，请求排队等连接 → 响应时间飙升。异步把写库移到消费者线程，接口只做 Redis 预扣 + 投递。
2. 消息丢失点有三个（生产者发丢 / broker 丢 / 消费者处理中丢），每个点都要有对应的可靠性机制，否则"异步化"就变成"丢单"。

### 不这么做会有什么问题
1. **不异步** → 高并发下 DB 连接池满载，P99 从 130ms 恶化到 350ms，接口直接被打崩。
2. **毒消息不修复** → 必然失败的消息无限 requeue 热循环，消费者 CPU 打满但永远不 ack，队列深度飙升，死信队列形同虚设——单条毒消息就能拖垮整个消费链路。
3. **业务拒绝和系统异常不分流** → 库存耗尽这种"重试多少次都不会成功"的消息，白白占着重试配额，加剧堆积。

### 面试官再追两层
#### 第一层：为什么重试计数不能靠 x-death 头？它到底在什么场景才写？
**答：** `x-death` 是消息被**投递到死信交换机（dead-letter）**时才写入的元数据。而 `basicNack(requeue=true)` 只是把消息放回原队列队尾，不产生 x-death。所以读 x-death 判断重试次数，`requeue=true` 场景下计数恒为 0，重试次数永远达不到上限。改用 Redis 独立计数（INCR + TTL）后，重投次数才真实累加。

#### 第二层：死信队列的补偿如果也失败了怎么办？会不会无限循环？
**答：** 死信是最后一道防线，它自己**不能再失败重投**，否则死信队列无限堆积。所以 `DlxOrderListener` 无论成功失败都 `basicAck`，补偿结果写 Redis LIST（`seckill:dlx:records`）供人工重放。这是"机器兜底 + 人工兜底"的分层——机器能自动收敛的自动收敛，自动收敛不了的留人工审计，绝不进入无限循环。

## 9.4 全链路追踪与可观测性（traceId + 成本归因）

### 为什么这么做
1. 交易链路跨 Redis / MQ / DB / 模型，出问题时没有 traceId，只能靠时间戳人肉关联日志，定位效率极低。
2. 成本优化要有数据支撑，不能拍脑袋——trace 里每个 span 记录了 token 和耗时，聚合出来才知道"钱花在哪"。

### 不这么做会有什么问题
1. **不打 traceId** → 一次下单涉及十几条日志，分散在不同组件里，线上问题定位靠猜，半天找不到根因。
2. **不做成本归因** → "成本降 50%"是拍脑袋的数字，面试官一句"怎么算的"就崩；有归因，每个优化决策（配轻量模型、加缓存）都有 span 数据支撑。

### 面试官再追两层
#### 第一层：traceId 跨线程 / 跨 MQ 怎么传递？ThreadLocal 会泄漏吗？
**答：** 同线程靠 ThreadLocal 传递；跨线程（@Async/线程池）和跨 MQ（消费者线程）必须**显式透传**——把 traceId 塞进消息体或 header，消费者取出后再 set 回 ThreadLocal。泄漏风险在"线程池复用 + 不清理"：所以 `TraceIdFilter` 的 finally 里强制 `endTrace()` + `MDC.remove()`，线程归还线程池前清干净，既防泄漏也防 traceId 串到下一个请求。

#### 第二层：自研追踪和 SkyWalking / OpenTelemetry 比，边界在哪？为什么不直接用开源的？
**答：** 自研的优势：① 无 agent 依赖，理解成本低、可控；② **成本归因（token 成本）是业务语义**，开源 trace 不直接给；③ 面试能讲清原理。劣势：跨进程传播弱、没有现成可视化。边界很清楚——单体 + 同步为主的场景自研够用，一旦拆成多服务就该上 OpenTelemetry + Jaeger。这是"按需选型"，不是"重复造轮子"。

## 9.5 AI 能力工程化与治理（Agent 编排 + 评测 + 治理）

### 为什么这么做
1. 单 Agent 把几十个工具塞一起，工具冲突 + Prompt 膨胀让准确率崩；拆成专业子 Agent，每个只挂自己领域 5-8 个工具，选择范围缩小。
2. LLM 是不可靠外部依赖（会幻觉、超时、超预算），要像治理数据库/缓存一样治理它——评测、限流、降级、缓存、可观测。

### 不这么做会有什么问题
1. **不拆 Agent** → 27 个工具塞给一个模型，语义相近的工具混选，准确率崩到 72%，且 Prompt 大量 Token 耗在工具描述上。
2. **不做评测** → "准确率 89%"是口头宣称，面试官一句"怎么测的"就崩；有 LLM-as-Judge + 标注测试集，每次改 prompt 可一键回归。
3. **不做治理** → 模型故障无降级（用户卡死）、成本失控（反复调大模型）、重复请求重复调 LLM（浪费）。

### 面试官再追两层
#### 第一层：LLM-as-Judge 有什么偏差？怎么缓解？
**答：** 位置偏差、偏好偏差（偏长答案）、自我增强偏差、一致性差。缓解：固定结构化 rubric（输出 JSON score + reason）、多次打分取均值、锚点样例校准。核心认知：评测的价值是"相对比较"（优化前 vs 优化后），不是绝对分。

#### 第二层：Agent 意图识别失败怎么办？降级链路是什么？
**答：** 三级降级：① 意图识别置信度低或失败 → 不硬路由，回退通用助手 `CustomerAssistant`（全量工具 + RAG 兜底）；② 专业 Agent 调用失败 → 同样回退通用助手；③ 主模型失败 → `ModelRouter` 切换备用模型；④ 所有模型失败 → 明确返回"服务繁忙"。核心原则：宁可回答得泛一点，也不回答错（把订单问题路由到评价 Agent 去）。
