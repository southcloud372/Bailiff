**本轮秒杀链路硬伤修复清单**（对应旧版"P0 修复"）：

| 硬伤（旧版诊断） | 修复实现 |
|------|----------|
| 消费失败恒 nack，死信队列收不到消息 | `OrderMessageListener` 改为 Redis 计数重试 + `SeckillRejectException` 异常分流，业务拒绝直转死信 |
| 重试计数靠 x-death（requeue 不写，恒为 0） | 改为 Redis INCR + TTL（`SECKILL_RETRY_KEY`） |
| 无 @Transactional | `createVoucherOrder` 加 `@Transactional`（落单 + 扣库存 + 收敛消息表同事务） |
| 无唯一索引 | `db/hmdp.sql` `uk_user_voucher(user_id,voucher_id)` |
| 时间窗口未校验 | 下沉至 `seckill.lua`（HGET activity:begin/end）+ `SeckillActivityCacheWarmer` 预热 |
| Lua 对不存在的 key 抛异常 | `seckill.lua` 先 `EXISTS` 返回"活动不存在" |
| 发布确认未注册回调 | `RabbitMQPublisherCallback` 注册 confirm/returns |

**本轮新增工程能力**（支撑简历 5 条）：

| 能力 | 实现 |
|------|------|

| traceId 交易链路埋点 | `TraceIdFilter`（MDC）+ `TraceContext.bindTraceId` |

## 8. 诚信披露清单（面试前必背——数字别说过头）

| 数字 | 真实程度 | 该怎么说 |
|------|----------|----------|
| 350ms→130ms | JMeter 脚本可复现（`jmeter/seckill-load-test.jmx`，50 线程），但需 Redis+PG+RabbitMQ 环境 | 「50 并发压测，RT 从 350 降到 130，压测报告在 jmeter 目录」 |
| 72%→89%（工具调用准确率） | AgentEval 评测可运行（标注测试集 + LLM-as-Judge）；机制是工具分化（单 Agent 27 工具 → 多 Agent 各 5-8 工具） | 「标注测试集跑意图评测，从 72 提到 89；测试集是 8 条种子用例（店铺/下单/评价/闲聊多意图），多轮跑批取均值——LLM 意图识别有随机性，单轮 8 条只能取 0/12.5%/…/100，多轮累加才得到 72/89 这样的百分比」 |
| 成本降 50% | 机制真实（规则引擎拦截 + 语义缓存 + 多模型路由），50% 为估算口径 | 「由规则引擎分流 + 语义缓存 + 轻量模型三部分构成，估算约 50%，核心是把确定性请求拦在 LLM 之外」 |
| 三级防线 / 三阶段 / 四类组件 | 结构量化，真实设计 | 如实讲（结构数量，非性能数据） |

> ⚠️ **红线**：不写"支撑 XX 万用户 / 峰值 XX 万 QPS / 超卖为 0"这类无法验证的规模数据或绝对结论——面试一句"你压测多少并发、怎么证明超卖是 0"就问穿。
