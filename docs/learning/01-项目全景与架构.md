# 01 · 项目全景与架构

读完这篇你应该能：用三句话向别人介绍这个项目；画出一次请求从 HTTP 到模型再回来的完整路径；
说清七层架构每一层「不做会怎样」。

---

## 1. 它解决什么问题

市面上的 Agent 项目大致分两类：

**第一类：Demo。** 一个 `main.py`，`ChatOpenAI` + 三个 `@tool` 函数 + `while` 循环。
能演示，但回答不了这些问题：

- 用户 A 能让 Agent 读用户 B 的文件吗？
- 模型要删库，谁拦？
- 服务重启，正在等审批的工单还在吗？
- 两个副本，限流是按 100/秒还是 200/秒？
- 这个月 token 花了多少钱，哪个用户花最多？
- 换了模型，回答质量掉了多少？

**第二类：平台。** 这个项目要做的，是把上面每个问题都变成一段可指认的代码。
它的价值不在于「有几个 Agent」，而在于**每一层都有明确的失败模型和兜底**。

> 一句话定位：**证明你能做生产级 Agent 工程，而不是调 API 的 demo。**

面向的场景是「企业知识助手 + 工单编排」：
员工问制度 → RAG 检索回答；员工说「把这批数据导出去」→ 进入工单工作流 →
识别为敏感操作 → 暂停等主管审批 → 批准后执行 → 全程审计。

## 2. 七层架构，逐层落到目录

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层  api/          FastAPI 路由 · SSE · request-id · 探针  │
├──────────────────────────────────────────────────────────────┤
│ 编排层  core/         create_agent(自主) · StateGraph(确定性) │
│                       checkpoint(三级) · interrupt(HITL)      │
├──────────────────────────────────────────────────────────────┤
│ 治理层  gateway/      鉴权 · 权限 · 限流 · 审计 · 护栏 · 沙箱  │
├──────────────────────────────────────────────────────────────┤
│ 协议层  gateway/mcp_client.py   动态发现 · 命名空间 · 容错    │
├──────────────────────────────────────────────────────────────┤
│ 模型层  router/       路由 · 成本 · 预算 · 重试熔断 · 语义缓存 │
├──────────────────────────────────────────────────────────────┤
│ 记忆层  memory/      长期记忆(向量) · 分域                     │
├──────────────────────────────────────────────────────────────┤
│ 数据层  knowledge/   PostgreSQL+pgvector(HNSW) · Redis · SQLite│
└──────────────────────────────────────────────────────────────┘
        横切：observability/(指标/trace/探针) · evaluation/(评测)
```

| 层 | 目录 | 一句话职责 | 不做会怎样 |
|---|---|---|---|
| 接入 | `api/` | 把能力暴露成 HTTP/SSE，串联 request-id | 无法被前端/其他服务调用 |
| 编排 | `core/` | 决定「下一步做什么」，并让状态可暂停可恢复 | 只能一问一答，敏感操作无法人工介入 |
| 治理 | `gateway/` | 工具调用的唯一入口，四件套按序执行 | Agent 等于拿到服务器 shell |
| 协议 | `gateway/mcp_client.py` | 把外部工具按标准接进来 | 每接一个工具写一次适配代码 |
| 模型 | `router/` | 选模型、算钱、限额、失败退避 | 单一供应商挂掉就全站不可用；账单不可控 |
| 记忆 | `memory/` | 跨会话记住用户 | 每次都要用户重复背景 |
| 数据 | `knowledge/` | 向量与业务数据 | 无法回答「公司自己的知识」 |

**横切关注点**之所以单独拿出来，是因为它们不属于任何一层，但每层都要用：
`observability/` 提供指标/trace/探针，`evaluation/` 提供质量门禁，`guardrails/` 提供安全边界。

## 3. 一次 `/v1/chat` 请求的完整路径

这是最该背下来的一段。面试时说清这条链路，等于展示了你对系统的整体掌握。

```
1. ASGI 中间件 (api/middleware.py)
   ├─ 取/生成 x-request-id，写入 contextvar
   ├─ 记录开始时间
   └─ 包一层 send，在响应头回显 x-request-id
        ↓
2. 鉴权依赖 (_get_principal)
   ├─ HTTPBearer 取 token
   ├─ TokenVerifier.verify → Principal(id, roles)
   └─ 失败 → 401
        ↓
3. Agent.chat (core/agent.py)
   ├─ 输入护栏：注入检测（中英双语）→ 不过则 400
   ├─ 预算检查：CostTracker 累计超限 → 402
   └─ principal_context(principal)  ← contextvar 注入身份
        ↓
4. LangGraph 图执行 (create_agent 编译出的 CompiledStateGraph)
   ├─ 从 checkpointer 按 thread_id 加载历史
   ├─ 调模型（ChatOpenAI → DeepSeek）
   │    └─ 回调：TracingCallback(OTel span) + CostCallbackHandler(计费)
   ├─ 模型返回 tool_calls？
   │    ├─ 是 → 进入工具节点
   │    └─ 否 → 结束，产出 AIMessage
        ↓
5. 工具节点 (build_tools 里包装的 StructuredTool)
   ├─ 从 contextvar 取 principal（框架签名塞不进身份参数）
   ├─ start_tool_span(name, principal.id)
   └─ gateway.call(principal, name, args)
        ↓
6. Gateway.call (gateway/gateway.py) —— 治理四件套
   ├─ ① 限流   aallow(principal.id) → 429
   ├─ ② 权限   policy.allows(principal, tool) → 403
   ├─ ③ 存在性 registry.get(tool) → 404
   ├─ ④ 执行   fn(principal, args)
   └─ 每步都写审计事件（含耗时、outcome）
        ↓
7. 回到图：工具结果作为 ToolMessage 喂回模型，继续循环
        ↓
8. 输出护栏：mask(reply) 脱敏密钥 → 返回
        ↓
9. 中间件收尾：打点 HTTP 指标 + 结构化访问日志
```

几个容易被忽略但很关键的细节：

- **限流在权限之前**：先挡住洪水，再谈谁能干什么。顺序反了，攻击者可以用无权限请求打满鉴权逻辑。
- **权限在存在性之前**：未授权用户不该知道某个工具是否存在（避免工具枚举）。
- **principal 走 contextvar 而不是参数**：LangGraph 决定工具函数签名，塞不进 `principal`；contextvar 随 asyncio task 隔离，不会跨请求串号（`agent_platform/context.py`）。
- **流式接口只做输入护栏**：输出脱敏无法撤回已发出的分块，这个取舍在 `Agent.stream` 的 docstring 里写明了。

## 4. 三条主线，三种编排形态

项目里同时存在三种「Agent 形态」，不是重复造轮子，而是对应三种确定性要求：

| 形态 | 入口 | 实现 | 适合 | 状态 |
|---|---|---|---|---|
| 自主 ReAct | `POST /v1/chat` | `create_agent` | 开放式问答、多步工具探索 | 多轮，thread 持久化 |
| 无状态问答 | `POST /v1/ask` | `Agent.ask` | 知识库一问一答 | 独立 thread，用完即删，可缓存 |
| 确定性工作流 | `POST /v1/tickets` | `StateGraph` + `interrupt()` | 敏感操作必须审批 | 暂停后可跨重启恢复 |

**为什么不全用自主 Agent？** 因为「删文件」这种操作不能让模型自己决定要不要审批。
工作流把「意图识别 → 是否敏感 → 审批 → 执行 → 答复」固化成图，模型只负责其中两个节点。
确定性流程用图，开放探索用 Agent —— 这是 LangGraph 官方也强调的分工。

**为什么 `/v1/ask` 要单独开？** 语义缓存只能用在无状态场景。多轮对话里同一个问题
在不同上下文中答案不同，缓存会绕过上下文导致答非所问。这个坑很多项目踩了。

## 5. 关键设计取舍一览

面试最容易被追问的就是「为什么不用 X」。项目里每个选择都有 ADR 或 docstring 记录理由。

| 决策 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 编排引擎 | LangGraph | 自己写状态机 / AutoGen / CrewAI | checkpoint + interrupt 是一等公民，别的要自己补 |
| Agent 入口 | `create_agent` | `create_react_agent` | v1 起后者只是兼容层 |
| 工具集成 | 自建 MCP 网关 | 直接给 Agent 挂函数 | 治理不旁路；工具可跨进程/跨语言 |
| 状态存储 | 三级后端 | 只上 Postgres | 本地要能零依赖跑 |
| 限流 | Redis Lua 滑动窗口 | 进程内令牌桶 | 多副本配额要一致 |
| 限流故障 | 降级本地桶 | fail-open 放行 | 放行等于关掉治理 |
| 向量库 | pgvector | 独立向量数据库 | 少一套运维；业务数据与向量同库可 join |
| 结构化输出 | function_calling | json_schema | DeepSeek 只有 `json_object`，没有官方 json_schema |
| 评测 | 自建 harness + pass^k | 只用 DeepEval | 需要「可靠性」而不只是「能力上限」 |
| 可观测 | OTel `gen_ai.*` → Langfuse | 只接 Langfuse SDK | 换后端不用改埋点 |
| A2A | 只写设计 | 真接入 | 校招项目演示价值低，内部协作用子图更可控 |

## 6. 它和「普通 CRUD 项目」的本质区别

| 维度 | CRUD 后端 | Agent 平台 |
|---|---|---|
| 执行时间 | 毫秒级 | 秒到分钟级，可能挂起数小时 |
| 确定性 | 输入决定输出 | 同样输入可能不同输出 |
| 失败模式 | 异常、超时 | 幻觉、死循环、工具误用、成本爆炸 |
| 状态 | 请求间无状态 | 会话/图状态必须持久化 |
| 安全边界 | 鉴权 + 参数校验 | 还要防提示注入、工具越权、路径穿越 |
| 质量验证 | 单测覆盖分支 | 单测 + 评测集 + LLM-judge + 人工标注 |
| 成本 | 服务器固定成本 | 每请求按 token 计费，必须实时可见 |

这张表本身就是面试素材：**能说清「Agent 系统特殊在哪」，比会调 API 值钱得多。**

## 面试追问

**Q：你这个项目和网上那些 LangChain demo 有什么本质区别？**
A：三点。一是治理闭环——所有工具调用强制过网关的限流/权限/审计，不是给 Agent 一堆函数；
二是状态可恢复——checkpoint 三级后端，服务重启后 HITL 工单还能续批；
三是质量可量化——pass@k/pass^k 双指标 + golden dataset 进 CI。这三点都能指到具体文件和测试。

**Q：为什么不用 CrewAI/AutoGen 这类多 Agent 框架？**
A：多 Agent 协作的难点不是「怎么让几个 Agent 说话」，而是状态一致性、失败重试、成本归属。
这些在 LangGraph 里用子图 + checkpoint 表达更直接，也更容易审计。框架抽象的「角色协作」
在业务里往往不如一张明确的图好维护。

**Q：你怎么保证 Agent 不会做危险操作？**
A：四层。输入护栏挡注入；权限策略按角色白名单（默认拒绝）；敏感操作走 `interrupt()`
人工审批；文件工具做路径沙箱（`resolve_within_root`），越界直接 400。注意 prompt 不是安全边界，
真正的边界在代码里的 policy 和 syscall 之前的检查。
