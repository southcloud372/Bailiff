# 04 · 面试追问手册

使用方式：**先自己答，再看要点**。每题给三样东西——答题骨架、可指认的代码位置、
以及「这样答会减分」的提示。

面试官问项目，本质在验证三件事：**你真的做过、你真的想过、你知道边界在哪。**
所以每题都要能落到「文件 + 数字 + 取舍」。

---

## 一、项目整体（必问）

### Q1. 用两分钟介绍一下这个项目

**骨架**：
1. 一句话定位：企业级 Agent 平台，不是 demo（30 秒）
2. 解决什么：知识问答 + 工单审批，敏感操作必须人工介入（30 秒）
3. 七层分层 + 三个亮点：MCP 真网关、checkpoint 可恢复、评测看可靠性（40 秒）
4. 数字收尾：52 模块 / 145 测试 / mypy strict 0 issue（20 秒）

**别做的事**：不要一上来讲技术栈清单。先讲「谁在用、解决什么痛」，再讲怎么实现。

---

### Q2. 你这个项目和网上的 LangChain demo 有什么本质区别？

**三层回答**：

| 维度 | Demo | 本项目 | 代码位置 |
|---|---|---|---|
| 治理 | 给 Agent 一堆 `@tool` | 所有工具调用强制过网关（限流/权限/审计） | `gateway/gateway.py` |
| 状态 | 内存，重启即丢 | 三级 checkpointer，HITL 可跨重启 | `core/checkpoint.py` |
| 质量 | 「跑通了」 | pass@k/pass^k + golden dataset 进 CI | `evaluation/harness.py` |

**加分**：主动说出「这三件事分别对应三个面试官最可能追问的点」。

---

### Q3. 为什么不用 CrewAI / AutoGen / Dify 这类现成框架？

**要点**：
- 多 Agent 的真难点不是「让几个 Agent 对话」，而是状态一致性、失败重试、成本归属、审计。
- LangGraph 用「图 + checkpoint」表达这些更直接，每个节点可观测、可重放。
- Dify 这类低代码平台适合业务同学快速搭，但**治理层没法按企业策略改**——
  而治理恰恰是本项目的核心命题。

**减分回答**：「因为 LangGraph 更火。」

---

### Q4. 这个项目最大的技术难点是什么？

**推荐选「HITL 跨重启恢复」**，因为它能把三层都串起来：

1. 难点：`interrupt()` 暂停后，状态必须落盘；人几小时后点同意时，进程早重启了。
2. 方案：三级 checkpointer + `_PostgresCheckpointer` 门面解决「同步 compile vs 异步 setup」。
3. 验证：`tests/test_checkpoint.py` 用「新建实例读旧状态」模拟重启。
4. 边界：SQLite 版只适合单机，多副本必须 Postgres。

**备选**：「成本可见性」或「MCP 网关的部分可用」，同样能串三层。

---

### Q5. 如果给你更多时间，你会继续做什么？

按优先级说，且每条都要说清「为什么现在没做」：

1. **代码执行沙箱**：现在只有路径沙箱。要做 `Sandbox` 抽象 + Docker/E2B 双实现。
   现在不做是因为校招场景用不上，且 Docker 依赖会抬高启动门槛。
2. **轨迹级评测（trajectory eval）**：现在只看结果对不对，没看「步骤是否合理」。
3. **A2A 真接入**：只写了设计，因为跨组织 agent 互联在校招项目里演示价值低。
4. **前端可观测面板**：现在指标只能 curl，缺可视化。

## 二、Agent 原理

### Q6. Agent 和「调一次 LLM」的区别是什么？

**要点**：Agent = LLM + 工具 + 循环 + 状态。
- 工具让模型能**改变外部世界**（不只是生成文本）
- 循环让它能**多步推理**（观察结果再决定下一步）
- 状态让它能**跨轮记忆**

**加分**：补一句「代价是引入不确定性：可能死循环、可能误用工具、成本不可预测」。

---

### Q7. ReAct 是什么？和 Function Calling 什么关系？

- ReAct = Reasoning + Acting，论文里的范式：Thought → Action → Observation 循环。
- Function Calling 是**模型厂商提供的机制**，让模型输出结构化的工具调用意图。
- 现代实现通常用 Function Calling 落地 ReAct 的 Action 部分（不需要模型输出文本再解析）。

**加分**：说明为什么现在很少手写 ReAct 提示词模板——原生 tool calling 更可靠。

---

### Q8. 工具（function）的 schema 是怎么给到模型的？

**要点**：
1. Pydantic 模型定义参数（`ReadFileArgs` 等，见 `core/agent.py`）
2. `StructuredTool.from_function(args_schema=...)` 转成 JSON Schema
3. 作为 `tools` 参数随请求发给模型
4. 模型返回 `tool_calls`（名字 + JSON 参数），框架反序列化后调用

**追问预案**：「参数校验失败怎么办？」→ Pydantic 校验报错会作为 ToolMessage 回给模型，
让它自己修正（这是 middleware 处理工具错误的典型场景）。

---

### Q9. 怎么防止 Agent 死循环？

**四道防线**：
1. `recursion_limit`（LangGraph 内置，超过步数抛错）
2. 预算硬限额（`BudgetPolicy`，超 token/成本直接 402）
3. 工具调用超时（`MCPServerSpec.timeout_seconds`）
4. 熔断（连续失败打开，快速失败）

**加分**：「前两个是必须的，后两个是锦上添花。没有预算限制的 Agent 在生产里等于一张空白支票。」

---

### Q10. 同一个问题，Agent 两次回答不一样，怎么保证质量？

**要点**：
- 承认非确定性是本质属性（temperature、采样、工具结果变化）
- 所以质量保证靠**统计**而不是单次：pass^k 才是上线指标
- 具体做法：golden dataset + 多次采样 + LLM-judge + CI 阈值

---

### Q11. 你怎么评估一个 Agent 好不好？

**三层**：
| 层 | 看什么 | 本项目 |
|---|---|---|
| 组件 | 检索命中率、工具选择准确率 | `knowledge/` 单测 + 检索评测 |
| 端到端结果 | 最终答案对不对 | `EvaluationHarness.run` |
| 轨迹 | 步骤是否合理、有无越权/重复 | 设计中（TODO） |
| 可靠性 | k 次是否都成功 | `run_trials` → pass^k |

## 三、LangGraph 与编排

### Q12. 为什么用 LangGraph 而不是自己写 while 循环？

**要点**：
1. checkpoint：自己写要处理「状态序列化 + 增量恢复 + 并发线程隔离」
2. interrupt：暂停/恢复的语义自己实现极易出错
3. 流式：`stream_mode` 提供了 token/事件/状态多种粒度
4. 可视化与可调试：图结构可导出

**减分**：「因为它火。」

**加分**：「如果只是单轮问答，while 循环确实够；我引入 LangGraph 是为了 HITL 和持久化。」

---

### Q13. `create_agent` 和 `StateGraph` 你都用了，怎么选？

- `create_agent`：开放式探索，步骤数不定，模型自己决定下一步 → `/v1/chat`
- `StateGraph`：业务流程固定，只是某些节点需要模型 → `/v1/tickets`

**核心判断**：「**流程的确定性要求 > 灵活性要求** 时用图。」

---

### Q14. `interrupt()` 的原理是什么？恢复时怎么继续？

**要点**：
1. 执行到 `interrupt(payload)` 时，LangGraph 把 payload 抛给调用方，**图停在当前节点之前**
2. 当前状态写入 checkpointer
3. 调用方用 `Command(resume=value)` 重新 `ainvoke`
4. 重新进入该节点，`interrupt()` 这一行**返回** `value`，继续往下

**关键**：不是 `await` 一个 Future，是「暂停 + 重启」。所以必须持久化。

代码：`core/workflow.py` 的 `approval_node`、`TicketWorkflow.resume`。

---

### Q15. State 里能不能放不可序列化的东西？

**不能**。checkpoint 要序列化 state，所以：
- 放 Pydantic / dict / 基本类型
- 不要放数据库连接、文件句柄、协程
- 大对象放外部存储，state 里只放 id

**加分**：「这也是为什么 `TicketState` 用 TypedDict 且字段都是简单类型。」

---

### Q16. LangGraph 的 checkpoint 和「缓存」有什么区别？

- checkpoint 是**状态快照**，用于恢复执行，必须完整、有序、按 thread 隔离
- 缓存是**结果复用**，可丢弃、可过期、按相似度命中

**加分**：「混为一谈会导致用缓存恢复执行，然后就出现『恢复到一半』的诡异 bug。」

---

## 四、MCP

### Q17. MCP 是什么？解决什么问题？

- Model Context Protocol：把「模型 ↔ 工具/数据」的集成标准化。
- 解决的问题：N 个模型 × M 个工具 = N×M 套适配；有 MCP 后变成 N+M。

**结构**：Host（宿主应用）→ Client（协议客户端）→ Server（工具提供方）。

---

### Q18. MCP 和 Function Calling 有什么区别？

| | Function Calling | MCP |
|---|---|---|
| 层次 | 模型能力（输出结构化调用意图） | 集成协议（工具怎么被发现、调用、授权） |
| 范围 | 单次请求内的工具列表 | 跨进程/跨服务的工具生态 |
| 复用 | 每个应用自己接 | 一次实现，多宿主可用 |

一句话：**Function Calling 是「怎么让模型说要调什么」，MCP 是「工具从哪来、怎么调」。**

---

### Q19. 你的 MCP 网关做了什么？为什么说它是「真网关」？

五件事（`gateway/mcp_client.py`）：
1. 作为 MCP **客户端**连接（stdio 子进程 / Streamable HTTP）
2. `tools/list` **动态发现**，不硬编码
3. 转成统一签名 `(principal, args) -> result`，复用治理
4. 名字加 **server 前缀**（`fs__read_file`）避免冲突
5. **故障隔离**：单 server 挂掉不影响其他，`health()` 可见

**加分**：「新接一个 server 时，权限是默认拒绝的，必须显式放行——这是刻意的。」

---

### Q20. MCP 有什么安全风险？

1. **工具投毒**：恶意 server 在 description 里藏指令，诱导模型调用
2. **路径穿越**：文件类工具被 `../../` 绕过（项目里 `resolve_within_root` 防）
3. **越权**：server 拿到的凭据权限过大
4. **供应链**：第三方 server 本身就是不可信代码

**加分**：「所以网关必须做白名单 + 沙箱 + 审计，而不是『能连上就信』。」

---

## 五、RAG

### Q21. 你的 RAG 链路是怎样的？

加载 → 切分 → 嵌入（bge-m3，1024 维）→ pgvector（HNSW）→ 检索（余弦 + metadata 过滤）
→ 格式化带来源 → 注入提示词。

代码：`knowledge/rag.py` 的 `ingest` / `search` / `format_context`。

---

### Q22. 为什么用 pgvector 而不是 Milvus/Pinecone？

- 业务数据本来就在 PG，向量同库可以 join、可以事务、少一套运维
- HNSW 索引在千万级以内够用
- **边界**：如果到亿级或需要多租户强隔离，会考虑专用向量库

**减分**：「因为简单。」（没讲边界）

---

### Q23. HNSW 的 `m` 和 `ef_construction` 是什么？怎么调？

- `m`：每个节点的邻居数，越大召回越高、内存越大（默认 16）
- `ef_construction`：建索引时的候选队列大小，越大索引质量越高、建索引越慢（默认 64）
- `ef_search`：查询时候选数，是**运行时**参数，越大越准越慢（项目设 100）

**加分**：「`ef_search` 可以按查询动态调，是召回-延迟的主要旋钮。」

---

### Q24. RAG 效果不好，你会怎么排查？

按链路顺序，每条给出判断方法：

| 环节 | 症状 | 怎么查 |
|---|---|---|
| 切分 | 答案被切断、上下文不完整 | 打印 chunk 看边界 |
| 嵌入 | 语义相近但检索不到 | 拿问题直接算相似度看排名 |
| 检索 | 召回了但排不进 top_k | 调大 k / 加 `ef_search` / 混合检索 |
| 过滤 | `metadata @>` 把正确结果滤掉 | 去掉 filter 对比 |
| 生成 | 有上下文但答非所问 | 换提示词 / 检查是否要求「仅依据上下文」 |
| 知识 | 知识本身过期 | 看文档更新时间 |

## 六、工程化与生产

### Q25. 你的服务重启，正在等审批的工单还在吗？

**在**（前提：非 memory 后端）。
- 工单图停在 `interrupt()`，状态写入 checkpointer
- 默认 `AGENT_CHECKPOINT_BACKEND=sqlite`，生产切 `postgres`
- 恢复走 `POST /v1/tickets/{id}/resume`，`Command(resume=...)`

**加分**：主动说「如果用 `MemorySaver` 就丢了，这正是我改造它的原因」。

---

### Q26. 多副本部署要注意什么？

1. **状态外置**：checkpoint 必须 Postgres，不能 SQLite/内存
2. **限流共享**：Redis 滑动窗口，否则配额被放大 N 倍
3. **缓存一致**：语义缓存要么共享（Redis），要么接受各副本独立
4. **会话粘性**：同一 thread 尽量打到同一副本（或干脆依赖共享状态）
5. **探针**：`/readyz` 挂了下游就摘流量，不要重启

---

### Q27. `/healthz` 和 `/readyz` 为什么要分开？

- liveness 失败 → **重启容器**。只能查本地状态，查下游会导致上游抖动引发全量重启。
- readiness 失败 → **摘流量**，不重启。这才该查下游依赖。

**加分**：「把两者合成一个『什么都查』的探针，是 K8s 部署最常见的坑。」

代码：`api/app.py` 两个端点 + `observability/health.py`。

---

### Q28. 限流你怎么做的？为什么不用固定窗口？

- 单副本：令牌桶（允许突发，平滑）
- 多副本：Redis 滑动窗口 + Lua 原子脚本
- 固定窗口的问题：**窗口边界双倍流量**（59 秒 100 次 + 61 秒 100 次 = 2 秒内 200 次）

**加分**：「Redis 挂了会降级到本地令牌桶，而不是放行——放行等于关掉治理。」

---

### Q29. 你怎么控制成本？

四层：
1. **可见**：token 级回调计费，`/v1/cost` 暴露，含上下文缓存命中率
2. **可控**：`BudgetPolicy` 硬限额，超限 402
3. **可省**：无状态接口开语义缓存；简单任务用小模型（`ModelRouter`）
4. **可预警**：指标 `agent_llm_cost_yuan_total` 接 Prometheus 告警

---

### Q30. 你的项目有什么已知缺陷？

**主动说三条**（比被问出来强）：
1. 沙箱只有路径级，不是执行级；跑模型生成的代码需要 Docker/E2B 隔离。
2. 语义缓存阈值 0.95 是初始值，没在数据上标定过。
3. 评测缺轨迹级（trajectory）评分，只看结果不看过程。

## 附：答题的通用结构

任何技术问题都可以套这个四段式，30 秒讲完：

```
1. 结论（一句话）
2. 为什么（约束/权衡）
3. 怎么做（具体机制 + 文件）
4. 边界（什么情况下不适用）
```

例：

> 「我用三级 checkpointer（结论）。因为本地要能零依赖跑，生产要多副本（为什么）。
> memory/sqlite/postgres 由环境变量切换，sqlite 是继承官方 InMemorySaver 做写穿（怎么做）。
> 但 sqlite 只适合单机，多副本必须 Postgres（边界）。」

这个结构能让你在任何一个问题上都显得「想过」，而不是「背过」。
