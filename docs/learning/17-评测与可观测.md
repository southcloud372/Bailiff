# 17 · 评测与可观测：把「感觉还行」变成可回归的数字

这篇解决一个具体问题：Agent 改一句提示词、换一个模型、调一次 `top_k`，你怎么知道它变好了还是
变坏了？读完你能设计三层评测（单测/组件/端到端）、识别 LLM-as-judge 的偏差、用 trace/span/
metric/log 定位一次慢请求，并能把评测接进 CI 挡住提示词回归。

阅读方式：先把「pass@k 与 pass^k」的数学搞清，再看本项目 `evaluation/` 与 `observability/` 的实现；评测不是跑一次看分数，而是建立一条可重复的判断链。

---

## 1. 为什么「单步 90%」不能上线

Agent 不是一次模型调用，而是一条轨迹：规划 → 选工具 → 填参数 → 执行 → 观察 → 再规划。
假设每一步独立成功率 90%，5 步全对的概率是：

```text
0.9 × 0.9 × 0.9 × 0.9 × 0.9 = 0.9^5 ≈ 0.590
```

10 步是 `0.9^10 ≈ 0.349`。这就是「单步通过率陷阱」：每一步看起来都不错，连起来只有六成甚至
三成。更要命的是，用户不会给你 5 次机会，他只要一次正确结果。

所以两个指标必须分开：

| 指标 | 定义 | 回答的问题 | 用途 |
|---|---|---|---|
| pass@k | k 次里**至少一次**通过 | 模型能力上限有多高 | 模型选型、探索 |
| pass^k | k 次里**全部**通过 | 用户每次都拿到好结果吗 | 上线门槛、SLA |

公式：单次成功率 `p`，则 `pass@k = 1 - (1-p)^k`，`pass^k = p^k`。

| p | k | pass@k | pass^k |
|---|---|---|---|
| 0.9 | 5 | 99.999% | 59.05% |
| 0.9 | 10 | ≈100% | 34.87% |
| 0.5 | 5 | 96.88% | 3.13% |

注意 `p=0.9, k=5` 时 pass@5 几乎 100%，pass^5 只有 59%。只看 pass@k 会被「答对过一次」骗过去，
上线必须看 pass^k。本项目 `evaluation/harness.py` 的 `run_trials` 就是同时算这两个数：

```python
passed_any = any(s >= threshold for s in scores)
passed_all = all(s >= threshold for s in scores)
# pass@k：至少一次；pass^k：全部
pass_at_k = sum(1 for c in case_trials if c.passed_any) / total
pass_k = sum(1 for c in case_trials if c.passed_all) / total
```

`scripts/eval.py --trials 3` 会把两个数都打印出来。CI 里用 `--trials 3`，不是为了「多跑几次
取最好」，而是为了看**最差的那次**能不能过。

## 2. 评测三层次：从确定性到概率性

| 层次 | 回答的问题 | 典型手段 | 成本 | 确定性 |
|---|---|---|---|---|
| 单测 | 代码逻辑对不对 | pytest、假模型、固定输入 | 毫秒级 | 完全确定 |
| 组件评测 | 检索/工具选择/护栏准不准 | recall@k、工具命中率、混淆矩阵 | 秒级 | 基本确定 |
| 端到端 | 任务完成得好不好 | outcome 断言、trajectory、LLM judge | 分钟级/花钱 | 有随机性 |

三层不是替代关系。**下层不稳，上层的分数没有意义**；只有下层、没有上层，又证明不了「任务真的
完成了」。合理的比例是：大量单测、少量组件评测、极少量高价值端到端用例。

### 2.1 单测：不调用模型，锁住确定性行为

本项目 25 个测试文件、146 个测试函数，绝大多数属于这一层。它们不花 token，跑得快，是重构的
安全带。典型的四类：

```python
def test_path_traversal_is_rejected(tmp_path):
    with pytest.raises(SandboxViolation):
        resolve_within_root(tmp_path, "../../etc/passwd")


def test_budget_rejects_when_cost_limit_reached():
    tracker = CostTracker()
    tracker.record("deepseek-flash", 1000, 500, cost=1.0)
    with pytest.raises(BudgetExceeded):
        BudgetPolicy(cost_limit=0.5).check(tracker)


async def test_recall_is_scoped_by_user(memory_service):
    await memory_service.remember("我偏好简洁回答", user_id="u1")
    assert await memory_service.recall("回答风格", user_id="u2") == []
```

单测应该覆盖：鉴权 401、越权 403、限流 429、预算 402、路径穿越、checkpoint 重启恢复、
线程隔离、Redis 故障降级。这些是**无论模型怎么变都不该变**的契约。

### 2.2 组件评测：把「检索好不好」拆出来量

端到端答错，可能是检索没召回、工具选错、参数填错、模型总结错。组件评测就是逐段归因。

**检索**用 recall@k 和 MRR：

```python
def recall_at_k(retrieved_ids: list[str], relevant_ids: set[str], k: int) -> float:
    if not relevant_ids:
        return 1.0
    hit = len(set(retrieved_ids[:k]) & relevant_ids)
    return hit / len(relevant_ids)
```

构造 30 到 50 条「问题 → 应该命中的片段 id」标注，扫 `top_k` 和相似度阈值。本项目默认
`top_k=4`；生产上这个值应该由标注集选出来，而不是照抄默认值。

**工具选择**用混淆矩阵：给 50 条意图，看模型选的工具名与参数 schema 是否正确。错误分三类：
选错工具、该调不调、参数缺字段。三类错误的修法不同，不要混成一个「准确率」。

**护栏**看 precision/recall：注入样本被拦了多少（recall），正常问题被误杀多少（precision）。
「宁可误杀」是策略，但误杀率要量化，否则用户会先跑掉。

### 2.3 端到端：outcome、trajectory、judge 三种打分

| 打分方式 | 看什么 | 例子 | 能发现什么 |
|---|---|---|---|
| outcome | 最终状态/产物 | 工单状态变成 completed、文件真的写入 | 「答得漂亮但事没办成」 |
| trajectory | 过程轨迹 | 工具顺序、步数、是否越权、是否重复 | 「结果对了但绕了 12 步/调了危险工具」 |
| LLM judge | 回答质量 | 正确性、完整性、语气 | 开放式答案的语义质量 |

优先用 outcome。它能写成断言，确定性最高。例如工单审批的用例，不要 judge「回答是否像审批通过」，
直接断言 `status == "completed"` 且工具真的执行了。trajectory 适合抓两类事故：**越权**
（调了不该调的工具）和**成本失控**（步数/token 超预算）。judge 只用在确实无法断言的地方。

## 3. LLM-as-judge：它有用，但它有偏差

开放式回答没有唯一答案，BLEU/ROUGE 这类 n-gram 重叠指标会把「意思对但换了说法」判成错。
LLM-as-judge 是目前最实用的替代，但它不是一个「客观裁判」，而是一个**有偏见的标注员**。

### 3.1 常见偏差

| 偏差 | 表现 | 后果 |
|---|---|---|
| 位置偏差 | 成对比较时偏好第一个/最后一个 | A/B 顺序一换，结论反转 |
| 长度/啰嗦偏差 | 长答案看起来更「完整」 | 模型学会写废话 |
| 自我偏好 | 偏爱同家族模型的输出 | 用 DeepSeek 判 DeepSeek，分数虚高 |
| 讨好偏差 | 倾向给「看起来合理」的答案高分 | 事实错误被放过 |
| 评分压缩 | 大量集中在 70-85，区分度低 | 阈值怎么调都不敏感 |
| 提示词敏感 | rubric 措辞一改，分布就变 | 分数不可跨版本比较 |

### 3.2 缓解手段

1. **独立 grader**。至少不要和被测 Agent 共享同一个对话/上下文；更高要求是换模型家族。
   本项目 `scripts/eval.py` 用 `build_model(settings)` 新建一个 judge 实例，避免了共享上下文，
   但仍是 DeepSeek 判 DeepSeek——这一点要诚实，高 stakes 场景应换家族或人工抽检。
2. **rubric 锚定**。不要只说「打 0-100 分」，要给分档描述：

```text
90-100：事实全对，覆盖参考答案所有要点，无多余错误
70-89：主要事实正确，漏 1 个次要要点
60-69：方向对，但有 1 个事实错误或明显遗漏
0-59：答非所问、事实错误、或编造来源
```

3. **成对比较 + 交换位置**。同一对答案跑两次（A/B 和 B/A），两次一致才算数；不一致就判平局。
4. **多采样取中位数**。judge 温度建议设 0（本项目当前复用 Agent 的 0.3，属于待改），跑 3 次取中位数，比单次稳。
5. **人工校准**。抽 30 到 50 条人工标注，算 judge 与人的一致率；一致率低就先修 rubric，
   不要急着用它做 CI 门禁。
6. **能断言就别 judge**。数字、状态、工具名、文件存在性，全部用代码判。

本项目的 judge 用 function calling 拿结构化输出，而不是 `response_format`：

```python
class JudgeVerdict(BaseModel):
    score: int = Field(ge=0, le=100)
    reason: str


# DeepSeek 只有 json_object，没有官方 json_schema；
# with_structured_output(method="function_calling") 走工具调用，能拿到 Pydantic 校验后的对象
structured = model.with_structured_output(JudgeVerdict, method="function_calling")
verdict = await structured.ainvoke(prompt)
```

这个细节面试很加分：不是「用了 LangChain 的 judge」，而是知道**为什么不用结构化输出接口**。

## 4. 可观测：trace、span、metric、log 四件套

四个东西经常被混为一谈。用一句话区分：

| 件 | 回答的问题 | 数据形态 | 本项目 |
|---|---|---|---|
| trace | 这一次请求经历了什么 | 一棵 span 树 | OTel → Langfuse |
| span | 这一步花了多久、带了什么属性 | 有起止时间的操作 | `llm.call`、`agent.tool.call` |
| metric | 整体趋势如何 | 时间序列聚合 | `/metrics` Prometheus |
| log | 那一刻发生了什么 | 离散事件（一行 JSON） | `observability/logging.py` |

排查顺序通常是：metric 发现异常 → trace 定位慢在哪 → log 看具体错误。三者靠 `request_id`
串起来，否则就是三座孤岛。

### 4.1 `gen_ai.*` 语义约定：字段要写对，但别当成 Stable API

OpenTelemetry 的 GenAI 语义约定目前仍在 **Development**，没有 Stable。这意味着属性名可能变，
不能把内部存储 schema 硬绑在它上面。落地时至少写这几个：

| 属性 | 含义 | 本项目 |
|---|---|---|
| `gen_ai.operation.name` | 操作类型（chat/embeddings） | 尚未显式设置，待补 |
| `gen_ai.provider.name` | 供应商标识 | 未设置；旧字段 `gen_ai.system` 仍在过渡 |
| `gen_ai.request.model` | 请求的模型名 | `tracing.py` 已设置 |
| `gen_ai.usage.input_tokens` | 输入 token | 已设置 |
| `gen_ai.usage.output_tokens` | 输出 token | 已设置 |

```python
span = self._tracer.start_span("llm.call")
span.set_attribute("gen_ai.request.model", str(model))
span.set_attribute("gen_ai.usage.input_tokens", int(usage.get("prompt_tokens") or 0))
span.set_attribute("gen_ai.usage.output_tokens", int(usage.get("completion_tokens") or 0))
```

工程建议：

- **双写过渡字段**。`gen_ai.provider.name` 与 `gen_ai.system` 同时写一段时间，工具链才都能查。
- **锁定 semconv 版本**。升级 OTel 时把属性变更当破坏性变更评审。
- **自定义字段另开命名空间**。项目用 `agent.tool.name`、`agent.principal.id`，不要硬塞进
  `gen_ai.*`，否则将来规范一变就得全量迁移。

### 4.2 OTLP → Langfuse：一条链路，不要两套埋点

本项目的策略是「先 OTel 打点，再把 OTLP 指向 Langfuse」：

```python
def _otlp_endpoint() -> str:
    endpoint = os.environ.get("OTEL_EXPORTER_OTLP_ENDPOINT", "").strip()
    if endpoint:
        return endpoint
    host = os.environ.get("LANGFUSE_HOST", "").strip()
    return f"{host.rstrip('/')}/api/public/otel/v1/traces" if host else ""
```

没配 endpoint 时 `TracerProvider` 不挂 exporter，span 是 no-op，本地开发和测试零开销。
配了就用 `BatchSpanProcessor` 批量导出，避免每个 span 一次 HTTP。

认证头不要写进代码，用 `OTEL_EXPORTER_OTLP_HEADERS` 注入（Langfuse 用 public/secret 的
Basic Auth）。同时在 exporter 层做**采样**：高 QPS 下全量 trace 会把存储打爆，按错误、
慢请求、特定租户采样，比 uniform 采样更有用。

### 4.3 metric：零依赖不等于简陋

`observability/metrics.py` 用 300 多行实现了 Prometheus 文本格式，只支持 counter / gauge /
histogram 三种原语。为什么不用 `prometheus-client`？理由很实际：演示环境越少依赖越容易起来，
而文本暴露格式本身是稳定规范，几十行就能实现且完全可测。

```python
class Counter:
    def inc(self, value: float = 1.0, **labels: str) -> None:
        key = tuple(labels.get(k, "") for k in self.label_names)
        with self._lock:  # ASGI 多协程，自增必须原子
            self._values[key] = self._values.get(key, 0.0) + value
```

两个容易踩的坑，项目都处理了：

- **label 基数爆炸**。HTTP 指标用路由模板（`/v1/tickets/{thread_id}/resume`），不是原始路径；
  否则每个工单 id 一个 label，Prometheus 内存会被打爆。
- **输出可复现**。暴露时按指标名和 label 排序，方便做快照测试。

当前指标覆盖：LLM 调用次数/token/成本/延迟、工具调用与治理结论、护栏拦截、预算拒绝、
缓存命中、评测均分/通过率、活跃会话、熔断状态。要回答「这个月钱花在哪」，看
`agent_llm_cost_yuan_total{model=...}` 就够了。

### 4.4 log：一行 JSON，三个关联 id

```json
{"ts":"2026-11-10T06:00:00.000Z","level":"INFO","logger":"agent_platform.access",
 "msg":"POST /v1/chat 200 812.4ms","request_id":"a1b2...","principal_id":"u1","thread_id":"u1"}
```

`request_id` 来自上游 `x-request-id` 或本地生成，回显到响应头；`principal_id` 来自
`contextvars`；`thread_id` 标识会话。没有这三个字段，Agent 的「一次请求 → N 次模型调用 →
M 次工具调用」就无法串成一条链。

日志用标准库 `logging` + 自定义 Formatter，不引 structlog。少一个依赖少一个故障面；
结构化日志的关键是**字段稳定**，不是库高级。

## 5. 本项目在哪：评测与可观测的落点

| 能力 | 代码 | 现状 | 缺口 |
|---|---|---|---|
| 评测集 | `evaluation/dataset.py` + `golden.jsonl` | JSONL 版本化，10 条 | 规模偏小，RAG 引用类用例待补 |
| 评测运行 | `evaluation/harness.py` | 逐条 + 多轮采样，pass@k/pass^k | 无并发，串行跑得慢 |
| judge | `evaluation/judge.py` | 结构化打分，独立实例 | 同模型家族，仍有自我偏好 |
| CI | `scripts/eval.py` + `.github/workflows/ci.yml` | 退出码 0/1；threshold=80，trials=3 | 只在 push 跑，PR 不拦 |
| 漂移 | `evaluation/drift.py` | 线上采样对比基线，容差 10% | 还没有线上采样任务 |
| 指标 | `observability/metrics.py` | 零依赖 Prometheus 文本 | 无 exemplar，trace 关联弱 |
| 追踪 | `observability/tracing.py` | OTel + OTLP，no-op 降级 | 缺 `gen_ai.operation.name`，无采样配置 |
| 日志 | `observability/logging.py` | JSON + request_id/principal/thread | 无日志采样，敏感字段脱敏有限 |
| 请求关联 | `api/middleware.py` | 纯 ASGI，request-id 贯穿 | thread_id 还没在 Agent 入口统一注入 |

`middleware.py` 用纯 ASGI 而不是 `BaseHTTPMiddleware`，原因是后者会给每个请求再包一层 anyio
任务，SSE 容易出现首包延迟甚至缓冲异常。纯 ASGI 只包一层 `send`，对流式零影响，还能在
`http.response.start` 时改写响应头回显 `x-request-id`。

`drift.py` 的思路值得单独说：线上随机采样真实问答，用**同一个 judge 和同一个阈值**打分，
与上次全量评测的基线比；跌幅超过 10% 就判漂移。它把评测从「改 prompt 时回归」延伸到
「线上持续监控」，但前提是采样不能带用户隐私，且 judge 版本要固定。

## 6. 为什么评测必须进 CI

先说结论：**提示词、模型版本、工具 schema、检索参数都是代码，但它们不会被 ruff/mypy/pytest
检查**。只有评测能覆盖这一类变更。

五个理由：

1. **单测抓不到语义回归**。你把「先给结论再给依据」改成「20 字以内」，所有单测照样绿，
   但答案开始漏关键点。
2. **模型是非确定性的**。本地跑一次通过，不代表第二次通过；必须用多轮采样看 pass^k。
3. **回归要在 merge 前挡**。等用户发现「昨天还好好的」，成本已经是事故，不是 bug。
4. **评测结果要成为基线**。没有 CI 里的固定分数，`drift.py` 的「基线通过率」从哪来？
5. **退出码是契约**。`scripts/eval.py` 返回 0/1，CI 不需要解析报告，失败就红。

### 6.1 一个提示词回归的例子

假设 golden 里有一条：

```json
{"id":"q007","question":"TCP 和 UDP 的主要区别是什么？",
 "reference":"TCP 面向连接、可靠传输；UDP 无连接、不可靠但更快","category":"network"}
```

原来的系统提示词：

```diff
- 回答要准确、完整：先给结论，再给关键依据，必要时举例。
+ 回答控制在 20 字以内，只给结论，不要解释。
```

单测全绿，评测输出：

```text
评测结果: 7/10 通过，平均分 71.4
  [FAIL] q007: 45 分 — 只说了「TCP 可靠、UDP 快」，缺少「面向连接/无连接」这一关键差异
  [FAIL] q009: 52 分 — 数组与链表的区别被压缩成一句话，漏掉随机访问与插入删除的取舍
...
```

`scripts/eval.py` 最后一行：

```python
return 0 if report.passed == report.total else 1
```

CI 变红，合并被挡住。这就是「提示词回归」：不是代码错了，是**行为契约**变了。

### 6.2 成本与稳定性怎么平衡

一次 10 条用例、`--trials 3` 的评测：

- Agent 调用：10 次（`run`）+ 30 次（`run_trials`）= 40 次；
- judge 调用：同样 40 次；
- 合计约 80 次模型调用。按 DeepSeek Flash 的价格，这是分钱级，但会消耗时间。

实践策略：

- **PR 跑小集**：10 条 smoke，threshold 80，1 次采样；只对 `prompts/`、`evaluation/`、
  模型配置的改动触发（path filter）。
- **main/nightly 跑全量**：30 到 50 条，trials=3，记录 pass@3/pass^3 作为基线。
- **judge 温度 0 + 中位数**，减少 flaky；但仍接受「偶发 1 条波动」，不要把阈值卡到 100%。
- **密钥门控**：没有 `DEEPSEEK_API_KEY` 就 skip，fork 的 PR 不会因为缺 secret 一直红。

本项目当前 `ci.yml` 的 eval job 只在 `push` 和 `workflow_dispatch` 跑，PR 不跑。这是成本
取舍，但也意味着回归是在 merge 后才发现。更严格的做法是给 prompt/评测相关路径加 PR 触发，
或者用 label 手动触发。

### 6.3 golden dataset 的维护规则

- **一条用例只测一个行为**。把「检索准 + 格式对 + 语气好」混在一条，失败时无法归因。
- **参考答案写事实，不写风格**。风格交给 rubric，事实必须可判定。
- **每个线上 bug 补一条用例**。这是 golden 集增长的唯一健康方式。
- **控制在 50 条以内**。50 条 × 3 trials 已经是 150 次生成 + 150 次评判，再多跑不动。
- **版本化**。JSONL 进 git，diff 可审计；不要放数据库里随手改。

## 自测题

**1. pass@k 和 pass^k 的区别是什么？p=0.9、k=5 时各是多少？**
pass@k 是 k 次里至少一次通过，`1-(1-p)^k`，约 99.999%；pass^k 是 k 次全部通过，`p^k`，
约 59.05%。前者看能力上限，后者看部署可靠性。

**2. 为什么单测全绿，仍然可能是一次糟糕的上线？**
单测只覆盖确定性代码逻辑，不覆盖模型语义。提示词、模型版本、检索参数变了，单测不会失败，
但回答质量可能显著下降；这类回归只能靠端到端评测发现。

**3. 评测三层次各举一个本项目里的例子。**
单测：路径穿越被拒绝、预算超限抛 `BudgetExceeded`；组件：检索 recall@k、工具选择混淆矩阵；
端到端：工单审批后 `status=completed` 且工具真的执行、judge 给回答打质量分。

**4. LLM-as-judge 的位置偏差怎么缓解？**
成对比较时交换 A/B 顺序各跑一次，两次结论一致才算数；不一致判平局。再叠加 rubric 锚定、
多采样中位数、人工校准。

**5. `gen_ai.operation.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens`
分别表示什么？为什么不能把它们当 Stable API？**
分别表示操作类型（chat/embeddings）、请求模型、输入 token 数。GenAI 语义约定仍在
Development，属性名可能变；要锁版本、双写过渡字段，不要把内部 schema 硬绑上去。

**6. trace、metric、log 各自回答什么问题？**
trace 回答「这一次请求经历了什么」，metric 回答「整体趋势如何」，log 回答「那一刻具体发生了
什么」。排查时先用 metric 发现异常，再用 trace 定位，再用 log 看细节。

**7. 为什么 `/metrics` 要被排除在 HTTP 指标之外？**
抓取指标本身的请求会污染指标：每次 Prometheus 抓取都增加请求数和延迟样本，形成自我放大的
噪声。项目在中间件里用 `_EXCLUDED_PATHS` 排除了它。

**8. 评测时为什么每条用例要用独立的 `thread_id`？**
checkpoint 会保留历史；如果多条用例共用一个 thread，后一条会带着前一条的上下文，分数不可比。
`harness` 用 `eval-<case.id>`，trials 再加 `-<i>`，保证互不污染。

## 面试追问

**Q1：你怎么证明这个 Agent 的质量？**
要点：三层评测 + 双指标。单测锁确定性契约（鉴权、预算、路径穿越、checkpoint 恢复）；
组件评测量检索 recall@k 与工具选择；端到端用 outcome 断言优先、trajectory 抓越权与步数、
judge 补语义质量。上线看 pass^k，模型选型看 pass@k。最后补一句 golden 只有 10 条，
正在按「每个 bug 补一条」扩到 50 条。

**Q2：LLM-as-judge 自己也会错，你怎么信它？**
要点：先承认它有偏（位置、长度、自我偏好、评分压缩）；再做工程缓解：独立实例/换家族、
rubric 分档、成对交换、温度 0、多采样中位数、人工抽检算一致率。能断言的绝不用 judge。
如果一致率上不去，就先修 rubric，不要拿它做门禁。

**Q3：pass^k 很低，但 pass@k 很高，怎么排查？**
要点：说明「有能力但不稳定」。拆轨迹看哪一步方差大：工具选择是否摇摆、参数是否偶发缺字段、
检索是否 top_k 边界抖动、模型温度是否过高、是否有超时重试。再针对性加约束（工具 schema、
few-shot、确定性校验、降低温度），最后用 trials 复测。

**Q4：线上怎么发现 Agent 变差了？**
要点：三条线。指标线看错误率、延迟、成本、预算拒绝；trace 线看慢在哪一步、工具失败率；
质量线用 `drift.py` 采样同 judge 打分，对比基线，跌幅超容差告警。再加上用户反馈与人工抽检。

**Q5：为什么不用 BLEU/ROUGE 评 Agent 回答？**
要点：它们是 n-gram 重叠，奖励字面相似，不奖励语义正确；同一意思换个说法就低分，啰嗦抄袭反而
高分。Agent 回答开放、长度差异大，应该用断言 + rubric judge，必要时再加人工。

**Q6：评测很贵，怎么在 CI 里控制成本？**
要点：分层触发。PR 跑 10 条 smoke、1 次采样、path filter 只对 prompt/评测/模型配置触发；
main 或 nightly 跑 30-50 条、trials=3；无密钥 skip；judge 温度 0 减少重跑；报告缓存/复用
基线。关键是「挡住高风险改动」，不是每次提交都全量跑。
