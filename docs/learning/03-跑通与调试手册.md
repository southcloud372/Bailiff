# 03 · 跑通与调试手册

这篇保证你在**任何一台干净机器**上都能把项目跑起来，并且知道出错时该看哪里。

---

## 1. 前置条件

| 需要 | 版本 | 检查 |
|---|---|---|
| Python | 3.13+ | `python --version` |
| uv | 0.9+ | `uv --version`（没有就 `pip install uv`） |
| Docker | 可选 | 只有知识库/Redis/Postgres 才需要 |

项目用 `uv` 管理依赖与环境（比 pip 快一个数量级，且锁文件可复现）。
没有 uv 也可以 `pip install -e .`，但下面命令都按 uv 写。

## 2. 路径 A：零依赖启动（推荐先走这条）

**目标：3 分钟内看到 Agent 回话，不需要 Docker、不需要数据库。**

```bash
uv sync                       # 只装基础 + dev，不装 Postgres/Redis 客户端
cp .env.example .env          # Windows: copy .env.example .env
# 编辑 .env，填 DEEPSEEK_API_KEY
uv run python scripts/serve.py
```

看到这行就成功了：

```
INFO:     Uvicorn running on http://127.0.0.1:8000
```

**这一条路径下系统在用什么？**

| 能力 | 实现 | 说明 |
|---|---|---|
| 图状态 | `data/checkpoints/*.sqlite` | 重启不丢，单机持久化 |
| 限流 | 进程内令牌桶 | 单副本有效 |
| 语义缓存 | 关闭 | 需要嵌入服务 |
| 知识库 | 惰性连接 | 不调用就不报错 |
| 可观测 | no-op | 没配 OTLP 就什么都不发 |

### 2.1 验证清单（逐条敲）

```bash
# 1) 存活
curl http://127.0.0.1:8000/healthz
# {"status":"ok"}

# 2) 就绪：会告诉你每个依赖的状态
curl http://127.0.0.1:8000/readyz
# {"ready":true,"probes":[{"name":"gateway",...},{"name":"auth",...},{"name":"checkpoint",...}]}

# 3) 指标
curl http://127.0.0.1:8000/metrics | head -20

# 4) 拿一个测试 token（JWT）
uv run python scripts/mint_token.py | tail -1

# 5) 对话
export TOKEN=<上一步的 token>
curl -X POST http://127.0.0.1:8000/v1/chat \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"message":"帮我在 note.txt 写入 hello，再读出来确认"}'

# 6) 成本账面
curl http://127.0.0.1:8000/v1/cost -H "Authorization: Bearer $TOKEN"
```

`/v1/cost` 应该返回类似：

```json
{"total_cost":0.00051,"total_prompt_tokens":2789,"total_completion_tokens":157,
 "total_cached_tokens":1664,"cache_hit_rate":0.5966,
 "by_model":{"deepseek-flash":{...}}}
```

`cache_hit_rate` 是 DeepSeek 上下文缓存命中率——这是真金白银的省钱比例。

> **注意**：如果本机开了代理，`curl 127.0.0.1` 可能被代理劫持并报
> `upstream connect failed`。加 `--noproxy '*'`，或改用 Python `urllib` 直接访问。

### 2.2 流式对话

```bash
curl -N -X POST http://127.0.0.1:8000/v1/chat/stream \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"message":"用三句话介绍你自己"}'
```

应看到逐块 `data: {"delta":"..."}`，最后 `data: [DONE]`。

## 3. 路径 B：接上知识库与记忆（需要 Docker）

```bash
docker compose up -d
docker exec -it agent-ollama ollama pull bge-m3     # 首次拉模型，约 1-2GB
uv run python scripts/ingest.py --docs-dir examples/knowledge
uv run python scripts/smoke_knowledge.py            # 不依赖模型 key，验证检索链路
```

`smoke_knowledge.py` 打通说明：加载 → 切分 → 嵌入 → pgvector 写入 → 检索 全链路 OK。

拉起来之后 `/readyz` 会多出知识库相关探针（如果你的 `serve.py` 里加了）。
`/v1/tools` 会从 3 个文件工具变成 6 个（多出 `search_knowledge` / `remember` / `recall`）。

**Docker 跑在虚拟机里怎么办？** 改 `.env`：

```bash
AGENT_INFRA_HOST=192.168.x.x     # 虚拟机 IP
```

`KnowledgeSettings` 会据此推导嵌入端点和 DSN。

## 4. 路径 C：切生产后端（不改代码，只改环境变量）

```bash
uv sync --extra prod        # 装 Postgres checkpoint 与 Redis 客户端

AGENT_ENV=prod \
AGENT_CHECKPOINT_BACKEND=postgres \
AGENT_POSTGRES_DSN=postgresql://agent:agent@localhost:5432/agent_platform \
AGENT_RATE_LIMIT_BACKEND=redis \
AGENT_REDIS_URL=redis://localhost:6379/0 \
AGENT_CACHE_ENABLED=true \
uv run python scripts/serve.py
```

要点：

- `AGENT_ENV=prod` 会让 `/readyz` 在 JWT 密钥仍是示例值时返回 503——防止带病上线。
- Postgres 建表由 `startup_hooks` 里的 `_setup_postgres_guarded()` 执行（幂等）。
  DDL 失败只记 error，不阻止启动，但 `/readyz` 会报 `checkpoint` 探针异常。
- 多副本部署时，所有副本必须连同一个 Postgres 与同一个 Redis，否则状态与配额都不一致。

## 5. 常见报错对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `ModuleNotFoundError: mcp.server.mcpserver` | mcp 版本过旧（<2.3） | `uv sync` 重装；检查锁文件 |
| `/readyz` 返回 503，probe=auth | 用了示例 JWT 密钥且 `AGENT_ENV!=dev` | 换密钥，或本地设 `AGENT_ENV=dev` |
| `/v1/chat` 返回 503「未配置模型」 | `DEEPSEEK_API_KEY` 为空 | 填 `.env` |
| `/v1/chat` 返回 402 | 预算限额触发 | 调大 `DEEPSEEK_COST_LIMIT` 或清零 |
| `/v1/chat` 返回 400「检测到疑似 Prompt 注入」 | 输入命中注入正则 | 改措辞；或换自定义 `InputGuard` |
| 调用工具 403 | 权限默认拒绝，工具没放行 | 在 `build_platform(extra_rules=...)` 加规则 |
| 调用工具 404 | 工具未注册 | 检查 `registry.register` |
| 429 | 限流 | 调大 `rate_limit_capacity` |
| 启动时卡 20 秒 | LiteLLM 在拉远程价格表 | 已内置 `LITELLM_LOCAL_MODEL_COST_MAP`；确认版本已更新 |
| `another command is already in progress` | pgvector 单连接被并发共享 | 已改连接池；确认用的是新版 `PgVectorStore` |
| `psycopg_pool` 导入失败 | 没装 prod extra | `uv sync --extra prod` |
| `dimension mismatch` 插入报错 | `AGENT_EMBEDDING_DIMENSIONS` 与实际模型不符 | bge-m3 是 1024 |
| 审批恢复后图重新跑了一遍 | 没传 `Command(resume=...)` | 见 `TicketWorkflow.resume` |
| 重启后工单丢了 | 用了 `memory` checkpoint | 切 `sqlite` 或 `postgres` |

## 6. 怎么加一个自己的能力

### 6.1 加一个工具（走完整治理）

三步，缺一不可：

```python
# 1) 实现工具函数：签名必须是 (principal, args) -> result
async def get_weather(principal: Principal, args: dict[str, Any]) -> str:
    city = args["city"]
    return f"{city} 今天晴，22 度"      # 真实实现换成 httpx 调用

# 2) 注册进平台，并显式放行（默认拒绝）
platform = build_platform(
    extra_tools={"get_weather": get_weather},
    extra_rules=[PermissionRule(tool="get_weather", roles=frozenset({"agent"}))],
)
```

```python
# 3) 让 Agent 能看到它：core/agent.py 的 build_tools 里按名字追加
if "get_weather" in gateway.tool_names():
    tools.append(_tool("get_weather", "查询某城市天气", GetWeatherArgs))
```

为什么第 3 步不能省：`build_tools` 是「给模型看的工具清单」，
注册进 registry 只是「网关能执行」。两者分开是有意的——你可以先注册、灰度再暴露给模型。

### 6.2 加一个工作流节点

```python
async def confirm_node(state: TicketState) -> dict[str, Any]:
    # 读 state，写回增量字段
    return {"reply": "已确认"}

graph.add_node("confirm", confirm_node)
graph.add_edge("execute", "confirm")
graph.add_edge("confirm", END)
```

注意：`StateGraph(TicketState)` 里的 `TicketState` 是 `TypedDict`，
节点返回的是**增量**（只写要改的 key），不是完整 state。

### 6.3 换成别的模型

```bash
# 只改环境变量，代码不动
DEEPSEEK_MODEL=deepseek-v4-pro
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

要接 OpenAI/Claude，改 `build_model` 里的 `ChatOpenAI` 为对应适配器即可；
`router/llm.py` 的 `ModelRouter` 已经封装了多供应商 + fallback。

## 7. 调试技巧

### 7.1 用 request-id 串起所有日志

每个响应头都有 `x-request-id`。全链路日志、审计事件、trace 都能按它检索。

```bash
curl -i http://127.0.0.1:8000/healthz | grep -i x-request-id
```

也可以主动传入，跨服务关联：

```bash
curl -H "x-request-id: trace-debug-001" http://127.0.0.1:8000/healthz
```

### 7.2 看 checkpoint 里到底存了什么

```python
from agent_platform.core.checkpoint import SqliteCheckpointSaver
saver = SqliteCheckpointSaver("data/checkpoints/tickets.sqlite")
print(saver.get_tuple({"configurable": {"thread_id": "demo"}}))
```

LangGraph 的 time-travel 调试也是基于它：给定 `thread_id` + `checkpoint_id` 可以回放。

### 7.3 单测是最快的调试器

```bash
uv run pytest tests/test_workflow.py -q          # 单文件
uv run pytest -q -k interrupt                    # 按名字筛
uv run pytest -q -x                              # 首个失败就停
```

每个模块都有测试，且**不依赖外部服务**（假模型、假 embedder、内存存储）。
写新功能时先照着同类测试写一个，比手动 curl 快得多。

### 7.4 打开 trace

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
LANGFUSE_PUBLIC_KEY=pk-... LANGFUSE_SECRET_KEY=sk-... \
uv run python scripts/serve.py
```

不配就是 no-op，**不会因为没装 Langfuse 而起不来**——这是刻意的降级设计。

## 附：两个只在「多步任务」里出现的故障（真实复盘）

这两条不在常见报错表里，因为它们都不在第一次调用时爆发。判断方法很重要：
**看它是不是"第一次正常、第二次挂"**。

### 故障 A：调一次工具后，第二次模型调用 400

现象：

```
OpenAIInvalidRequestError: Error code: 400 -
  The `reasoning_content` in the thinking mode must be passed back to the API.
```

排查路径（照着做，30 秒定位）：

1. 用裸 `ChatOpenAI` 直接发一条带 `tool_calls` 的 assistant 消息 + 一条 ToolMessage，看是否 400：
   ```python
   from langchain_openai import ChatOpenAI
   from langchain_core.messages import HumanMessage, AIMessage, ToolMessage
   m = ChatOpenAI(model="deepseek-flash", api_key="...", base_url="https://api.deepseek.com")
   msgs = [
       HumanMessage(content="读 a.txt"),
       AIMessage(content="", tool_calls=[{"id": "c1", "name": "read_file", "args": {"path": "a.txt"}}]),
       ToolMessage(content="hello", tool_call_id="c1"),
   ]
   m.invoke(msgs)   # 400 就在这里复现
   ```
2. 复现即确认：**是序列化层丢了 `reasoning_content`**，不是 Agent 逻辑的问题。

根因：思考模型要求带 `tool_calls` 的 assistant 消息回传推理内容；
LangChain 的 `ChatOpenAI` 序列化只映射白名单字段，`additional_kwargs` 被丢掉。

修复位置：`agent_platform/router/deepseek.py` 覆写 `_get_request_payload`。
回归测试：`tests/test_deepseek_payload.py`。

### 故障 B：一次失败的工具调用，让整条会话永久 400

现象：

```
An assistant message with 'tool_calls' must be followed by tool messages
responding to each 'tool_call_id'. (insufficient tool messages following tool_calls message)
```

关键特征：**换新 thread_id 就好，老 thread 永远坏**。这几乎是「历史被写坏」的铁证。

排查路径：

1. 用同一个 `thread_id` 连续发两条消息，若第一条成功、第二条失败 → 历史有问题；
2. 去 checkpoint 里看那条 assistant 消息有几个 `tool_calls`、后面有几条 tool 消息，数量不等即确认。

根因有两层：

| 层 | 问题 | 修复 |
|---|---|---|
| 产生 | 工具抛异常 → ToolNode 中途中止 → 少写一条 ToolMessage | 所有工具异常转结构化结果（`{"ok": false, "kind": ...}`） |
| 存量 | 已经写坏的 checkpoint | `_repair_dangling_tool_calls` 在序列化时补齐缺失的 tool 消息 |

修复位置：`agent_platform/core/agent.py`（产生侧）、`agent_platform/router/deepseek.py`（存量侧）。

**面试价值**：这两个都是「协议约束 × 框架实现差异」的典型。能讲清楚"为什么 demo 测不出来、
怎么用最小复现定位、修复为什么要分两层"，比背十个八股有用。

## 面试追问

**Q：面试官让你当场跑一遍，你怎么保证不出丑？**
A：先走零依赖路径（`uv sync` + 填 key + serve），三个探针端点验证，
再用 `mint_token.py` 拿 token 打一次对话。全程不碰 Docker，失败面最小。
如果网络受限，提前把 `uv.lock` 和 `.venv` 准备好。

**Q：你怎么保证别人 clone 下来能跑？**
A：三个设计。默认值全部指向零依赖实现（SQLite/内存/关闭缓存）；可选依赖放 extras，
不装也能 import；启动时任何外部依赖失败都只降级不崩溃，并由 `/readyz` 如实报告。
CI 里用 `uv sync --frozen` 保证依赖可复现。
