# 18 · 生产化与部署治理：从「本机能跑」到「敢接流量」

这篇解决一个具体问题：demo 在笔记本上跑通了，但一上多副本就丢会话、一被刷就限不住、
数据库一抖整个服务全挂。读完你能说清从 demo 到生产要补的十件事、三种部署形态的取舍、
K8s 两类探针的语义，以及 Agent 服务为什么比普通 Web 服务更难扩容。

阅读方式：把「十件事」当检查表，逐项对照本项目代码，标出「已落地 / 部分 / 缺口」；生产化不是加组件，而是把失败模式一个个关掉。

## 1. 从 demo 到生产要补的十件事

| # | 事项 | 不做的后果 | 最小做法 | 本项目状态 |
|---|---|---|---|---|
| 1 | 鉴权 | 任何人都能调工具、烧 token | JWT 验签 → `Principal`；401 | 已落地基础（HS256） |
| 2 | 权限 | 普通用户调用管理工具 | 默认拒绝 + 显式白名单；403 | 已落地 |
| 3 | 限流 | 一个用户打满全站 | 令牌桶/滑动窗口；429 | 已落地（含 Redis） |
| 4 | 审计 | 出事后查不到谁干了什么 | 每次工具调用留痕 | 部分（内存 sink） |
| 5 | 超时/重试/熔断 | 上游抖动拖垮整个事件循环 | 超时 + 退避 + 熔断 | 模块已实现，未接主线 |
| 6 | 幂等 | 重试导致重复下单/重复写 | 幂等键 + 结果复用 | 缺口 |
| 7 | 可观测 | 只知道「慢」，不知道慢在哪 | trace/metric/log + request id | 基本落地 |
| 8 | 灰度 | 一次 prompt 改动全量翻车 | 按用户/流量分流 + 回滚 | 缺口 |
| 9 | 容量 | 大促被打穿或过度扩容 | 压测 + Little's law + 限流 | 缺口（无压测） |
| 10 | 成本 | 账单失控，月底才发现 | token 计费 + 硬预算 + 配额 | 部分（进程内） |

这张表最重要的不是「做了几项」，而是**知道哪项是缺口、缺口会怎么炸**。下面挑几项展开。

### 1.1 鉴权与权限：401 和 403 是两件事

- **401 Unauthorized**：你是谁不清楚。token 缺失、过期、签名不对。
- **403 Forbidden**：知道你是谁，但你没权限。角色不够、工具不在白名单。

本项目在 API 边界用 `HTTPBearer` 取 token，`TokenVerifier` 验 HS256 并提取 `sub/roles`，
再交给 `PermissionPolicy`。权限模型是 **deny-by-default**：没有命中任何规则就拒绝。

```python
def _get_principal(request, credentials) -> Principal:
    if credentials is None:
        raise HTTPException(401, "缺少 Bearer token")
    try:
        return platform.verifier.verify(credentials.credentials)
    except AuthenticationError as exc:
        raise HTTPException(401, str(exc)) from exc
```

生产上要补的：

- HS256 共享密钥只适合演示/单服务；多服务用 RS256/ES256 + JWKS，支持密钥轮换。
- token TTL 要短，配 refresh token；不要用永久 token。
- `roles` 不要由客户端传，必须来自可信 IdP。
- 审计里记录 `principal_id`，但不要记录 token 本身。

### 1.2 超时、重试、熔断：三者正交，不能互相替代

模型 API 的失败是常态：429 限流、502/503 网关抖动、长尾超时。`router/resilience.py`
把三件事拆开：

1. **超时**：每次调用设上限，避免一个卡住的请求占住事件循环。
2. **重试 + 指数退避 + 抖动**：瞬时错误再试，但退避带随机，避免同频重试形成尖峰。
3. **熔断**：连续失败到阈值后快速失败，半开放一个探测请求，给上游恢复时间。

```python
async def call(self, fn):
    async def attempt():
        if not self.breaker.allow():
            raise CircuitOpenError("熔断器打开")
        try:
            result = await asyncio.wait_for(fn(), timeout=self.timeout)
        except Exception:
            self.breaker.record_failure(); raise
        self.breaker.record_success(); return result
    return await self.retry.run(attempt)
```

三个工程约束：

- **只重试幂等操作**。读、查询可以重试；写文件、下单、发消息不能盲目重试，除非有幂等键。
- **重试预算要小于上游超时**。3 次 × 60 秒会把用户挂 3 分钟，体验比快速失败更差。
- **熔断按目标隔离**。模型 A 挂了不应该熔断模型 B；本项目 `CircuitBreaker` 带 `target` 标签。

需要诚实说明：这一层目前是独立模块并有单测，但主 Agent 走的是 `ChatOpenAI`，
还没有把 `ResilientCaller` 包到模型调用外面。接法有两种：给 `ChatOpenAI` 配
`timeout`/`max_retries`，或者把 `ModelRouter` 接进 `build_model`。这是明确的待办，
面试被问「你这层真的生效了吗」时要能答出来，而不是含糊过去。

### 1.3 幂等：Agent 的重试比普通服务更危险

普通 Web 请求重试一次，最多多查一次库。Agent 重试可能**重复执行工具**：重复写文件、
重复建工单、重复发通知。更糟的是，模型可能在一次运行里自己重复调用同一个工具。

本项目的 HITL 工单已经有一个天然幂等点：恢复前先看状态。

```python
# 伪代码：resume 前检查，已完成的工单直接返回
state = await graph.aget_state(config)
if state.values.get("status") == "completed":
    return existing_result
```

但通用的 HTTP 幂等还没做。最小设计：

```text
客户端带 Idempotency-Key: <uuid>
  1. key 不存在 → SET key "in_progress" NX EX 86400
  2. 已存在且 body_hash 不同 → 409；已完成 → 返回缓存响应；执行中 → 409/202
  3. 执行完成 → 写回 {body_hash, status, response}，TTL 24h
```

注意三点：

- 幂等键要覆盖**写操作**，不要覆盖读；读重试是安全的。
- 流式响应不能简单缓存整个 body，要么只对非流式接口开幂等，要么缓存事件流并在重放时标注。
- 工单审批的「同意/拒绝」按钮要防双击：状态机先判终态，再执行副作用。

### 1.4 审计：从「有日志」到「可追责」

`AuditLogger` 现在把 `AuditEvent` 存在内存列表里，带 `principal_id/tool/arguments/outcome/
duration_ms`。`outcome` 有四种：`allowed/denied/rate_limited/error`。这已经比「只记成功日志」
好，因为**失败的调用同样重要**：谁试图越权、谁被限流，都是安全信号。

生产上要补：

- **持久化 sink**：写 PostgreSQL 或 Kafka，append-only；进程重启不丢。
- **参数脱敏**：工具参数可能带密钥、身份证、文件内容；落库前按字段白名单/正则脱敏。
- **保留期、访问控制与不可篡改**：审计本身是敏感数据，按合规设保留期，只追加、定期归档，必要时用哈希链或 WORM。

### 1.5 成本：token 级计费 + 硬限额

`router/cost.py` 用 LangChain callback 在每次 LLM 调用结束时读 `token_usage`，
按 LiteLLM 价格表估算费用；`BudgetPolicy` 在**每次请求进入图之前**检查累计值，超限抛
`BudgetExceeded`，API 返回 402。注意它不是在每一步模型调用前检查，长轨迹中途仍可能穿透，
要靠 `max_steps`/`max_tokens` 兜底。DeepSeek 的上下文缓存命中 token 单独记在
`cached_tokens`，并算命中率，不臆造缓存单价。

两个必须知道的边界：

- **预算是进程内的**。`CostTracker` 是内存累加器；多副本时每个副本各算各的，全局上限
  会被放大 N 倍。生产要么把累计值放 Redis/账单系统，要么按租户做配额。
- **预算是事后 + 事前混合**。`CostTracker` 在调用后记账，`BudgetPolicy` 在下次请求前检查；
  单次超大调用仍可能穿透。要更严格就设单次 `max_tokens` 上限。

## 2. 部署形态：单机、多副本、容器

### 2.1 单机：够用，但别开多 worker

适合本地开发、演示、内部小流量。形态是：

```text
uvicorn（单进程） + SQLite checkpoint + 进程内令牌桶 + 进程内语义缓存
```

关键限制：**不要用 `uvicorn --workers 4` 配 SQLite saver**。每个 worker 是独立进程，
各自持有一份 `InMemorySaver` 缓存，却写同一个 SQLite 文件；`SqliteCheckpointSaver` 的
`threading.Lock` 只保证进程内线程安全，跨进程写同一文件不安全。要多 worker，就换 PostgreSQL。

单机也要备份：WAL 模式下备份要连 `-wal`/`-shm` 一起考虑，或用 `sqlite3 .backup`；别把 checkpoint 目录放网络文件系统。

### 2.2 多副本：把状态外置，计算无状态

多副本的前提是「任何一个副本都能处理任何一个请求」：

| 能力 | 单机 | 多副本 |
|---|---|---|
| 会话状态 | SQLite 文件 | PostgreSQL（`AsyncPostgresSaver` + 连接池） |
| 限流 | 进程内令牌桶 | Redis 滑动窗口（Lua 原子） |
| 缓存/成本 | 进程内 | 仍是进程内：命中率摊薄、全局预算不准 |
| 文件工具 | 本地目录 | 对象存储/共享卷，且要做租户隔离 |

checkpoint 放 PostgreSQL 后，不需要粘性会话：`thread_id` 是状态主键，LB 打到哪个副本都能
`get_tuple` 恢复。但 SSE 长连接仍需要 LB 支持长超时和连接排空，这部分见第 4 节。

多副本还要注意 **checkpoint 写入放大**：每个超级步都写一次，工单/对话多了以后表会快速膨胀。
需要按 `thread_id` 归档、按时间分区、定期清理；`/v1/ask` 用完即删就是最基础的止损。

### 2.3 容器：多阶段、非 root、密钥不进层

本项目 `deploy/Dockerfile` 的要点：

```dockerfile
FROM ghcr.io/astral-sh/uv:python3.13-bookworm-slim AS builder
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project --extra prod
COPY agent_platform ./agent_platform
RUN uv sync --frozen --no-dev --extra prod

FROM python:3.13-slim AS runtime
RUN useradd --create-home --uid 10001 app
COPY --from=builder --chown=app:app /app /app
USER app
HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')"
CMD ["python", "scripts/serve.py"]
```

四个设计点：

1. **多阶段**：builder 装依赖，runtime 只留虚拟环境，最终镜像不含 uv/编译器，攻击面更小。
2. **先拷锁文件再拷源码**：源码变更不会触发依赖重装，层缓存利用率高。
3. **非 root（uid 10001）**：容器逃逸后的第一道限制；但要注意数据目录要 `chown` 给 app。
4. **密钥只从运行时环境变量注入**：`DEEPSEEK_API_KEY`、`AGENT_JWT_SECRET` 绝不打进镜像层，
   否则 `docker history` 就能扒出来。

`docker-compose.yml` 只起基础设施：PostgreSQL 18 + pgvector、Redis 8（AOF +
`allkeys-lru`）、Ollama（本地 bge-m3）。应用镜像单独 build/run。compose 里的
`agent/agent` 密码是本地开发用，生产必须换。

### 2.4 K8s 探针：liveness 和 readiness 不能混

这是生产事故的高发点。语义完全不同：

| 探针 | 端点 | 失败动作 | 该查什么 |
|---|---|---|---|
| startup | `/healthz` | 重启容器（启动期） | 进程是否起来 |
| liveness | `/healthz` | 重启容器 | 只查本地状态 |
| readiness | `/readyz` | 从 Service 摘除，不重启 | 下游依赖是否可用 |

如果把两者合成一个「什么都查」的探针，PostgreSQL 抖一下，所有 Pod 的 liveness 同时失败，
K8s 会把全部副本重启——**部分不可用被放大成全部不可用**。这是本项目在
`observability/health.py` 开头专门写明的取舍。

```yaml
startupProbe: {httpGet: {path: /healthz, port: 8000}, failureThreshold: 30, periodSeconds: 2}
livenessProbe: {httpGet: {path: /healthz, port: 8000}, periodSeconds: 10}
readinessProbe: {httpGet: {path: /readyz, port: 8000}, periodSeconds: 5}
terminationGracePeriodSeconds: 120
```

`/readyz` 内部并发探测，任一 **critical** 探针失败就返回 503；非 critical 的（如语义缓存、
MCP 外部 server）只报告状态，不改变整体判定——缓存挂了应该降级直连模型，而不是拒绝服务。
每个探针自己吞异常并转成 unhealthy，单个探针不会把 `/readyz` 打成 500。

Agent 服务还要特别注意**优雅停机**：SSE 连接可能正在流式输出，`terminationGracePeriodSeconds`
要给够；`preStop` 先让 Service 停止转发，再等连接排空；不能在工具执行到一半时硬杀，
否则副作用可能只做了一半。配合幂等，才能安全重试。

### 2.5 配置与密钥

本项目用 `pydantic-settings`，前缀 `AGENT_`，`.env` 只用于本地：

```text
AGENT_CHECKPOINT_BACKEND=postgres
AGENT_POSTGRES_DSN=postgresql://...
AGENT_RATE_LIMIT_BACKEND=redis
AGENT_REDIS_URL=redis://...
AGENT_JWT_SECRET=<32+ bytes random>
```

生产原则：

- 密钥放 K8s Secret / External Secrets / Vault，不进 git、不进镜像、不进日志。
- 配置按环境分层，默认值要「本地零依赖」，但不能让默认密钥上生产。
- 本项目 `default_readiness` 会检查 JWT 密钥是否是示例值：`dev` 只告警，`staging/prod`
  直接 503。这是「同一份代码，严格度按环境分级」的例子。
- 轮换密钥要有灰度：旧密钥验签 + 新密钥签发并行一段时间，否则全量用户掉登录。

## 3. 本项目在哪：治理闭环的四段代码

### 3.1 网关四件套：限流 → 权限 → 存在性 → 执行

`gateway/gateway.py` 的顺序不是随手排的：

```python
# 1. 限流（最早，防 DoS）
if limiter and not await limiter.aallow(principal.id):
    self._record(principal, tool, arguments, "rate_limited", start)
    raise RateLimitExceeded(principal.id)
# 2. 权限（先权限后存在性：不向未授权调用方泄露工具是否存在）
if not policy.allows(principal, tool):
    self._record(principal, tool, arguments, "denied", start)
    raise PermissionDenied(tool)
# 3. 存在性（已授权但未注册 = 配置错误）
fn = registry.get(tool)
if fn is None:
    self._record(principal, tool, arguments, "error", start)
    raise UnknownTool(tool)
# 4. 执行 + 审计成功
result = await fn(principal, arguments)
self._record(principal, tool, arguments, "allowed", start)
```

为什么是这个顺序：

- **限流最先**：最便宜，能在进任何业务逻辑前挡住刷量。
- **权限先于存在性**：如果先查存在性，未授权用户可以通过 404/403 的差异探测有哪些工具，
  这是信息泄露。先判权限，统一返回 403。
- **审计是横切，不是第五步**：四个分支都调用 `_record`，失败路径也留痕。只记成功等于没审计。

### 3.2 Redis 滑动窗口：Lua 保证「读-改-写」原子

```lua
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
  redis.call('ZADD', key, now, ARGV[4])
  redis.call('PEXPIRE', key, window)
  return 1
end
return 0
```

三个细节：

- **ZSET 的 member 必须唯一**。项目用 `"{now_ms}-{uuid}"`，不能只用时间戳；同一毫秒的两个请求会覆盖，计数少算。
- **清理、计数、写入必须在同一个 Lua 脚本里**。拆成多条命令有竞态：两个请求同时看到 99，然后都写入，实际 101。
- **滑动窗口 vs 固定窗口**：固定窗口在边界会放过双倍流量，滑动窗口没有这个问题，代价是每个请求一次 Redis 往返。

Redis 挂了呢？`RedisRateLimiter` 降级到本地令牌桶，并打 warning：

```python
except Exception as exc:
    logger.warning("rate_limiter_degraded", extra={"event": "ratelimit_degraded",
                                                   "error": str(exc)})
    return await self._fallback.aallow(key)
```

这是 **fail-degraded**，不是 fail-open。直接放行等于关掉治理；降级到本地桶至少保住单副本的
防雪崩能力。代价是多副本下配额不共享，但比「完全不限」好。这个取舍面试可以展开讲。

### 3.3 `/readyz`：并发探测，critical 决定 503

```python
async def check(self) -> ReadinessReport:
    results = await asyncio.gather(*(self._run(p) for p in self._probes))
    ready = all(r.healthy for r in results if r.critical)
    return ReadinessReport(ready=ready, probes=list(results))
```

`_run` 用 `asyncio.wait_for(..., timeout=3.0)` 给每个探针超时，异常转 unhealthy。
`serve.py` 追加 checkpoint（critical）、MCP 与语义缓存（非 critical）。注意：当前 checkpoint
探针只返回后端类型，没有真正 ping PostgreSQL；要让「PG 挂了 → 503」成立，得补 `SELECT 1`。

`/healthz` 则只有一行：

```python
@app.get("/healthz")
async def healthz(): return {"status": "ok"}
```

它不碰任何下游。这是刻意设计：liveness 的职责是「进程还在不在」，不是「业务能不能用」。

### 3.4 镜像与 compose：本地能跑，生产能换

`deploy/Dockerfile` 的 `--extra prod` 安装 `langgraph-checkpoint-postgres`、`psycopg[pool]`、
`redis`；本地 `uv sync` 不装这些也能跑，因为默认是 SQLite + 内存限流。这就是
ADR-0006 的「运行时后端可插拔」：同一份代码，靠 `AGENT_*` 环境变量切换形态。

`docker-compose.yml` 的 PG 用 `pgvector/pgvector:pg18`，首次初始化执行 `deploy/initdb`
里的扩展；Redis 开 AOF，因为限流计数/缓存丢了会放大流量；Ollama 提供本地 bge-m3 嵌入，
不依赖外部 API key。注意 compose 里**没有应用服务**，应用是单独 build/run 的，这样
本地调试和容器部署不会互相绑死。

## 4. Agent 服务为什么比普通 Web 服务更难扩容

普通 Web 服务的容量单位是 QPS：请求短、无状态、可随时重试。Agent 不是。

### 4.1 长连接与流式：连接数就是内存和文件描述符

SSE 让一个请求持续几十秒到几分钟。LB 的 idle timeout、代理的缓冲区、客户端断线重连都会影响
容量。更关键的是：

- 每个连接占一个文件描述符和一段缓冲区，1 万并发连接不是「1 万 QPS」，而是 1 万个**同时活着**
  的连接；
- 反向代理如果缓冲 SSE，首 token 会被延迟到整个响应结束，流式就失去意义；
- 扩缩容时不能硬杀连接，必须 drain。

本项目的中间件用纯 ASGI 而不是 `BaseHTTPMiddleware`，就是为了不破坏 SSE 的逐块下发。

### 4.2 长任务：容量按「并发会话」算，不按 QPS 算

用 Little's law 估算：`并发数 L = 到达率 λ × 平均停留时间 W`。如果平均请求 20 秒、要支撑
200 个并发会话，则 `λ = 200 / 20 = 10 QPS`。

同样 10 QPS，普通 Web 服务可能只需要 1 个副本；Agent 需要同时挂住 200 个协程、200 条模型连接、
200 份上下文。p99 如果是 60 秒而不是 20 秒，容量要按 3 倍留。

### 4.3 状态：每一步都要写 checkpoint

LangGraph 每个超级步都写一次状态。对话越长、工具越多，写放大越明显。多副本下 PostgreSQL
要扛住这些写；单机 SQLite 只能单写者。工单停在 `interrupt()` 可能几天，不能占着 worker，
必须靠 checkpoint 外置 + 恢复，而不是「把请求挂在内存里等审批」。

### 4.4 成本不可预测：token 是二阶变量

普通请求的 CPU/内存相对稳定；Agent 的成本取决于模型生成多少 token、循环几次、调几个工具。
一次失控的 ReAct 循环可能烧掉几百次调用。容量规划不能只看 QPS，还要看：

- 每请求平均/ P99 token；
- 每次会话平均工具调用次数；
- 缓存命中率（命中价约为未命中价的 1/50，命中率变化会显著改变成本）；
- 供应商的 RPM/TPM 配额（你扩容了副本，供应商配额不会跟着扩）。

所以要有**准入控制**：最大并发、单请求 max_steps、单次 max_tokens、每租户预算、队列和
429 + `Retry-After`。没有这些，扩容只是把压力更快地打到模型供应商。

### 4.5 非确定性：压测结果不可完全复现

同一个请求跑两次，token 数、工具路径可能不同。压测要报告分布（P50/P95/P99），不要用单次
平均值；要固定模型版本、温度、提示词，否则两次压测不可比。

### 4.6 运维含义

| 普通 Web | Agent |
|---|---|
| 扩容看 QPS/CPU | 扩容看并发会话 + token 吞吐 + 供应商配额 |
| 请求可随时重试 | 写操作要幂等，流式不能无脑重放 |
| 无状态，随便杀 | 状态外置，停机要 drain + checkpoint |
| 成本随流量线性 | 成本随轨迹长度超线性，必须硬限额 |
| 探针查 DB 就行 | liveness 绝不查下游，readiness 才查 |

## 5. 上线检查清单

```text
[ ] 鉴权/权限：401 与 403 分开；token 有 TTL；默认拒绝 + 白名单；越权有测试
[ ] 限流/审计：多副本 Redis；故障降级不放行；成功失败都留痕；参数脱敏
[ ] 超时/熔断：模型、工具、HTTP 三层上限；按目标隔离；重试只用于幂等操作
[ ] 幂等/可观测：写接口支持 Idempotency-Key；request_id 贯穿日志/trace
[ ] 灰度/容量：prompt/模型版本可分流回滚；压测 P95/P99；最大并发有准入
[ ] 成本/部署：token 级计费 + 402；多阶段非 root；liveness/readiness 分开
```

## 自测题

**1. `/healthz` 和 `/readyz` 的区别是什么？混用会怎样？**
`/healthz` 是存活探针，只查进程本身，失败重启容器；`/readyz` 是就绪探针，并发查下游，
critical 失败返回 503 并摘流量，但不重启。混用会让上游抖动触发全量重启，把部分不可用放大成
全部不可用。

**2. 单副本令牌桶和多副本 Redis 滑动窗口，差别在哪？**
令牌桶计数在进程内存，N 个副本等于配额放大 N 倍；Redis 滑动窗口把计数放共享存储，Lua 保证
清理+计数+写入原子，多副本才有一致配额。

**3. Redis 限流器故障时为什么降级而不是放行？**
放行等于关掉治理，突增流量会直接打到模型和工具；降级到本地令牌桶至少保住单副本防雪崩，
同时打 warning 让运维介入。这是 fail-degraded，不是 fail-open。

**4. 网关为什么先判权限再判工具是否存在？**
避免向未授权调用方泄露「工具是否存在」。先查存在性会让攻击者通过 404/403 差异枚举工具；
先判权限统一返回 403。

**5. Lua 脚本里为什么 ZSET 的 member 要带 uuid？**
ZSET 的 member 唯一。如果只用毫秒时间戳，同一毫秒的两个请求会覆盖成同一个 member，计数少算；
`now_ms-uuid` 保证每次请求都是独立成员。

**6. 为什么 `uvicorn --workers 4` 不能配 SQLite checkpoint？**
每个 worker 是独立进程，各自有内存缓存，却写同一个 SQLite 文件；文件锁只保证进程内线程安全，
跨进程写不安全。多 worker 必须换 PostgreSQL 共享存储。

**7. Agent 服务为什么不能只按 QPS 扩容？**
Agent 是长任务、长连接、有状态、成本随轨迹超线性。容量单位是并发会话数 × 停留时间，还要看
token 吞吐和供应商 RPM/TPM 配额；200 并发 × 20 秒只相当于 10 QPS，但需要挂住 200 条连接。

**8. 幂等键的设计要注意什么？**
只覆盖写操作；key 相同但 body 不同返回 409；执行中返回 409/202；完成后缓存响应并设 TTL；
流式接口要么不缓存，要么缓存事件流并标注重放；审批按钮先判终态再执行。

## 面试追问

**Q1：你的项目从 demo 到生产还差什么？**
要点：按十件事说，主动标缺口。已落地：JWT 鉴权、默认拒绝权限、Redis 限流、网关审计、
Prometheus/OTel、token 计费与 402。部分：审计还是内存 sink、成本是进程内、韧性层未接主线。
缺口：幂等、灰度、压测。最后说优先级：先幂等和共享预算，再灰度和压测。

**Q2：多副本下会话状态怎么处理？**
要点：checkpoint 外置到 PostgreSQL，`thread_id` 是主键，任意副本都能恢复，不需要粘性会话；
SQLite 只适合单机单写者；连接池按副本配置，`setup()` 幂等；还要考虑表增长、归档和清理。
引流一句 ADR-0005 的三档后端。

**Q3：限流怎么做？Redis 挂了怎么办？**
要点：单副本令牌桶允许突发；多副本 Redis ZSET 滑动窗口，Lua 原子执行清理/计数/写入；
member 带 uuid 防同毫秒覆盖；故障降级到本地桶，fail-degraded 而非 fail-open；429 带
Retry-After，客户端要退避。

**Q4：K8s 里 Agent 服务怎么配探针和停机？**
要点：startup/liveness 用 `/healthz`，绝不查下游；readiness 用 `/readyz`，critical 失败 503；
`terminationGracePeriodSeconds` 给足，preStop 先摘流量再 drain SSE；工具执行到一半不能硬杀，
配合幂等重试；`maxUnavailable: 0` 滚动更新。

**Q5：成本怎么防失控？**
要点：token 级 callback 记账；调用前硬预算，超限 402；单请求 max_tokens/max_steps；
每租户配额；缓存命中单独入账；多副本把累计值放共享存储；对 P99 token 和工具调用次数做告警。
一句话：预算要在调用前生效，不是月底看账单。

**Q6：prompt 或模型怎么灰度？**
要点：prompt/模型版本当配置，进 git、带版本号；按用户 hash 或 header 分流；trace 打
`deploy.version` 标签；对比 pass^k、成本、P95 延迟；设自动回滚阈值；数据库 schema 变更用
expand/contract，保证新旧版本并存。
